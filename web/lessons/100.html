2.5 @login_required：视图的门卫 ★

装饰器是放在函数定义前面的「@ 指令」，在函数运行前先跑一遍自己的代码。@login_required 的逻辑就一句：没登录？不许运行这个视图，重定向到登录页。

类比：小区门禁。没门禁卡的人到不了楼里，直接被请到物业登记（登录页）。settings.LOGIN_URL 就是告诉门禁「物业办公室在哪」——不配这一行，门禁不知道把人往哪送。

用起来极简单，但别漏：

Pythonfrom django.contrib.auth.decorators import login_required


@login_required
def topics(request):
    """显示所有主题。"""
    topics = Topic.objects.filter(owner=request.user).order_by("date_added")
    context = {"topics": topics}
    return render(request, "learning_logs/topics.html", context)

保护策略（教材的建议，值得抄走）：先列出哪些页面不需要保护——主页（谁都能看）、注册页（没账户的人才来）——然后限制对其他所有页面的访问。过于严格的限制顶多被用户抱怨，漏保护敏感页面则是事故。

2.6 数据隔离的安全红线 ★★★

本单元最重要的一句话：查询数据时，必须按当前用户过滤。写 Topic.objects.filter(owner=request.user).order_by("date_added")，而不是 Topic.objects.all()——后者不管是谁的，全都捞出来。

.all() 的后果：用户 A 登录后，能看到用户 B 的所有主题和条目。类比：酒店的房卡只能开自己的门——filter(owner=request.user) 是「按门牌号发钥匙」，.all() 是「把整栋楼的钥匙复印一份发给每个客人」。教材在讲超级用户权限时特意提醒：用户对访问的应用程序有极大的信任，优秀的管理员会小心对待用户的敏感信息——这不是风度问题，是职业道德和法律责任。

数据隔离要做三层，一层都不能少：

层 页面 手段
列表层 主题列表 filter(owner=request.user)，只捞自己的
详情层 单个主题 查到后比对 topic.owner != request.user，不等就 raise Http404
编辑层 编辑条目 通过 entry.topic.owner 往上追两层，不等就 raise Http404

为什么「查出来再在 Python 里筛」不行？那等于把全楼的钥匙读一遍再扔掉。filter(owner=...) 在数据库层面过滤，捞出来的就只有你该看的。
