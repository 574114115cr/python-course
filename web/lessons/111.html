四、动手练习

基础档

练习 21-1【给三个项目补齐工程件】 为外星人入侵、数据可视化、学习笔记各补齐缺失的工程件。要求：① 每个项目根目录有 README.md（必含三段：这是什么 / 怎么装依赖 / 怎么运行，附一段运行输出示例）；② 有 requirements.txt，由 pip freeze > requirements.txt 生成且依赖都锁了版本；③ 有 .gitignore，至少忽略 __pycache__/、虚拟环境目录、.env；④ 三个项目都 git init 过并推到公开仓库。验收点：跑一遍示例 1 的 project_doctor.py，问题数为 0；把任意一个仓库 clone 到另一台机器，照 README 能跑起来——关卡 2 第 1 条就过了。

练习 21-2【给自己的函数写 pytest 测试】 不许抄教材里现成的测试。挑三个项目里各一个纯逻辑函数（不碰屏幕、不碰数据库的），各写 2 条 pytest 测试。要求：① 文件名 test_xxx.py、函数名 test_xxx；② 每条测试断言具体数值（不是 assert result is not None）；③ 至少覆盖一条边界情况（0、空列表、非法输入）；④ pytest -v 输出全绿。验收点：能逐条说清「这条测试在防哪种 bug」。项目里没有纯逻辑函数的话，先按 2.3 标准一拆文件。

进阶档

练习 21-3【重构冲刺】 任选一个项目（推荐外星人入侵，alien_invasion.py 通常最大），做一次 60 分钟的重构冲刺。要求：① 用示例 3 跑出基线（重构前的总行数、最长函数、最高复杂度）；② 按「谁调用它」拆文件，每个新文件不超过 300 行；③ 把魔法数字/路径抽到 settings.py；④ 拆完后功能必须和重构前完全一样；⑤ 再跑一次示例 3，对比前后数据。验收点：能说清「重构后代码行数变多」的原因（拆文件会多出 import 和模块文档字符串，这是正常的；可维护性提升不以行数下降衡量）。

练习 21-4【接手一个陌生项目】 找一个真实的开源 Python 项目（200–800 行、3 个以上文件），按 2.4 的五步读它，并完成：① 画出目录树 + 每个文件角色的清单；② 找到程序入口，从入口往下追三层调用关系；③ 找到一个你认为是 bug 的地方，写出复现步骤并用 # INTENTIONALLY-BROKEN 标出来；④ 如果上游有 issue 区，说明你的问题是不是已知问题。验收点：能用 5 分钟向别人口述这个项目「干什么、怎么跑、入口在哪、你发现的 bug 在哪一行」。

参考答案 21-2（pytest 测试，可直接运行）

以「外星人入侵」里 game_functions.py 的三个纯逻辑函数为例：

Python# test_game_functions.py —— 关卡 2 第 3 条的验收材料：自己写的测试
import pytest

from game_functions import check_collision, check_ship_limit, update_score


# ===== 一个只提供 colliderect 的替身，够测试用了 =====
class FakeRect:
    def __init__(self, x, y, w, h):
        self.x, self.y, self.w, self.h = x, y, w, h

    def colliderect(self, other):
        return (self.x < other.x + other.w and self.x + self.w > other.x
                and self.y < other.y + other.h and self.y + self.h > other.y)


def far_apart():
    """飞船和外星人相距很远，谁也碰不到谁。"""
    return FakeRect(0, 0, 10, 10), FakeRect(500, 500, 50, 50)


class TestCheckShipLimit:
    def test_normal(self):
        """正常：还有 2 艘。"""
        assert check_ship_limit([1, 2]) == 2

    def test_zero_ships_means_game_over(self):
        """★ 边界：0 艘必须返回 0，调用方据此结束游戏。"""
        assert check_ship_limit([]) == 0

    @pytest.mark.parametrize("ships,expected", [([], 0), ([1], 1), ([1, 2, 3], 3)])
    def test_parametrized(self, ships, expected):
        """参数化：一次测多个输入。"""
        assert check_ship_limit(ships) == expected


class TestCheckCollision:
    def test_ship_hits_alien(self):
        """飞船和外星人位置重叠 → 碰撞。"""
        assert check_collision(FakeRect(100, 100, 50, 50),
                              FakeRect(120, 120, 50, 50), []) is True

    def test_bullet_hits_alien(self):
        """★ 飞船没撞到，但子弹撞到了 → 也算碰撞。"""
        ship, alien = far_apart()
        assert check_collision(ship, alien, [FakeRect(510, 510, 10, 10)]) is True

    def test_no_collision(self):
        """谁都没碰到 → 不碰撞。"""
        ship, alien = far_apart()
        assert check_collision(ship, alien, []) is False


class TestUpdateScore:
    def test_one_alien(self):
        """★ 断言具体数值：1 个外星人 = 10 分。"""
        assert update_score(0, 1) == 10

    def test_none_hit_adds_zero(self):
        """边界：没击落任何外星人，分数不变。"""
        assert update_score(30, 0) == 30

    def test_custom_points(self):
        """改成每只 20 分。"""
        assert update_score(0, 2, points_per_alien=20) == 40

    def test_negative_score_is_allowed(self):
        """★ 业务约定：分数可以减（踩到外星人扣分），不是 bug。"""
        assert update_score(5, -1) == -5

参考答案 21-4（陌生项目定位 bug 的完整过程）

定位 bug 的标准动作。假设读到一个这样的小游戏片段：

Python# buggy_code.py —— INTENTIONALLY-BROKEN 演示用：4 处 bug，请自己发现
import pygame


def check_keydown(event, ship, bullets):
    """处理按键。"""
    if event.key == pygame.K_q:
        sys.exit()                      # bug 1：用了 sys.exit() 但没 import sys
    elif event.key == pygame.K_SPACE:
        bullets.add(Bullet(ship))       # bug 2：Bullet 类没定义、也没导入
    elif event.key == pygame.K_RIGHT:
        ship.moving_right = False       # bug 3：按右键反而停下，应该 = True


def update_aliens(aliens):
    """让整个舰队横向移动。"""
    for alien in aliens.sprites():
        alien.x += 1
    if len(aliens) == 0:
        game_active = False            # bug 4：只是定义了函数内的局部变量

定位过程（这四步就是关卡 2 第 4 条的答案）：

步骤 做法 对上面代码的发现
① 分类 看 import 和目录：用了 pygame，属于「事件驱动的图形程序」 搜 if __name__ 找到入口 run_game()
② 静态看 从入口往下追三层：run_game → check_keydown / update_aliens 找到两个可疑函数
③ 读报错 看 traceback 的最后一行（异常类型）和第一行 File "…", line N NameError: name 'sys' is not defined（bug 1）→ 定位到具体行
④ 判断是不是 bug 对着「代码想表达的意思」逐行对照 bug 2/3/4 静态就能看出来

修复要点：bug 1、2 补上 import sys 和 from bullet import Bullet；bug 3 把 ship.moving_right = False 改成 True；bug 4 把 update_aliens 改成接收一个 game_state 字典参数，写 game_state["active"] = False，让状态改动作用到调用方可见的对象上。

★ bug 4 最值得记住：game_active = False 只在函数内创建了一个局部变量，函数一返回就没了，调用方的状态一点没变。这和阶段 1 里 self.count = count 是同一个家族的问题——赋值只是给一个名字绑定对象，能不能影响别人，取决于这个名字的作用域。

六、常见错误清单（务必逐条自查）

错误 1：★ 没有 .gitignore 就 git add .，虚拟环境和数据库进了仓库

现象：git push 传了 400MB。原因：没有 .gitignore，git add . 把一切都加进去了。修复：补写 .gitignore，再 git rm -r --cached ll_env 把已跟踪文件撤出索引（只删索引，不删本地文件），然后提交。

错误 2：pip freeze 在全局环境执行，清单长到没法看

现象：requirements.txt 有 80 行，大部分是本项目没用到的包。原因：没建虚拟环境就 pip freeze，冻的是全局环境。修复：python -m venv venv → 激活 → 只装项目需要的包 → pip freeze > requirements.txt。

错误 3：★ 测试全是抄教材的，自己一条没写

现象：关卡 2 第 3 条过不了。原因：test_game_functions.py 里全是照抄的用例，没有一条针对你自己写的代码。修复：挑 3 个自己的纯逻辑函数，各写 2 条断言具体数值的测试（练习 21-2）。判断标准：关掉讲义后还能写出来，才算真的会。

错误 4：把 SECRET_KEY 硬编码在 settings.py 里，还推上了公开仓库

现象：仓库公开后被人 issue 提醒。原因：SECRET_KEY = "django-insecure-…" 直接写在代码里。修复：改成 os.environ["DJANGO_SECRET_KEY"]，立刻去平台后台重置旧密钥（删记录没用，克隆里已经有了），把 .env 加进 .gitignore、提交 .env.example 说明要配哪些变量。

错误 5：代码里全是魔法数字，改一个参数要翻 8 个文件

现象：「敌人快一点」这个需求改了半小时。原因：alien.rect.top += 1 这种数字散落在各处。修复：按 2.3 标准二抽到 settings.py，用有名字的常量替换；改完再搜一遍那个数字，确认没有漏网。

错误 6：所有代码堆在一个文件里，两千行

现象：想加个功能要读 500 行才敢动手；pytest 一导入就把 pygame 窗口开起来了。原因：没拆文件（2.3 标准一）。修复：按「谁调用它」拆，先把纯逻辑挑出来——这一步顺带就解决了测试要开窗口的问题。

七、本单元验收自测

1. 判断题：跟着教材把三个项目完整敲了一遍，就算「具备独立做项目的能力」了。

要点：错误，也是最需要警惕的自我感觉。跟着敲得到的是能跑的代码；独立做项目需要的是能交付、能维护、能被接手的工程——判断标准就是关卡 2 那五条。三个项目敲完但一条硬指标没过，只能算「完成了教材」。

2. 简答题：为什么 requirements.txt 里每个依赖都要写 == 版本号？什么时候可以不写？

要点：因为部署环境是一台全新的机器，只能靠清单重建；不带版本号就是「装最新版」，大版本升级可能带不兼容改动，半年后重建环境直接启动失败。可以不写的情况只有一种：这个包只在你本地开发环境用（如 platformshconfig、本地 gunicorn），但即使这种也建议写清，注释说明理由。

3. 改错题：下面这段想把「最高分」从 JSON 文件读出来，错在哪里？该怎么改？

Python# high_score_buggy.py —— INTENTIONALLY-BROKEN 演示用：改错题
import json

HIGH_SCORE_FILE = "data/high_score.json"


def load_high_score():
    with open(HIGH_SCORE_FILE) as f:      # 第一次运行时文件还不存在，会直接崩
        return json.load(f)["score"]

要点：三个问题。① 没处理文件不存在：第一次运行 FileNotFoundError 直接崩，游戏开不了；修法是 try/except FileNotFoundError 返回默认值 0。② 没指定 encoding="utf-8"：Windows 默认按 GBK 打开，含中文时抛 UnicodeDecodeError。③ 路径硬编码：按 2.3 标准二应放进 settings.py。建议另补 except json.JSONDecodeError 处理文件被写坏的情况。

4. 简答题：接手一个 500 行的陌生项目，你的前三步分别做什么？为什么不能从头读到尾？

要点：① 画目录树 + 标文件角色（入口 / 配置 / 测试 / 业务逻辑 / 数据），python explorer.py 项目路径 可自动完成；② 读 README 和 requirements.txt，知道它解决什么问题、用了什么库；③ 从入口往下追三层调用关系（__main__ → main() → 它调用的函数 → 被调用函数的定义）。从头读到尾会把常量、工具函数、类、业务逻辑混着看，读完记不住也拼不出全貌——先建地图再进细节，是读代码的第一原则。

5. 简答题：print() 和 logging 有什么区别？为什么正式项目要用后者？

要点：print 无条件打到标准输出，没有时间戳、没有级别、不能按级别开关、不能按文件分类、出错后不留痕。logging 有级别（DEBUG/INFO/WARNING/ERROR）、有格式（时间+级别+模块+内容）、可同时输出到终端和文件（RotatingFileHandler 自动轮换防写满磁盘）。用 logging 的真正价值是：出问题时能回头查「那一刻发生了什么」。模板见示例 4。

八、关卡 2 验收标准（五条硬指标）

这五条对应学习路线图与主页上的「关卡 2 · 判定『能独立做项目』」。五条全部达标，说明你已经从「会写代码的人」变成「能交付软件的人」。

✅ 硬指标 1：三个项目全部跑通，且已推到公开仓库，每个都有 README + requirements.txt

怎么算达标：三个仓库链接都拿到了；每个仓库首页能看到 README；每个仓库里有 requirements.txt 且依赖都带 ==；把任意一个仓库 clone 到另一台机器，照 README 能跑起来。怎么验证：跑一遍示例 1 的 project_doctor.py，问题数为 0。没过怎么办：README 照参考答案 21-1 的三段结构写；requirements.txt 在虚拟环境里重新 pip freeze > requirements.txt；仓库还没有就 git init → git add . → git commit → 建远程仓库 → git push。

✅ 硬指标 2：「学习笔记」已部署上线，公网可访问，错误页已定制

怎么算达标：platform url 给出的网址在手机流量（不是同一个 WiFi）下能打开；访问不存在的网址返回你定制的 404 页；服务器出错时 500 页也是定制的，不是 Django 调试页。怎么验证：重点测首页、/不存在/、/accounts/login/ 三个 URL。没过怎么办：回单元 20，按 2.7 节三大坑（ALLOWED_HOSTS、collectstatic、DEBUG）逐项排查，改完 git commit + platform push。注意：定制错误页只在 DEBUG = False 时生效，本地默认看不到。

✅ 硬指标 3：能用自己的函数写出 pytest 测试并跑过（不是抄教材的）

怎么算达标：≥ 3 条测试针对你自己项目里的纯逻辑函数；每条断言具体数值；至少一条覆盖边界（0 / 空 / 非法输入）；pytest -v 全绿。怎么验证：关掉讲义和教材，只留项目代码和 pytest，问自己：这三条测试的断言值我能自己算出来吗？ 算不出来就是抄的。没过怎么办：先按 2.3 标准一把纯逻辑从「界面/数据库代码」里拆出来（这是前提），再照参考答案 21-2 写。记住：文件名和函数名都要 test_ 前缀，命名不对 pytest 显示 collected 0 items 而不报错。

✅ 硬指标 4：接手一个没写过的 500 行 Python 项目，能读懂结构并定位一个 bug

怎么算达标：能在 30 分钟内画出结构图、指出入口、找到至少一处 bug（或明确的改进点）并说明理由；能判断项目属于哪一类（脚本 / 事件驱动 / 数据处理 / Web）。怎么验证：按 2.4 的五步走一遍，用 grep -rn 搜关键字。没过怎么办：找不到入口就搜 if __name__；读不懂逻辑就画调用图（grep 搜函数名看谁调用谁）；不敢确定是 bug就看上游有没有 open 的 issue。

✅ 硬指标 5：能说清每个项目「解决了什么问题、还能怎么扩展」

怎么算达标：对三个项目各能回答两问——① 它解决什么真实问题（不是「练了 xxx API」）；② 至少说得出三条扩展方向，并能说明每条要动哪几个文件。怎么验证：录一段 3 分钟口述，或写进每个项目 README 的「未来想法」一节。没过怎么办：这题问的是判断力，只能自己想。万能模板（以数据看板为例）：① 数据源换更细的粒度；② 加一个导出报告的功能；③ 每天定时跑并把结果推给你。能说出「要动哪几个文件」，就说明你真懂它的结构。
