◆ 复盘（10 分钟）｜上一节：第 52 节 · 为什么需要测试与三条命名规则

  • Bug 分两种：语法错（跑不起来）和逻辑错（跑得起来但结果不对）——测试专治第二种。
  • 三条命名规则：文件名 test_*.py、函数名 test_*、类名 Test*。
  • 不符合命名规则的测试，pytest 根本不会收集——静默不跑，最容易误判成「测试通过了」。
  • 上节作业：10-1 ~ 10-2 做完几道？

◆ 课堂实操（40 分钟，全程不许看答案）

  1. 给一个函数写 3 条测试：正常 / 边界 / 异常
  2. 故意让一条测试失败并读懂报告

2.4 assert：用代码描述"应该是什么"

assert 的意思是"断言"。写法是：assert 表达式，表达式为假就报错。

Pythondef test_add():
    assert 1 + 1 == 2          # 通过：条件为真，测试通过

def test_add_wrong():
    assert 1 + 1 == 3          # 失败：AssertionError

关键在于 assert 里要写"实际结果 == 预期结果"，而不是只写实际结果：

Python# 不推荐：只测了"返回了一个东西"，测不出返回值对不对
def test_bad(result):
    assert result is not None

# 推荐：明确写出期望值
def test_good():
    assert add(2, 3) == 5

断言消息：可以给 assert 加一句说明，失败时这条消息会显示出来。这在测试复杂逻辑时非常有用：

Pythonassert actual == expected, f"期望 {expected}，实际得到 {actual}"

2.5 测试与被测代码必须分离

不要把测试代码写在被测文件里。 正确做法是两个文件：

目录结构project/
├── calculator.py       ← 被测代码（纯粹的函数定义）
└── test_calculator.py  ← 测试代码（只有测试）

这样做的好处： 1. 测试可以独立运行、独立删除（删掉测试不影响程序运行）。 2. 被测代码保持干净，没有"为了测试而加的怪代码"。 3. 一目了然哪些是测试哪些是功能。

2.6 测试用例的设计：正常 + 边界

一个好的测试不只测"正常情况"，更重要的是测"极端情况"。

类别 例子
正常用例 divide(10, 2) == 5
边界用例 divide(10, 1)、divide(1, 10)
异常用例 divide(10, 0) —— 除零会怎样？
类型用例 add("a", "b") —— 字符串能加吗？
空值用例 average([]) —— 空列表会怎样？
负数用例 factorial(-1) —— 负数怎么处理？

除零、负数、空输入这三类是最容易藏 bug 的地方，也是面试和实际工作里最常被要求测试的点。本单元的练习会重点覆盖。
