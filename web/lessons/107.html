四、动手练习

基础档

练习 20-1【给「学习笔记」换装】 用 django-bootstrap5 改造登录页、主页、主题列表页。要求：① 安装并在 INSTALLED_APPS 注册；② base.html 引入 Bootstrap、导航区分登录态；③ 登录页用 {% bootstrap_form form %} 并保留 {% csrf_token %}；④ 主页用 jumbotron 大卡片，.jumbotron 写在 static/css/styles.css；⑤ 主题页用列表组逐行列出。验收点：三页都有 Bootstrap 样式；登录后导航变「你好，用户名 + 退出」；能说清每个模板文件改了影响哪些页面。

练习 20-2【写部署三件套】 写出 requirements.txt（用 pip freeze 生成，不许手写版本号）、requirements_remote.txt（只放 gunicorn 和 psycopg2 并写注释）、.gitignore（至少忽略虚拟环境、__pycache__、*.sqlite3）、.platform.app.yaml、.platform/routes.yaml、.platform/services.yaml。要求两处「暗号」对上：routes 的 upstream ↔ app.yaml 的 name；app.yaml 的 relationships ↔ services.yaml 的服务名。验收点：能解释每个文件「谁读它、什么时候读、读错会怎样」。

练习 20-3【诊断三个线上故障】 三个故障都发生在部署之后：① 打开网址显示 400 Bad Request；② 页面能打开但没有样式；③ 部署日志报 ModuleNotFoundError: No module named 'gunicorn'。不写代码，回答每个现象的根因、验证方法、修法。验收点：三个原因都能定位到具体文件的具体一行，并说清「为什么本地没这问题」。

进阶档

练习 20-4【本地模拟双环境】 参考示例 1 写一个 env_switch.py：不安装 platformshconfig，仅用 os.environ 以 PLATFORM_APPLICATION 控制，打印两套配置对比（DEBUG、数据库引擎、ALLOWED_HOSTS、STATIC_ROOT、SECRET_KEY 来源），并写注释解释 is_valid_platform() 为什么能判断「我在云上」。验收点：python env_switch.py 与 PLATFORM_APPLICATION=1 python env_switch.py（Windows PowerShell 用 $env:PLATFORM_APPLICATION="1"; python env_switch.py）两次输出确实不同。

练习 20-5【本地验证定制错误页面】 在本地把 404/500 定制页面做完并跑出来验证（难点：DEBUG=True 时定制页不生效）。要求：① 建项目级 templates/，放 404.html 和 500.html，都继承 base.html；② settings.py 的 TEMPLATES['DIRS'] 指向它；③ 用 Django 测试客户端请求一个不存在的路径，确认返回 404 且用的是你的模板。验收点：能说清「为什么本地默认看不到定制错误页」。

练习 20-6【扩展部署检查清单】 在示例 5 基础上给 deploy_checklist.py 增加至少 3 项检查。建议方向：requirements.txt 是否锁版本、有没有 pytest 测试文件、routes 的 upstream 和 app.yaml 的 name 是否一致、build 钩子是否包含 collectstatic。验收点：新增检查在「缺项」和「齐全」两种情况下都能正确报 ✓/✗；脚本不依赖 Django，纯标准库。

参考答案 20-3（故障诊断）

# 根因 怎么验证 怎么修
1 ALLOWED_HOSTS 没有包含线上域名，Django 在校验 Host 阶段直接 400，视图根本没执行 看部署日志里是否有 DisallowedHost Platform.sh 段加 ALLOWED_HOSTS.append('.platformsh.site')，提交后重新 push
2 DEBUG = False 后 Django 不再代发静态文件，而 collectstatic 没跑或 /static 路由没配，CSS/JS 全 404 浏览器开发者工具 → Network，看 CSS 请求是不是 404 build 钩子确保有 collectstatic --noinput；确认 STATIC_ROOT 已设置
3 gunicorn 只写在 requirements_remote.txt，但 build 钩子漏了 pip install -r requirements_remote.txt（或文件没提交） 看部署日志 build 阶段的输出 补上这行 pip install；确认新文件已 git add 并提交

共同教训：三个故障本地全都不会出现。本地 DEBUG=True 兜底了静态文件、localhost 天然在白名单里、依赖是你手动装的。部署的本质就是把这些「本地豁免」一项项取消。

参考答案 20-4（本地模拟双环境）

Python# env_switch.py —— 不装 platformshconfig，纯 os.environ 模拟双环境配置
import os

def build_settings():
    """模拟 settings.py：同一份逻辑，两套配置。

    platformshconfig 的 is_valid_platform() 底层就是在查
    PLATFORM_APPLICATION：Platform.sh 运行应用时一定会注入它，
    本地没有——所以「变量存在与否」就是「我在哪」的判据。
    """
    on_platform = os.environ.get("PLATFORM_APPLICATION") == "1"
    return {
        "DEBUG": not on_platform,
        "数据库": "PostgreSQL（credentials('database')）" if on_platform else "SQLite（db.sqlite3）",
        "ALLOWED_HOSTS": ["localhost", ".platformsh.site"] if on_platform else ["localhost"],
        "STATIC_ROOT": "/app/static" if on_platform else None,
        "SECRET_KEY": "config.projectEntropy" if on_platform else "settings.py 里的字符串",
        "错误页面": "定制 404/500" if on_platform else "Django 调试页（DEBUG=True）",
    }


if __name__ == "__main__":
    label = "Platform.sh 云环境" if os.environ.get("PLATFORM_APPLICATION") else "本地开发"
    print(f"=== 当前环境：{label} ===")
    for key, value in build_settings().items():
        print(f"  {key:<14} = {value}")

参考答案 20-6（检查清单增强版）

在示例 5 基础上新增一项「依赖体检」（完整脚本 = 示例 5 + 下面新增部分），其余方向（测试文件有无、build 钩子是否含 collectstatic）思路相同，都是「读文件内容 → 判断关键词」：

Python# 新增检查：requirements.txt 是否锁版本 + 线上依赖齐全
def check_requirements(root):
    results = []
    main_file = root / "requirements.txt"
    if not main_file.exists():
        return [("✗", "requirements.txt 不存在")]
    text = main_file.read_text(encoding="utf-8")
    unpinned = [
        line for line in text.splitlines()
        if line.strip() and not line.strip().startswith("#") and "==" not in line
    ]
    if unpinned:
        results.append(("✗", f"有未锁版本的依赖：{unpinned}"))
    remote = root / "requirements_remote.txt"
    remote_text = remote.read_text(encoding="utf-8") if remote.exists() else ""
    for pkg in ("gunicorn", "psycopg2"):
        if pkg not in remote_text.lower():
            results.append(("✗", f"requirements_remote.txt 缺少 {pkg}（线上跑不起来）"))
    if not results:
        results.append(("✓", "依赖清单：版本已锁，线上依赖齐全"))
    return results

调用时把新检查加进 report()（片段，需与示例 6 合在一起运行）：

六、常见错误清单（务必逐条自查）

错误 1：★ ALLOWED_HOSTS 没加平台域名，线上 400

现象：部署成功、日志没报错，但一打开网址就是 400 Bad Request。原因：Django 校验每个请求的 Host 头，不在 ALLOWED_HOSTS 就直接 400，视图根本不执行。修复：settings.py 的 Platform.sh 段加 ALLOWED_HOSTS.append('.platformsh.site')，提交后重新 push。

错误 2：忘了注册 django_bootstrap5，模板报 Invalid block tag

现象：页面 500，报 TemplateSyntaxError: Invalid block tag: 'bootstrap_form'。原因：{% load %} 只是「打开工具包」，包本身要在 INSTALLED_APPS 注册。修复：INSTALLED_APPS 加 'django_bootstrap5'。

错误 3：DEBUG 关了却没收静态文件，白脸页面

现象：线上页面结构都在，但没有样式。原因：DEBUG = False 后 Django 不再代发静态文件；collectstatic 没跑，或 STATIC_ROOT 没设置。修复：build 钩子确保有 python manage.py collectstatic --noinput，云上段设置 STATIC_ROOT。

错误 4：requirements.txt 漏了 gunicorn 或 psycopg2

现象：部署日志 ModuleNotFoundError: No module named 'gunicorn'，或连不上数据库。原因：本地用 runserver + SQLite，这两个包本地没装过，pip freeze 不会列出来。修复：建 requirements_remote.txt 写上两者，并在 build 钩子里 pip install -r requirements_remote.txt。

错误 5：.gitignore 缺失，虚拟环境和本地数据库被推上云

现象：push 奇慢，仓库几百 MB；甚至线上用了你本地带数据的 SQLite 文件。原因：没有 .gitignore，git add . 把 ll_env/、__pycache__/、db.sqlite3 全提交了。修复：补写 .gitignore，用 git rm -r --cached 把已跟踪文件撤出索引，再提交。

错误 6：新文件忘了 git add，推送后线上缺东西

现象：本地明明建了 templates/404.html，线上还是默认错误页。原因：git commit -am 只提交已跟踪文件的修改，新文件必须先 git add。修复：只要产生了新文件（包括 makemigrations 生成的迁移文件），先 git add . 再 commit。

七、本单元验收自测

1. 简答题：{% load django_bootstrap5 %} 和 {% bootstrap_form form %} 分别负责什么？只写后者不写前者会怎样？

要点：load 把模板标签库加载进当前模板，是「拿工具」；bootstrap_form 把字段逐个渲染成带 Bootstrap 类名的 HTML，是「干活的」。只写后者会报 TemplateSyntaxError: Invalid block tag——INSTALLED_APPS 注册和模板 load 缺一不可。

2. 判断题：requirements.txt 里写 Django（不带 == 版本号）也能正常部署，只是不优雅。

要点：错误。不带 == 意味着装最新版。大版本升级经常带不兼容改动，半年后平台重建环境时可能直接启动失败。锁版本是部署的纪律，不是风格问题。

3. 简答题：relationships: database: "db:postgresql" 里的暗号怎么读？routes.yaml 的 upstream: "ll_project:http" 又和谁对应？

要点："db:postgresql" 冒号前是 services.yaml 里的服务名（db），冒号后是服务类型；config.credentials('database') 读的就是这份关系。routes 的 upstream 必须和 .platform.app.yaml 的 name 一致——路由按应用名转发域名。两处暗号对不上，部署直接失败。

4. 改错题：下面这段被加进 settings.py 的 Platform.sh 段，但部署后数据库连不通。为什么？

Python# settings_snippet.py —— INTENTIONALLY-BROKEN 演示用：改错题，数据库配置连不通
from platformshconfig import Config

config = Config()
if config.is_valid_platform():
    db_settings = config.credentials('database')
    # 有 bug：引擎写死 SQLite，读来的 PostgreSQL 连接信息一个都没用
    DATABASES = {'default': {'ENGINE': 'django.db.backends.sqlite3', 'NAME': 'db.sqlite3'}}

要点：引擎写死了 SQLite，读来的 PostgreSQL 连接信息（host/port/username/password）一个都没用。云上必须用 'django.db.backends.postgresql'，并把 db_settings 的字段填进 NAME/USER/PASSWORD/HOST/PORT。另外 credentials('database') 要放在 if not config.in_build(): 里——构建阶段连不上数据库。

5. 简答题：DEBUG = False 之后，本地看到的报错页发生了什么变化？为什么定制 404/500 要求 DEBUG = False？

要点：DEBUG = False 后 Django 不再显示带堆栈信息的黄色调试页，而是渲染 templates/404.html/500.html。调试页会泄露配置细节（设置项、SQL、文件路径），只适合本地；线上关闭调试后，友好的定制错误页才出场。

6. 简答题：描述一次「加功能」的完整部署流程，从本地改第一行代码到线上验证。

要点：① 本地改代码并跑通；② 产生了新文件（含迁移文件）就 git add .；③ git commit -am "提交说明"；④ platform push（平台自动执行 build 钩子装依赖、collectstatic，再执行 deploy 钩子 migrate）；⑤ platform url 打开线上网址验证；出问题先看部署日志，修好再走一遍 ③④。
