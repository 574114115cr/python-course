2.3 阶段 1 → 阶段 2 的能力跃迁

维度 阶段 1 阶段 2
代码规模 单文件几十到几百行 多文件、几百到上千行
文件数 1 个 .py 目录 + 多模块 + 配置 + 模板
依赖 只有标准库 第三方库（pygame / matplotlib / Django）
依赖管理 不用管 requirements.txt 必须锁版本
数据存放 JSON / CSV 文件 SQLite → PostgreSQL，带迁移
别人能跑吗 给你代码你也许能跑 有 README 和 requirements，别人 5 分钟跑起来

标准一：单文件不超过 300 行。 超了按「谁在调用它」拆：

示例alien_invasion.py  400 行  →拆成↓
├── settings.py            所有常量（颜色、数量、速度）
├── ship.py                Ship 类
├── alien.py               Alien 类
├── bullet.py              Bullet 类
├── game_functions.py      update() / check_keydown() / fire_bullet() 等纯逻辑
└── main() 留在 alien_invasion.py 里，只负责"组装"

拆完有个意外的好处：game_functions.py 里全是纯逻辑、不碰 pygame 屏幕，这些函数能直接写 pytest 测试了（测的时候根本不用开窗口）。这就是「逻辑与 I/O 分离」的实际收益。

动手拆之前先量一遍，别凭感觉挑文件：

Python# 哪个文件该拆：先量再拆，别凭感觉
FILE_LIMIT = 300

PROJECT = {
    "alien_invasion.py": 412,
    "settings.py": 88,
    "ship.py": 64,
    "game_functions.py": 274,
    "test_game_functions.py": 96,
}


def should_split(files, limit=FILE_LIMIT):
    """返回 [(文件, 行数, 超出多少)]，按超出量从大到小。"""
    over = [(name, lines, lines - limit) for name, lines in files.items() if lines > limit]
    return sorted(over, key=lambda row: row[2], reverse=True)


for name, lines, extra in should_split(PROJECT):
    print(f"{name:<24}{lines:>5} 行  超出 {extra} 行 -> 按「谁调用它」拆")

print(f"\n其余 {len(PROJECT) - len(should_split(PROJECT))} 个文件都在 {FILE_LIMIT} 行以内：")
for name, lines in sorted(PROJECT.items(), key=lambda x: -x[1]):
    if lines <= FILE_LIMIT:
        print(f"  {name:<24}{lines:>5} 行")

print("\n★ 拆完行数往往变多（每个新文件多 import + 文档字符串），")
print("   衡量指标是「最长文件」和「最长函数」，不是总行数。")

这份清单里只有 alien_invasion.py（412 行，超出 112 行）该拆，game_functions.py 的 274 行虽然接近上限但还在线内。先拆超出最多的那个，拆完重新量一次，别一次动三个文件——否则功能坏了你不知道是哪次拆分引入的。

标准二：配置与逻辑分离。 判据很简单：代码里出现一个"魔法数字"或"魔法字符串"，就应该考虑搬到配置文件里。

Python# 反面：逻辑和配置糊在一起
def create_ship():
    return Ship(57, 63, pygame.image.load("images/ship.bmp"), 5)
    #                      ↑多少   ↑多少        ↑路径           ↑速度
    #                     改一次要动函数体，改坏了不知道是谁的锅

def create_ship():
    return Ship(SHIP_START_X, SHIP_START_Y, pygame.image.load(SHIP_IMAGE), SHIP_SPEED)

Django 侧更彻底：ll_project/settings.py 是纯配置，models.py / views.py 是纯逻辑。单元 20 追加 Platform.sh 配置时，逻辑一行都没动——这就是分离带来的安全感。

2.4 常见工程问题速查

这一节是「查手册」性质的，卡住时回来翻。

问题一：依赖怎么锁？ 在虚拟环境里执行 pip freeze > requirements.txt，别人拿到项目后 pip install -r requirements.txt 重建环境。三条纪律：① 只在虚拟环境里 pip freeze，否则会把系统全局的包也冻进去；② 必须带 == 版本号，不带就是「装最新版」，半年后可能装到不兼容的大版本；③ 间接依赖也留着（asgiref、sqlparse 是 Django 带进来的）。

问题二：密钥怎么不提交？ 一行口令：密钥只从环境变量读，永远不写进代码。

Pythonimport os
# 正确：代码里没有密钥本身，值从环境变量来
SECRET_KEY = os.environ["DJANGO_SECRET_KEY"]

# 错误：密钥躺在代码里，推到公开仓库谁都能拿到
SECRET_KEY = "django-insecure-9f8a7b6c5d4e3f2a1b0c9d8e7f6a5b4c"

配套三步：① .gitignore 忽略 .env、settings_local.py；② 仓库里放 .env.example，只写键名不写值；③ 密钥已经推出去了怎么办？立刻去平台后台重置旧密钥——删记录没用，旧值已在别人的克隆里。Django 的 SECRET_KEY 泄露，攻击者能伪造 sessionid cookie 冒充任意用户。

读取函数的写法有个反直觉的纪律：读不到就抛异常，绝不给默认值。

Python# 密钥读取：从环境变量来，缺了就立刻报错，绝不给默认值
import os

REQUIRED = ["DJANGO_SECRET_KEY", "DATABASE_URL"]


def read_secret(name, env=None):
    """读不到就抛异常——比给个默认值安全得多。"""
    env = os.environ if env is None else env
    value = env.get(name, "").strip()
    if not value:
        raise RuntimeError(
            f"环境变量 {name} 没设置。本地请写进 .env（已在 .gitignore 里），"
            f"线上请在平台面板配置，不要写死在 settings.py")
    return value


print("模拟环境里只配了一个变量：")
fake_env = {"DJANGO_SECRET_KEY": "s3cr3t-from-env"}
for name in REQUIRED:
    try:
        value = read_secret(name, fake_env)
        print(f"  [OK] {name} = {value[:4]}…（只打印前 4 位，日志里也别泄全）")
    except RuntimeError as error:
        print(f"  [缺] {error}")

print("\n★ 为什么不能给默认值：给了默认值，线上忘了配也不会报错，")
print("   于是所有会话都用一个公开的密钥签名——比直接崩掉危险得多。")

注意输出里只打印 s3cr… 前 4 位：日志本身也是泄露渠道，print(SECRET_KEY) 打出来的东西会进 CI 日志、进别人的终端。第二个变量缺失时直接抛 RuntimeError——宁可启动失败，也不要带着错误的默认值跑起来。

问题三：数据库怎么备份？ SQLite 就是一个文件，sqlite3 db.sqlite3 .backup backup.db 或直接复制走就是备份；PostgreSQL 用 pg_dump > backup.sql 导出、psql < backup.sql 恢复。Django 侧更省事：manage.py dumpdata > data.json / loaddata data.json。三个要点：① 备份要定期；② 异地存一份，同一台机器上的副本在磁盘坏掉时一起没；③ 定期演练恢复，没验证过的备份等于没有备份。

这三种库的命令不一样，写错一次就是在生产环境上试错。把命令生成出来、复制粘贴，比背下来可靠：

Python# 备份命令生成器：三种数据库，三种打法
from datetime import datetime
from pathlib import Path


def backup_plan(db_kind, db_path="db.sqlite3", stamp=None):
    """返回 (备份命令, 恢复命令, 备份文件名)。只拼字符串，不执行。"""
    stamp = stamp or datetime.now().strftime("%Y%m%d")
    if db_kind == "sqlite":
        name = f"backup_{stamp}.db"
        return (f"sqlite3 {db_path} \".backup {name}\"",
                f"cp {name} {db_path}", name)
    if db_kind == "postgresql":
        name = f"backup_{stamp}.sql"
        return (f"pg_dump {db_path} > {name}", f"psql {db_path} < {name}", name)
    if db_kind == "django-json":
        name = f"data_{stamp}.json"
        return ("python manage.py dumpdata > " + name,
                "python manage.py loaddata " + name, name)
    raise ValueError(f"不认识的数据库类型：{db_kind}")


for kind, target in [("sqlite", "db.sqlite3"),
                     ("postgresql", "learning_log"),
                     ("django-json", "-")]:
    dump, restore, name = backup_plan(kind, target, stamp="20261026")
    print(f"[{kind}] {name}")
    print(f"  备份：{dump}")
    print(f"  恢复：{restore}")

print("\n★ 三条纪律：定期备、异地存一份、定期演练恢复。")
print("   没恢复过的备份，等于没有备份。")
print("   另外：备份文件别提交进 git —— .gitignore 里加上 *.db / *.sql / *.json")

注意 dumpdata 生成的是 JSON 文本（跨版本、跨库都能读，但大库会很慢），pg_dump 生成的是 SQL 语句（快，但要版本匹配）。演练恢复才是重点：把 psql < backup.sql 真的对一个新的空库跑一次，你才会发现「备份里少了那张表」这类问题。

问题四：怎么读一个没写过的项目？ 五步，顺序别乱：

示例第 1 步  看目录树          哪些是入口？哪些是配置？哪些是测试？
第 2 步  读 README         它自称解决什么问题？怎么跑？
第 3 步  读依赖清单        requirements.txt 告诉你用了什么库
第 4 步  找入口再往外读    main.py / manage.py → 调用的函数 → 函数定义
第 5 步  grep 搜关键字     搜函数名/类名，找到全部使用点

第 5 步的具体命令（在项目根目录执行）：

终端命令grep -rn "def update" --include="*.py" .      # 找函数在哪定义、哪被调用
grep -rn "Group()" --include="*.py" .        # 找精灵编组在哪用
grep -rn "SECRET_KEY" --include="*.py" .     # 找密钥相关代码
grep -rn "class .*Model" --include="*.py" .  # 找 Django 模型

Windows 上没有 grep 也不要紧：这套搜索用 pathlib 十几行就能实现，还能顺手过滤编码坏掉的文件：

Python# 读陌生项目第 5 步的 grep，用 pathlib 自己实现一遍
from pathlib import Path

DEMO = {
    "game_functions.py": "def update_aliens(aliens):\n    for alien in aliens:\n"
                         "        alien.y += 1\n",
    "main.py": "from game_functions import update_aliens\n\n"
               "def main():\n    update_aliens([])\n",
    "notes.txt": "update_aliens 调用了两次\n",
}


def grep(root, keyword, suffix=".py"):
    """返回 ["文件:行号: 内容"]；只扫指定后缀，别把 .log 也扫进来。"""
    hits = []
    for path in sorted(Path(root).rglob(f"*{suffix}")):
        try:
            lines = path.read_text(encoding="utf-8").splitlines()
        except (UnicodeDecodeError, OSError):
            continue
        for lineno, line in enumerate(lines, 1):
            if keyword in line:
                hits.append(f"{path.name}:{lineno}: {line.strip()}")
    return hits


root = Path("data/demo_project")
for name, text in DEMO.items():
    path = root / name
    path.parent.mkdir(parents=True, exist_ok=True)
    path.write_text(text, encoding="utf-8")

for keyword in ("update_aliens", "def main"):
    print(f"搜索 {keyword!r}：")
    for hit in grep(root, keyword):
        print("  ", hit)
    print()

print("★ 四个最常用的搜索词（对应 2.4 节第 5 步）：")
print('  grep("def update")  找函数在哪定义、哪被调用')
print('  grep("Group()")     找编组在哪创建')
print('  grep("SECRET_KEY")  找密钥有没有硬编码')
print('  grep("class ")      找模型和类')

import shutil
shutil.rmtree("data", ignore_errors=True)

搜 update_aliens 命中三处（定义一次、import 一次、调用一次），这就是调用图的原材料：定义在 game_functions.py，入口在 main.py。搜 def main 只命中一处——它就是程序入口。notes.txt 里也出现了关键词，但只扫 *.py 的规则把它排除了。

为什么顺序重要：从头读到尾是新手读代码最慢的方式——你会同时看到常量、工具函数、类、业务逻辑，全都混在一起。先建「地图」再进细节，才不会迷路。示例 5 会给一个能把前四步自动做掉的脚本。
