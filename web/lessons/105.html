2.5 三个配置文件：一个描述应用，一个描述路由（对应教材 20.2）

这是本单元最需要建立宏观认识的部分。部署时你要告诉平台三件事：跑什么、怎么跑、从哪进。对应三个文件：

示例learning_log/
├── .platform.app.yaml      ← ① 应用清单：用什么运行、依赖什么、构建/部署时执行什么
├── manage.py
└── .platform/              ← 注意：这是个以点开头的隐藏文件夹
    ├── routes.yaml         ← ② 路由：域名怎么指过来
    └── services.yaml       ← ③ 服务：数据库容器怎么开

一次完整的请求这样流转：

示例浏览器访问 https://learning-log-main-xxxx.us-3.platformsh.site/
        │
        ▼
① .platform/routes.yaml ：「这个域名该转给谁？」
        │   "https://{default}/" → upstream: "ll_project:http"
        ▼
② .platform.app.yaml ：「应用怎么启动？」
        │   start: gunicorn ... ll_project.wsgi:application
        ▼
   gunicorn（WSGI 服务器）───► Django（ll_project/wsgi.py）
                          settings.py（platformshconfig 在运行时改写它）
                                    │
                                    ▼
                        ③ PostgreSQL（services.yaml 里定义的 db 容器）

.platform.app.yaml（和 manage.py 同级，注意别漏开头的点）：

YAMLname: "ll_project"                 # 应用名，routes.yaml 要靠它对上暗号
type: "python:3.12"                # 用什么语言、什么版本（教材写 3.10，以平台文档为准）

relationships:                     # 应用依赖哪些外部服务
    database: "db:postgresql"      # 叫 database 的关系 → 指向 services.yaml 里的 db

web:                               # 暴露到 Web 的配置
    upstream:
        socket_family: unix
    commands:
        start: "gunicorn -w 4 -b unix:$SOCKET ll_project.wsgi:application"   # 启动命令
    locations:
        "/":
            passthru: true         # 动态请求交给 gunicorn/Django
        "/static":
            root: "static"         # 静态文件直接由 Web 服务器发，不麻烦 Django

hooks:                             # 生命周期钩子：构建时和部署时各执行一批命令
    build: |
        pip install --upgrade pip
        pip install -r requirements.txt        # 本地依赖清单
        pip install -r requirements_remote.txt # 线上专用依赖清单
        python manage.py collectstatic --noinput   # ★ 收集静态文件（2.7 节细说）
    deploy: |
        python manage.py migrate               # 每次部署自动应用数据库迁移

.platform/routes.yaml：路由只干一件事——把域名指到应用。

YAML"https://{default}/":
    type: upstream
    upstream: "ll_project:http"    # ← 这个名字必须和 app.yaml 的 name 一致

"https://www.{default}/":
    type: redirect
    to: "https://{default}/"       # 带 www 的访问跳到主域名

.platform/services.yaml：服务清单，每个服务以独立容器部署。

YAMLdb:
    type: postgresql:16            # 开一个 PostgreSQL 容器（版本以平台文档为准）
    disk: 1024

app.yaml 的 relationships 说「我需要一个叫 database 的数据库」，services.yaml 说「我开一个叫 db 的 PostgreSQL」，两边用 "db:postgresql" 这个暗号对上；routes.yaml 的 upstream: "ll_project:http" 则要和 app.yaml 的 name 一致。两处暗号对不上，部署直接失败。

「对暗号」这件事不需要平台也能查——三个 yaml 都是文本，正则一比就知道：

Python# 三个 yaml 的「暗号」对不对得上，用字符串就能查
import re

APP = 'name: "ll_project"\nrelationships:\n    database: "db:postgresql"\n'
ROUTES = '"https://{default}/":\n    upstream: "ll_project:http"\n'
SERVICES = "db:\n    type: postgresql:16\n"


def audit(app_yaml, routes_yaml, services_yaml):
    """三处暗号：应用名 ↔ upstream、关系名 ↔ 服务名、关系类型 ↔ 服务类型。"""
    app_name = re.search(r'name:\s*"([^"]+)"', app_yaml)
    upstream = re.search(r'upstream:\s*"([^":]+)', routes_yaml)
    relation = re.search(r'database:\s*"([^":]+):([^"]+)"', app_yaml)
    service = re.search(r"^(\w+):", services_yaml, re.M)
    kind = re.search(r"type:\s*(\w+)", services_yaml)
    return [
        ("应用名 ↔ routes.upstream",
         app_name.group(1) == upstream.group(1),
         f"{app_name.group(1)} / {upstream.group(1)}"),
        ("关系名 ↔ services 服务名",
         relation.group(1) == service.group(1),
         f"{relation.group(1)} / {service.group(1)}"),
        ("关系类型 ↔ services 服务类型",
         relation.group(2) == kind.group(1),
         f"{relation.group(2)} / {kind.group(1)}"),
    ]


for label, ok, detail in audit(APP, ROUTES, SERVICES):
    print(f"[{'✓' if ok else '✗'}] {label}：{detail}")

print("\n改坏一处试试（把 routes 的 upstream 改成 app）：")
bad = audit(APP, ROUTES.replace("ll_project:http", "app:http"), SERVICES)
for label, ok, detail in bad:
    print(f"[{'✓' if ok else '✗'}] {label}：{detail}")
print("第一项立刻变 ✗ —— 部署会报「找不到应用 app」，但本地 runserver 一切正常。")

2.6 platformshconfig：一份代码怎么知道自己在哪（对应教材 20.2）

现在到本单元最烧脑的地方。难点先说在前面：settings.py 只有一份，但它要在两个完全不同的环境里给出两套完全不同的配置。 就像同一个人，在家穿拖鞋、在工地戴安全帽——他没变，是环境变了，他自己能感觉到。

Django 的感觉器官就是环境变量。Platform.sh 运行你的应用时，会往环境变量里注入一大堆信息，其中最关键的一个叫 PLATFORM_APPLICATION——只要这个变量存在，就说明代码正跑在 Platform.sh 的云上。platformshconfig 这个库，本质就是把这一大堆环境变量（有的还是 base64 编码的 JSON）包装成几个好用的方法。

教材的做法是在 settings.py 的末尾追加一段（导入语句没放在文件开头，而是和「远程专属设置」放在一起，方便一眼看出哪些配置是云上才生效的）：

Python# settings.py —— 文件末尾追加的片段（完整文件以上方已有配置为基础）

# Platform.sh settings.
from platformshconfig import Config

config = Config()
if config.is_valid_platform():                    # ① 在云上才为 True（底层就是查 PLATFORM_APPLICATION）
    ALLOWED_HOSTS.append('.platformsh.site')     # ② 放行平台域名（见 2.7 第一个坑）
    DEBUG = False                                # ③ 云上必须关调试模式

    if config.appDir:                            # ④ 应用在云上的绝对路径
        STATIC_ROOT = Path(config.appDir) / 'static'
    if config.projectEntropy:                    # ⑤ 平台为项目生成的随机串，拿来当 SECRET_KEY
        SECRET_KEY = config.projectEntropy

    if not config.in_build():                    # ⑥ 构建阶段连不上数据库，只有运行期才配
        db_settings = config.credentials('database')   # ⑦ 读 relationships 里 database 的连接信息
        DATABASES = {
            'default': {
                'ENGINE': 'django.db.backends.postgresql',
                'NAME': db_settings['path'],
                'USER': db_settings['username'],
                'PASSWORD': db_settings['password'],
                'HOST': db_settings['host'],
                'PORT': db_settings['port'],
            },
        }

★ 为什么难：你要同时记住「两份配置」和「一个开关」。建议这样建心智模型——把 if config.is_valid_platform(): 想象成一道旋转门：代码走到这儿，本地身份的人直接走旁边的小门（沿用上面写的 SQLite 配置），云上身份的人转进门里，换上 PostgreSQL 的行头。门后面每一行，都是「仅云上生效」的覆写。

顺带回答一个可能的疑问：密钥怎么办？ SECRET_KEY 写进代码、传上公开仓库，别人理论上能拿着它伪造会话 cookie。Platform.sh 的答案是 projectEntropy——平台给每个项目生成一个足够随机的字符串，通过环境变量提供，代码里根本不出现密钥本身。这就是「配置与代码分离」在部署层的落地。

Config 看起来很神奇，其实它只是把一堆环境变量包装成方法。用 30 行替身就能把「本地 / 云上运行期 / 云上构建期」三种状态都跑一遍：

Python# platformshconfig 的替身：它只是把环境变量包装成好用的方法
import json


class FakeConfig:
    """真的 Config 读的是环境变量与 base64 的 PLATFORM_RELATIONSHIPS。"""

    def __init__(self, env):
        self.env = env

    def is_valid_platform(self):
        return "PLATFORM_APPLICATION" in self.env     # ★ 唯一的判据

    @property
    def appDir(self):
        return self.env.get("PLATFORM_APP_DIR")

    @property
    def projectEntropy(self):
        return self.env.get("PLATFORM_PROJECT_ENTROPY")

    def in_build(self):
        return self.env.get("PLATFORM_PHASE") == "build"

    def credentials(self, name):
        raw = self.env.get("PLATFORM_RELATIONSHIPS", "{}")
        return json.loads(raw).get(name)


def build_settings(env):
    """这就是 settings.py 末尾那段：本地走小门，云上换行头。"""
    settings = {"DEBUG": True, "ENGINE": "sqlite3", "ALLOWED_HOSTS": ["localhost"],
                "SECRET_KEY": "写死的开发密钥", "STATIC_ROOT": None}
    config = FakeConfig(env)
    if config.is_valid_platform():
        settings["DEBUG"] = False
        settings["ALLOWED_HOSTS"].append(".platformsh.site")
        settings["SECRET_KEY"] = config.projectEntropy
        settings["STATIC_ROOT"] = f"{config.appDir}/static"
        if not config.in_build():
            db = config.credentials("database")
            settings["ENGINE"] = f"postgresql://{db['username']}@{db['host']}"
        else:
            settings["ENGINE"] = "（构建阶段不连数据库）"
    return settings


CLOUD_ENV = {
    "PLATFORM_APPLICATION": "eyJ...", "PLATFORM_APP_DIR": "/app",
    "PLATFORM_PROJECT_ENTROPY": "a1b2c3d4", "PLATFORM_PHASE": "runtime",
    "PLATFORM_RELATIONSHIPS": json.dumps(
        {"database": {"username": "main", "host": "postgresql.internal"}}),
}

for label, env in [("本地（没有 PLATFORM_APPLICATION）", {}),
                   ("云上运行期", CLOUD_ENV),
                   ("云上构建期", {**CLOUD_ENV, "PLATFORM_PHASE": "build"})]:
    print(f"--- {label} ---")
    for key, value in build_settings(env).items():
        print(f"  {key:<14}= {value}")

三段输出最关键的区别在 ENGINE：本地是 sqlite3、云上运行期是 postgresql://main@postgresql.internal、云上构建期是「（构建阶段不连数据库）」。最后一段正对应教材那句 if not config.in_build():——collectstatic 和 migrate 跑在构建阶段，那时数据库容器还没起来，此刻去读 credentials() 只会拿到空值。
