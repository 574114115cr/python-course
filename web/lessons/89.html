2.4 GitHub search API：请求头与速率限制 ★

教材 17.1 的实操目标是「概述最受欢迎的仓库」，用的接口是 GitHub search API。这个网址要用问号把「接口地址」和「参数」分开读：

示例https://api.github.com/search/repositories   ← 接口路径：搜索仓库
?q=language:python                           ← q（query）：用 Python 写的仓库
&sort=stars                                  ← sort：按 star 数排序（最热在前）
&per_page=10                                 ← 每页 10 条（可选，默认 30）

请求头（headers）是 API 的另一半。 教材这一步要求带上 headers = {"Accept": "application/vnd.github+json"}。头干什么用？类比点菜时的备注栏：「我要微辣、多加葱」——不改你要的菜，而是告诉厨房要什么格式。

有了字典，接下来就是提取成几个平行的列表（Plotly 画图要的就是平行列表，单元 16 画地震图时你已经用过这套路）：repo_names 装 name 当柱子标签、stars 装 stargazers_count 当柱子高度、repo_urls 装 html_url 做可点击链接、descriptions 装 description、owners 装 owner.login 上色。完整循环见示例 2。

★ 提取时的三个坑：① items 和 total_count 不是一回事——后者是「符合条件的有几百万个」，前者才是这一次实际返回给你的（默认 30 条，可加 &per_page=100）；② description 可能是 None，写 repo["description"] or "（没写简介）"；③ 用 .get() 防缺字段——.get("forks_count", 0) 拿不到就返回默认值，但 response_dict["items"] 这种「核心结构」就该用 []，缺了说明 API 变了。

速率限制。 任何正经 API 都有速率限制——服务器资源有限，人人每秒请求 1000 次网站就垮了。GitHub 的规矩：未认证每小时 60 次，登录后（带 token）5000 次。超限返回 403 Forbidden，同时响应头 X-RateLimit-Remaining 告诉你还剩几次、X-RateLimit-Limit 告诉你总配额。完整守门员代码见示例 3。

★ 新手最容易忽略的一点：配额按「一小时窗口」算，不是「每 60 次后立刻重置」。 刚发出 3 次请求后 X-RateLimit-Remaining 应该显示 57 而不是 60。要连续取几十条数据时主动 time.sleep(1) 放慢速度。

四条必须养成的工程习惯（教材 17.1 反复强调的）：请求包 try/except（否则断网就崩）、检查 status_code（否则把 403 的错误 JSON 当数据用）、失败请求打印出来（否则数据悄悄少一半你却以为完整）、注意限速主动 sleep（否则被拒甚至被封禁）。

还有一个特别值得学的做法：把拿到的数据存下来（教材存成 github_repos.json，见示例 3）。API 数据随时会变，调图时反复请求既慢又烧配额；有了缓存，画图代码就完全不依赖网络。

2.5 Plotly 可视化仓库：悬停提示与颜色

数据齐了，进入 17.2。上一单元你用过 px.scatter_geo，这里换 px.bar——横向柱子，标签文字长也不怕挤在一起。三个最常用定制参数：hover_name（悬停时加粗显示的主标题，这里是仓库名）、hover_data（额外的悬停信息）、color + color_discrete_map（让某个字段的不同取值分到不同颜色，并用「取值 → 颜色」的字典固定配色，保证每次生成的图风格一致）。用 owner 分组上色，一眼就能看出哪几个仓库是同一个作者的。

★ 补充说明（教材未涉及，plotly 7.x 的变化）：hover_data 和 custom_data 传列名字符串时必须有 DataFrame 兜底，否则报 ValueError: String or int arguments are only possible when a DataFrame ... is provided。所以先把平行列表装进 pd.DataFrame({...})（键是列名），再 px.bar(df, x="name", ...)。样式参数见示例 4 的注释。
