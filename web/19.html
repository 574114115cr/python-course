一、学习目标

完成本单元后，你应该能够：

  1. 用 forms.ModelForm 把模型变成表单，并用 fields 白名单控制哪些字段暴露给用户，解释为什么 owner 绝对不能进白名单。
  2. 掌握 form.is_valid() → form.save(commit=False) → 补 owner → save() 的三段式，说清 commit=False 为什么存在。
  3. 用 Django 自带的 django.contrib.auth 视图实现登录和注销，并用 UserCreationForm 自己写出注册页面。
  4. 用 @login_required 保护视图，用 Topic.objects.filter(owner=request.user) 隔离数据，并说清 edit_entry 为什么要做双重保护。
  5. 解释「数据隔离」为什么是 Web 开发的安全红线，以及泄露一条用户数据的后果。

二、核心知识点讲解

2.1 表单与 ModelForm：把模型变成表单的捷径

到本章为止，只有超级用户能通过管理网站输数据。普通用户当然不能跟 /admin/ 打交道，解决办法是表单：网页上的输入框 + 提交按钮。

生活化类比：手写表单 = 自己印表格、自己收表格、自己逐张核对、自己归档，累且容易漏；ModelForm = 表格模板机——把 models.py 里定义好的模型塞进去，「哗啦」一声吐出一张能填、能自动核对、能直接归档的表单。Django 连验证都包了：必填项没填、字数超限、类型不对，统统自动拦截。

Python# learning_logs/forms.py —— 根据模型 Topic 自动生成表单
from django import forms

from .models import Topic


class TopicForm(forms.ModelForm):
    class Meta:
        model = Topic                  # 根据哪个模型生成
        fields = ["text"]              # 白名单：只暴露 text 这一个字段
        labels = {"text": ""}          # 不生成字段标签

fields 白名单是安全措施，不是省事措施。 它精确规定「用户能碰哪些列」。假如把 owner（数据归属）写进白名单，用户提交表单时就能偷偷塞一个 owner=别人——这条数据就归别人了，而你根本不知道。类比：驿站只收你填的单子，「寄件人」那一戳由系统盖章，绝不让你自己填。

labels = {"text": ""} 让字段不显示标签；widgets 可以换控件，比如 EntryForm 里把单行输入框换成 80 列的多行文本域，方便写长条目。

2.2 三段式与数据归属：commit=False 的经典手法 ★

添加新主题的视图，核心是这段被无数 Django 项目复制的「三段式」：

Python# learning_logs/views.py（片段）—— new_topic() 处理 POST 请求的部分
if request.method != "POST":
    # 未提交数据：创建一个新表单
    form = TopicForm()
else:
    # POST 提交的数据：对数据进行处理
    form = TopicForm(data=request.POST)
    if form.is_valid():
        new_topic = form.save(commit=False)   # 第一段：验证通过，但先别存
        new_topic.owner = request.user        # 第二段：补上「归属」，系统信息
        new_topic.save()                      # 第三段：数据齐了，真正存入数据库
        return redirect("learning_logs:topics")

逐段拆解：

段 代码 在干什么
一 form.is_valid() 让 Django 核对用户输入：必填项填了没、类型对没、有没有超长
二 form.save(commit=False) 验证通过了，但先不落库——创建一个「还没保存」的实例交到你手里
三 new_topic.owner = request.user 再 new_topic.save() 补上只有系统才知道的信息（当前用户是谁），然后真正保存

为什么需要 commit=False？ 用户填的表单里没有「这条主题归谁」——那是系统根据当前登录用户判断的。Django 特意留了这个口子：保存前的最后一刻，让你把系统信息补上。类比：快递单上「寄件人」必须由驿站盖章，不能由寄件人自己填。

忘了第三段的 save() 是最阴险的 bug：数据没进数据库，但页面照常跳转，用户以为成功了——静默丢数据。

2.3 request.user：每个请求自带的「当前用户」

Django 给每一个请求都挂上一个 user 对象，视图里直接用 request.user：已登录时是真实的 User 对象（带 username、id）；未登录时是 AnonymousUser——注意不是 None，所以视图里放心写 request.user，不会 AttributeError，只是 is_authenticated 为 False。

模板里同样有一个现成的 user 变量可用（不用在 context 里传）：

HTML{% if user.is_authenticated %}
  Hello, {{ user.username }}.
{% else %}
  <a href="{% url 'accounts:login' %}">Log in</a>
{% endif %}

这就是导航栏「已登录显示问候语、未登录显示登录链接」的实现——同一个变量，两种身份，模板自己判断。

「不是 None」这一点值得亲手验证一次，因为它决定了你后面所有视图函数的写法：

Python# request.user 的替身：登录与未登录，差别只在 is_authenticated
class AnonymousUser:
    """Django 里未登录时 request.user 就是这个对象——不是 None。"""

    username = ""
    pk = None

    def __str__(self):
        return "AnonymousUser"

    @property
    def is_authenticated(self):
        return False


class User:
    def __init__(self, username, pk):
        self.username = username
        self.pk = pk

    def __str__(self):
        return self.username

    @property
    def is_authenticated(self):
        return True


def nav_text(user):
    """视图或模板里唯一该用的判断：is_authenticated。"""
    if user.is_authenticated:
        return f"你好，{user.username}。"
    return "登录"


for user in (User("alice", 1), AnonymousUser()):
    print(f"{str(user):<14}is_authenticated={user.is_authenticated!s:<6}"
          f"pk={user.pk!r:<6}导航显示：{nav_text(user)}")

print("\n未登录时 username 是空串、pk 是 None，但对象永远存在——")
print("所以 request.user.username 不会 AttributeError，只是显示空字符串。")
print("视图里要拿「当前用户的主题」：Topic.objects.filter(owner=request.user)")
print("未登录还这么查，owner 会匹配到一个 AnonymousUser，结果恒为空集。")

实跑输出里 alice 那行是 is_authenticated=True pk=1，AnonymousUser 那行是 is_authenticated=False pk=None——pk 可以是 None，但 request.user 这个对象本身永远存在。所以判断登录状态永远写 if request.user.is_authenticated:，不要写 if request.user is not None:（那个条件永远为真）。

2.4 登录、注销、注册三件套

登录和注销不用自己写视图——Django 自带的用户身份验证系统（django.contrib.auth）全包了。在 accounts/urls.py 里包含默认 URL：

Python# accounts/urls.py —— 默认 URL 白拿 login / logout，register 用自己的视图
from django.urls import path, include

from . import views

app_name = "accounts"

urlpatterns = [
    # 包含默认的身份验证 URL
    path("", include("django.contrib.auth.urls")),
    # 注册页面（自己写）
    path("register/", views.register, name="register"),
]

但视图白送，模板要自己提供：默认登录视图只去 registration/login.html 找模板，位置放错就 TemplateDoesNotExist。注销请求必须以 POST 方式提交（防止攻击者伪造注销请求），所以在 base.html 里放一个只有提交按钮的小表单。

settings.py 末尾要交代三件事：

Python# ll_project/settings.py（末尾）
LOGIN_REDIRECT_URL = "learning_logs:index"   # 登录成功：去主页
LOGOUT_REDIRECT_URL = "learning_logs:index"  # 注销之后：回主页
LOGIN_URL = "accounts:login"                 # 被门禁拦下时：送到登录页

注册页面 Django 不提供，得自己写——但表单可以用现成的 UserCreationForm，它自带用户名合法性检查、两次密码一致性校验，保存时只存密码的哈希值（绝不存明文，教材专门强调过）。流程和 new_topic 一样：GET 显示空表单，POST 处理提交；验证通过后 form.save() 返回新用户对象，用 login(request, new_user) 让其自动登录，再重定向到主页。完整代码见示例 7。

2.5 @login_required：视图的门卫 ★

装饰器是放在函数定义前面的「@ 指令」，在函数运行前先跑一遍自己的代码。@login_required 的逻辑就一句：没登录？不许运行这个视图，重定向到登录页。

类比：小区门禁。没门禁卡的人到不了楼里，直接被请到物业登记（登录页）。settings.LOGIN_URL 就是告诉门禁「物业办公室在哪」——不配这一行，门禁不知道把人往哪送。

用起来极简单，但别漏：

Pythonfrom django.contrib.auth.decorators import login_required


@login_required
def topics(request):
    """显示所有主题。"""
    topics = Topic.objects.filter(owner=request.user).order_by("date_added")
    context = {"topics": topics}
    return render(request, "learning_logs/topics.html", context)

保护策略（教材的建议，值得抄走）：先列出哪些页面不需要保护——主页（谁都能看）、注册页（没账户的人才来）——然后限制对其他所有页面的访问。过于严格的限制顶多被用户抱怨，漏保护敏感页面则是事故。

2.6 数据隔离的安全红线 ★★★

本单元最重要的一句话：查询数据时，必须按当前用户过滤。写 Topic.objects.filter(owner=request.user).order_by("date_added")，而不是 Topic.objects.all()——后者不管是谁的，全都捞出来。

.all() 的后果：用户 A 登录后，能看到用户 B 的所有主题和条目。类比：酒店的房卡只能开自己的门——filter(owner=request.user) 是「按门牌号发钥匙」，.all() 是「把整栋楼的钥匙复印一份发给每个客人」。教材在讲超级用户权限时特意提醒：用户对访问的应用程序有极大的信任，优秀的管理员会小心对待用户的敏感信息——这不是风度问题，是职业道德和法律责任。

数据隔离要做三层，一层都不能少：

层 页面 手段
列表层 主题列表 filter(owner=request.user)，只捞自己的
详情层 单个主题 查到后比对 topic.owner != request.user，不等就 raise Http404
编辑层 编辑条目 通过 entry.topic.owner 往上追两层，不等就 raise Http404

为什么「查出来再在 Python 里筛」不行？那等于把全楼的钥匙读一遍再扔掉。filter(owner=...) 在数据库层面过滤，捞出来的就只有你该看的。

2.7 edit_entry 的双重保护

Entry 自己没有 owner 字段——它的归属是从 topic 继承的（教材的设计：只需把最高层数据关联到用户，低层数据自动跟着归属）。所以保护编辑页面时，要顺着「条目 → 主题 → 用户」追两层：

Python# learning_logs/views.py（片段）—— edit_entry() 的归属检查
entry = Entry.objects.get(id=entry_id)
topic = entry.topic
if topic.owner != request.user:
    raise Http404

类比：进房间前要验两道——先查这个房间号（entry）在哪一层（topic），再查这一层属于哪位住户（owner）。只验房间号不够：房间号对了，但那是别人家的楼层。

new_entry 同样要防（教材练习 19.4）：用户如果在 URL 里塞别人的 topic_id（比如 /new_entry/1/），就能往别人的主题里塞条目。保存前先问一句「这主题是你的吗」，不是就 404。

示例 1：用纯 Python 看懂「字段白名单」

Python# whitelist_simulation.py —— fields 白名单为什么是安全闸门

# 数据库里一条主题记录的真实长相
topic_data = {"id": 1, "text": "Python", "owner_id": 1, "date_added": "2026-10-15"}

# 表单声明的白名单：只允许用户填 text
FORM_FIELDS = ["text"]

# 恶意用户提交的表单数据：除了 text，还偷偷塞了 owner_id
submitted = {"text": "Django", "owner_id": 999}

# ===== 有白名单时：只取白名单内的字段，其余统统丢弃 =====
cleaned = {key: submitted[key] for key in FORM_FIELDS if key in submitted}
print("白名单清洗后的数据：", cleaned)
print("=> owner_id 被丢弃，用户无法把数据挂到别人名下")

# ===== 反面：把 owner_id 也加进白名单 =====
FORM_FIELDS_BAD = ["text", "owner_id"]
cleaned_bad = {key: submitted[key] for key in FORM_FIELDS_BAD if key in submitted}
print("\n白名单含 owner_id 时：", cleaned_bad)
print("=> 恶意提交的 owner_id=999 被接受，这条数据就归别人了！")

# 结论：fields = ['text'] 这行不是省事，是安全闸门
print("\nowner_id 从来不由用户填写，而由系统根据 request.user 盖章：")
topic_data.update(cleaned)
topic_data["owner_id"] = 1      # 系统盖章：当前登录用户的 ID
print("最终存入数据库的记录：", topic_data)

示例 2：用纯 Python 看懂 request.user

Python# current_user_simulation.py —— request.user 到底是什么


class User:
    """已登录的用户对象。"""

    def __init__(self, username, user_id):
        self.username = username
        self.id = user_id
        self.is_authenticated = True


class AnonymousUser:
    """未登录用户的替身：Django 不给 None，而是给一个匿名对象。"""

    username = ""
    is_authenticated = False


# 已登录的请求：request.user 是真实的 User 对象
logged_in_request = {"user": User("eric", 1)}

# 未登录的请求：request.user 是 AnonymousUser
anonymous_request = {"user": AnonymousUser()}

for label, request in [("已登录", logged_in_request), ("未登录", anonymous_request)]:
    user = request["user"]
    print(f"{label}: is_authenticated={user.is_authenticated}, "
          f"username={user.username!r}")

print("\n=> 视图里写 request.user 永远拿得到对象：")
print("   登录了是 User，没登录是 AnonymousUser，不会 AttributeError")
print("   所以 filter(owner=request.user) 对未登录用户是安全的——")
print("   查不到任何数据，而不是崩溃")

示例 3：用纯 Python 模拟 @login_required 门禁

Python# login_required_simulation.py —— 装饰器是怎么当上门禁的


def login_required(view_func):
    """模拟 Django 的 @login_required：没登录就不放行。"""

    def wrapper(request, *args, **kwargs):
        user = request.get("user")
        if user is None or not user.get("is_authenticated"):
            print("  门禁：未登录 -> 重定向到登录页（settings.LOGIN_URL）")
            return "重定向到 /accounts/login/"
        return view_func(request, *args, **kwargs)

    return wrapper


@login_required
def topics(request):
    """受保护的主题列表视图。"""
    return "主题列表页面（只含当前用户的主题）"


# 场景一：已登录用户
print("已登录用户访问：")
print(" ", topics({"user": {"is_authenticated": True, "username": "eric"}}))

# 场景二：未登录用户
print("\n未登录用户访问：")
print(" ", topics({"user": {"is_authenticated": False}}))

print("\n=> 装饰器不改变视图本身的代码，只是在门口加了一道检查：")
print("   忘写 @login_required，等于门禁没上岗，谁都能推门进去")

示例 4：用纯 Python 看懂数据隔离

Python# data_isolation_simulation.py —— .all() 和 .filter(owner=...) 的生死差别

# 内存「数据库」：三个主题，分属两个用户
DATABASE = [
    {"id": 1, "text": "Python", "owner": "eric"},
    {"id": 2, "text": "Django", "owner": "eric"},
    {"id": 3, "text": "私密日记", "owner": "willie"},
]


def all_topics():
    """错误示范：Topic.objects.all() —— 不管是谁的，全都捞出来。"""
    return list(DATABASE)


def filter_topics(owner):
    """正确写法：Topic.objects.filter(owner=request.user)。"""
    return [t for t in DATABASE if t["owner"] == owner]


print("=== 危险：用 .all() ===")
for t in all_topics():
    print(f"  {t['owner']} 的主题: {t['text']}")
print("  => eric 登录后看到了 willie 的「私密日记」——数据裸奔！")

print("\n=== 安全：filter(owner=request.user) ===")
for t in filter_topics("eric"):
    print(f"  {t['owner']} 的主题: {t['text']}")
print("  => eric 只看得到自己的两条")
for t in filter_topics("willie"):
    print(f"  {t['owner']} 的主题: {t['text']}")
print("  => willie 登录则只看得到自己的")

# 三层防护的另外两层：详情页和编辑页
print("\n=== 详情层/编辑层：查到之后再比对归属 ===")
topic = DATABASE[2]          # willie 的主题
current_user = "eric"
if topic["owner"] != current_user:
    print(f"  {current_user} 请求主题「{topic['text']}」-> raise Http404")
    print("  => 不是你的东西，当成不存在（连「存在但不给你看」都不透露）")

Python# learning_logs/forms.py —— 把模型变成表单（ModelForm）
from django import forms

from .models import Topic, Entry


class TopicForm(forms.ModelForm):
    class Meta:
        model = Topic
        fields = ["text"]                     # 白名单：只暴露 text
        labels = {"text": ""}                 # 不生成字段标签


class EntryForm(forms.ModelForm):
    class Meta:

Python# isolated_notebook.py —— 纯 Python 实现三道防线

# 内存「数据库」：{用户名: {主题ID: 主题文本}}
NOTEBOOK = {
    "eric": {1: "Python", 2: "Django"},
    "willie": {3: "私密日记"},
}

# 当前登录用户（None 表示未登录）
current_user = None

# 表单白名单：用户只能填 text，owner 一律由系统决定
FORM_FIELDS = ["text"]


def login(username):
    """登录：设置当前用户。"""
    global current_user
    if username not in NOTEBOOK:
        raise ValueError(f"用户 {username} 不存在")
    current_user = username


def logout():
    """注销。"""
    global current_user
    current_user = None


def check_login():
    """门禁：未登录就拒绝。"""
    if current_user is None:
        raise PermissionError("未登录，请先登录")


def submit_topic(submitted):
    """白名单表单：只接 text，归属由 current_user 决定。"""
    check_login()
    cleaned = {key: submitted[key] for key in FORM_FIELDS if key in submitted}
    # 用户塞的 owner 被丢弃；归属永远来自系统
    topic_id = max(
        tid for topics in NOTEBOOK.values() for tid in topics
    ) + 1
    NOTEBOOK[current_user][topic_id] = cleaned["text"]
    return topic_id


def list_topics():
    """数据隔离：只返回当前用户的主题。"""
    check_login()
    return dict(NOTEBOOK[current_user])       # 拷贝一份，防外部改动


def get_topic(topic_id):
    """详情层：查不到或不属于当前用户，一律 KeyError（相当于 404）。"""
    check_login()
    topics = NOTEBOOK[current_user]
    if topic_id not in topics:
        raise KeyError(f"主题 {topic_id} 不存在或不属于你")
    return topics[topic_id]


# ===== 演示：三道防线如何各自生效 =====
print("=== 防线一：白名单 ===")
login("eric")
malicious = {"text": "假装是别人的", "owner": "willie"}
new_id = submit_topic(malicious)
print(f"提交了 {malicious}")
print(f"实际存入：{{'text': {NOTEBOOK['eric'][new_id]!r}, 'owner': 'eric'}}")
print("=> 恶意塞的 owner=willie 被丢弃，归属由系统盖章")

print("\n=== 防线二：门禁 ===")
logout()
try:
    list_topics()
except PermissionError as error:
    print("未登录调用 list_topics() ->", error)

print("\n=== 防线三：数据隔离 ===")
login("eric")
print("eric 的主题：", list_topics())
try:
    get_topic(3)          # willie 的主题
except KeyError as error:
    print("eric 请求主题 3 ->", error)
login("willie")
print("willie 的主题：", list_topics())
print("willie 请求主题 3 ->", get_topic(3))

六、常见错误清单（务必逐条自查）

错误 1：★ 视图里用 .all()，忘了按用户过滤

症状：登录 A 账号，能看到 B 账号的全部主题和条目——数据裸奔，本单元最严重的事故。自查方法：搜索项目里所有 objects.all()，逐个问「这里该不该按 owner=request.user 过滤」。涉及用户私有数据的查询，一个都不能漏。

错误 2：★ fields 白名单里写了 owner

fields = ["text", "owner"] 等于把「归属」这一列的控制权交给用户——提交表单时塞个别人的用户 ID，数据就归了别人。归属信息只有一个合法来源：request.user，由系统在 save(commit=False) 之后盖章。表单白名单里永远不要出现 owner。

错误 3：忘了写 @login_required

未登录用户访问该视图时，request.user 是 AnonymousUser，filter(owner=AnonymousUser) 直接 500。装饰器就一行，漏写整个页面裸奔。建议：除了主页和注册页，其他视图全部加，加错了顶多严格一点，漏加了是事故。

错误 4：save(commit=False) 之后忘了 save()

new_topic = form.save(commit=False) 只是拿到一个没入库的实例；不补 owner、不调用 save()，数据就永远停在内存里。最阴险的是页面照常跳转、用户毫无察觉——静默丢数据。记住三段式是一个整体：commit=False → 补 owner → save()。

错误 5：登录模板放错位置

TemplateDoesNotExist at registration/login.html——默认登录视图只认 registration/login.html 这个路径，且要从某个 app 的 templates/ 目录下找。正确位置：accounts/templates/registration/login.html。差一个单词都不行，这是 Django 的约定，没有为什么，记住即可。

错误 6：edit_entry 只查了条目，没查主题归属

entry = Entry.objects.get(id=entry_id) 之后直接用，等于放任用户 A 通过 /edit_entry/别人的条目ID/ 编辑用户 B 的条目。Entry 自己没有 owner，归属要从 entry.topic.owner 往上追一层——这就是「双重保护」：既确认条目存在，也确认条目的主题属于当前用户。

七、本单元验收自测

1. 简答题：fields 白名单为什么不能包含 owner？用户提交恶意数据时会发生什么？

要点：fields 规定用户能填哪些列。如果包含 owner，用户提交表单时就能塞一个 owner=别人ID，这条数据就归属到别人名下，而所有者本人毫不知情——这是典型的越权。归属信息只有一个合法来源：request.user，由系统在 form.save(commit=False) 之后、save() 之前盖章。表单白名单里只放真正该由用户填写的字段（如 text）。

2. 简答题：三段式每一段在干什么？commit=False 为什么存在？

要点：form.is_valid() 让 Django 自动校验（必填、类型、长度）；form.save(commit=False) 创建实例但不落库，把最后修改的机会交给你；补上 new_topic.owner = request.user 这类只有系统知道的信息后，save() 才真正存入数据库。commit=False 的意义：用户填的表单里没有「归属谁」，而这是保存前最后一刻必须补上的系统信息。

3. 判断题：未登录用户访问带 @login_required 的视图，会看到 500 错误页。

要点：错误。未登录时 @login_required 会直接重定向到登录页（地址来自 settings.LOGIN_URL），根本不会运行视图代码，也就不会 500。如果忘了配 LOGIN_URL 或漏写装饰器，才可能看到难看的错误页。request.user 对未登录用户是 AnonymousUser（不是 None），所以视图里用 request.user 本身不会 AttributeError。

4. 简答题：为什么说数据隔离是「安全红线」？filter(owner=request.user) 和 .all() 的后果差别是什么？

要点：学习笔记存的是用户的私有数据，用户对应用有极大的信任。filter(owner=request.user) 在数据库层面只捞当前用户的主题——相当于按门牌号发钥匙；.all() 不管归属全捞——相当于把整栋楼的钥匙复印给每个客人，用户 A 能看到用户 B 的全部笔记，这是重大事故。隔离要做三层：列表页 filter、详情页查归属后 Http404、编辑页沿「条目 → 主题 → 用户」追两层。

5. 简答题：edit_entry 为什么要「双重保护」？new_entry 呢？

要点：Entry 没有自己的 owner 字段，归属从所属主题继承（只需把最高层数据关联用户）。所以编辑条目时，先取 entry.topic，再查 topic.owner != request.user——确认了条目所属的主题属于当前用户，才放行；否则 raise Http404。new_entry 同理：URL 里的 topic_id 可能指向别人的主题，保存前必须核实主题归属，否则用户能往别人的笔记里塞条目。永远不要相信 URL 里的 ID。

6. 改错题：下面的 register() 想实现「注册成功并自动登录」，有 2 处错误，找出来并改正。

故意写错 · 先跑一遍看报错def register(request):
    if request.method != "POST":
        form = UserCreationForm()
    else:
        form = UserCreationForm(data=request.POST)
        if form.is_valid():
            new_user = form.save()
            return redirect("learning_logs:index")
    context = {"form": form}
    return render("registration/register.html", context)
这是故意写错的示例——先自己跑一遍看报错，再对照下面的解析弄清错在哪

要点：错误一，注册成功后少了 login(request, new_user)——用户注册完还是未登录状态，刷新任何受保护页面都会被弹去登录页，体验断裂；正确做法是 form.save() 拿到新用户对象后，调用 login(request, new_user) 为其创建有效会话，实现自动登录。错误二，render() 少了第一个实参 request——应为 render(request, "registration/register.html", context)，Django 的 render() 签名是 render(request, template_name, context)，没有 request 会直接 TypeError。
