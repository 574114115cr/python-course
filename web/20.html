二、核心知识点讲解

2.1 django-bootstrap5：一行代码让表单变漂亮（对应教材 20.1）

先回忆「学习笔记」的登录页面现在长什么样：光秃秃的输入框、光秃秃的按钮，像 1998 年的网页。原因很简单——Django 只负责把表单渲染成合法的 HTML，好不好看它一概不管：{{ form.as_p }} 渲染出的控件上没有任何 CSS 类，浏览器就用默认样式显示。生活化类比：Django 是裁缝，只保证衣服合身；好不好看是造型师的事，django-bootstrap5 就是那位造型师。

第 3 版教材用的是 django-bootstrap5（注意：不是第 2 版的 django-bootstrap4，Bootstrap 4 到 5 是不小的升级，库名也跟着换了）。用法分三步，一步都不能少：

终端命令# 1. 安装（在虚拟环境里）
(ll_env)learning_log$ pip install django-bootstrap5

Python# 2. settings.py 的 INSTALLED_APPS 里注册（不注册，模板标签不生效）
INSTALLED_APPS = [
    'learning_logs',
    'accounts',
    'django_bootstrap5',      # ← 加这一行
    # ……（Django 自带的应用略）
]

HTML{% load django_bootstrap5 %}

<form action="{% url 'login' %}" method="post">
    {% csrf_token %}
    {% bootstrap_form form %}
    <button name="submit" class="btn btn-primary">登录</button>
</form>

两行模板标签的分工一定要分清：

  • {% load django_bootstrap5 %}：把工具包拿到这个模板里。不 load 就用 bootstrap_form，Django 会报 Invalid block tag——就像工具落在家里，活儿没法干。它只负责加载，不改变任何输出。
  • {% bootstrap_form form %}：一键美颜。它内部遍历表单的每个字段，给它们包上 Bootstrap 需要的 div 和 form-control 等类名。输出的还是同一个表单，但浏览器一渲染就有了圆角、间距、聚焦高亮。

★ 这里对新手最难的是：模板标签不是 Python 函数。你没法在 {% bootstrap_form %} 里写 if、传变量、或者 print 它看看结构。Django 模板语言是故意设计得「不会写代码」的，复杂逻辑必须提到视图函数里做好、用上下文传进来。想搞清楚它到底输出了什么，老办法：浏览器里右键「查看网页源代码」。

2.2 改造「学习笔记」的界面（对应教材 20.1 各小节）

讲 Django 项目，每动一个文件都要先说清：这个文件是干什么的、改了它会影响什么。这是新手在框架里最大的迷茫——「我不知道我改的东西在哪生效」。

先建静态文件目录。静态文件指 CSS、JavaScript、图片这类「不需要服务器计算、原样发给浏览器」的文件：

示例learning_log/                  ← 项目根目录（manage.py 所在处）
├── ll_project/                ← 项目配置包（settings.py、urls.py 在这）
├── learning_logs/             ← 应用：主题和条目
│   ├── templates/learning_logs/   ← 这个应用专用模板
│   ├── static/css/styles.css      ← ★ 新建：我们自己写的样式
│   └── views.py
├── accounts/                  ← 应用：用户账户
├── templates/                 ← 项目级模板（404/500 放这，2.8 节用）
├── manage.py
└── db.sqlite3                 ← 本地开发数据库（不能传上云！）

各文件的职责和影响范围：

文件 干什么用 改了它影响什么
static/css/styles.css 补 Bootstrap 没有的样式（如 .jumbotron） 引入了这个 CSS 的页面（base.html 引了就全站）
templates/learning_logs/base.html 全站骨架：导航条 + 内容占位区 所有页面，改坏了全站 500
templates/registration/login.html 登录页 只有登录页
templates/learning_logs/index.html 主页 只有主页
templates/learning_logs/topics.html 主题列表页 只有该页

base.html 是「继承树」的根：其他模板都 {% extends %} 它，所以 Bootstrap 的 CSS 链接写在 base.html 里，一次引入全站生效。导航条部分长这样：

HTML<nav class="navbar navbar-expand-md bg-body-tertiary mb-4 border">
  <div class="container-fluid">
    <a class="navbar-brand" href="{% url 'learning_logs:index' %}">学习笔记</a>
    <ul class="navbar-nav me-auto">
      <li class="nav-item"><a class="nav-link" href="{% url 'learning_logs:topics' %}">主题</a></li>
    </ul>
    <ul class="navbar-nav ms-auto">
      {% if user.is_authenticated %}
        <li class="nav-item"><span class="navbar-text">你好，{{ user.username }}。</span></li>
        <li class="nav-item">
          <form action="{% url 'logout' %}" method="post">
            {% csrf_token %}
            <button class="btn nav-link" type="submit">退出</button>
          </form>
        </li>
      {% else %}
        <li class="nav-item"><a class="nav-link" href="{% url 'login' %}">登录</a></li>
      {% endif %}
    </ul>
  </div>
</nav>

<main class="container">
  {% block page_header %}{% endblock page_header %}
  {% block content %}{% endblock content %}
</main>

注意 {% if user.is_authenticated %}：登录和未登录的人看到不同导航，这个判断用的是 Django 自动塞进每个模板的 user 对象，视图里什么都不用做。

jumbotron：教材给主页用了一个居中的大卡片当「门面」。这里有个版本细节——jumbotron 是 Bootstrap 4 时代的组件名，Bootstrap 5 已经把它删掉了（补充说明，教材未涉及），所以第 3 版的做法是在 static/css/styles.css 里自己写一个 .jumbotron 类，把当年的效果补回来：

css.jumbotron {
    padding: 2rem 1rem;
    margin-bottom: 2rem;
    background-color: #e9ecef;
    border-radius: 0.3rem;
}

登录页的表单用 {% bootstrap_form form %} 美颜，主题列表页用 Bootstrap 列表组（list-group）逐行列出主题。这些改动的共同点是：只动模板和 CSS，不动任何 Python 代码——这就是「样式」和「逻辑」分离的好处。

「改了它会影响什么」这张表，底层数据结构其实就是一条 {% extends %} 链。把模板当字符串读一遍，就能自动算出影响范围：

Python# 模板继承链：谁 extends 谁，渲染时从最外层往里套
import re

TEMPLATES = {
    "learning_logs/base.html":
        "<nav>导航条</nav>{% block content %}{% endblock content %}",
    "learning_logs/topics.html":
        '{% extends "learning_logs/base.html" %}{% block content %}<h2>主题</h2>{% endblock %}',
    "registration/login.html":
        '{% extends "learning_logs/base.html" %}{% block content %}<form>…</form>{% endblock %}',
}


def chain(name, depth=0):
    """顺着 extends 往上找，返回 [(模板名, 缩进层级)]。"""
    body = TEMPLATES[name]
    found = re.search(r'{%\s*extends\s+"([^"]+)"\s*%}', body)
    me = [(name, depth)]
    return me + (chain(found.group(1), depth + 1) if found else [])


for page in ("learning_logs/topics.html", "registration/login.html"):
    print(f"{page} 的继承链：")
    for name, depth in chain(page):
        print("  " + "    " * depth + ("└─ " if depth else "") + name)

print("\n改 base.html 的导航条 = 改全站；改 topics.html 只影响一个页面。")
print("这就是 unit 20 里「改了它影响什么」那张表能一眼看懂的底层原因。")

跑出来两条链都指向同一个根 learning_logs/base.html——它被全站每个页面 extends，所以它坏了就是全站 500；而 topics.html 只出现在自己的链里。凡是「有几个模板 extends 我」这个数大的文件，改动前都该多跑一次测试。

2.3 部署是什么：从「只有你能跑」到「谁都能访问」（对应教材 20.2）

到目前为止，「学习笔记」只活在你这台电脑上。部署（deploy）就是把它搬到一个 7×24 小时开机的云服务器上，让任何人输入网址都能访问。

先建立本地与云环境的差异感，这张表是后面所有操作的「为什么」：

事项 本地开发 Platform.sh 云环境
数据库 SQLite（一个文件） PostgreSQL（独立数据库容器）
Web 服务器 manage.py runserver（仅供开发调试） gunicorn（生产级 WSGI 服务器）
静态文件 直接读 static/ 目录 构建时 collectstatic 汇总到 STATIC_ROOT
DEBUG True（报错显示详细信息） 必须 False（否则泄露配置、拖慢速度）
依赖来源 你手动 pip install 的现成环境 一台干干净净的新机器，全靠 requirements.txt 重建
ALLOWED_HOSTS localhost 就行 必须写上平台的域名，否则一律 400

生活化类比：本地开发像在自家厨房练手，油盐酱醋随手就有；部署像去美食广场开店，一切都是陌生的、干净的，你必须带一张采购清单（requirements.txt），否则连盐都买不到。

Platform.sh 是一个「平台即服务」（PaaS）：你不用自己买服务器、装系统，把代码推给它，它负责在容器里构建、运行。上手三步：浏览器访问 https://platform.sh 注册账户；安装 Platform.sh CLI（curl -fsS https://platform.sh/cli/installer | php，需要 PHP 环境，Windows 上跑不动时可用 Git Bash 或 WSL——补充说明，教材未涉及）；pip install platformshconfig 让 Django 在云上读取平台配置。装完 CLI 先 platform --version 验证。

2.4 requirements.txt：云环境的采购清单（对应教材 20.2）

为什么它是部署必需品？因为云环境是一台全新的、干净的机器，它不知道你的项目用过 Django，更不会知道你要 4.2 版还是 5.0 版。你要把所有依赖和精确版本写在清单里，平台构建时照着装：

终端命令# freeze = 冻结当前环境的所有包及版本
(ll_env)learning_log$ pip freeze > requirements.txt

生成的内容大致这样（具体以你机器上的实际输出为准）：

示例asgiref==3.7.2
Django==4.2.10
django-bootstrap5==23.4
platformshconfig==2.4.0
sqlparse==0.4.4

两个细节：

  1. == 是版本锁。写 Django==4.2.10，云上装的就是 4.2.10，一分不差。没有 == 意味着「最新版就行」，半年后平台装到一个大版本更新，项目可能直接崩。锁版本不是洁癖，是纪律。
  2. 清单里也会有间接依赖（如 asgiref、sqlparse 是 Django 带进来的）。这正是 pip freeze 的价值：它冻结的是整棵依赖树，换一台机器能原样重建。

pip freeze 的输出不能照抄，先规范化一遍再提交——大小写、多余空格、-e 可编辑安装都是坑：

Python# pip freeze 的原始输出要先规范化，再比对
RAW = """Django==4.2.10
  django-bootstrap5==23.4
asgiref==3.7.2
# 下面这行是本地可编辑安装，推上云会直接失败
-e git+https://github.com/me/django-bootstrap5#egg=django-bootstrap5
sqlparse==0.4.4
Django==4.2.10
"""


def normalize(text):
    """返回 ({包名小写: 版本}, [被剔除的行])。"""
    packages, dropped = {}, []
    for line in text.splitlines():
        line = line.strip()
        if not line or line.startswith("#"):
            continue
        if line.startswith("-e ") or line.startswith("--"):
            dropped.append(line)
            continue
        if "==" not in line:
            dropped.append(line + "（没锁版本）")
            continue
        name, version = line.split("==", 1)
        packages[name.strip().lower()] = version.strip()
    return packages, dropped


packages, dropped = normalize(RAW)
print("规范化后的依赖（小写键，重复的自动合并）：")
for name, version in sorted(packages.items()):
    print(f"  {name:<20}{version}")
print("\n被剔除的行：")
for line in dropped:
    print("  ", line)
print(f"\n共 {len(packages)} 个依赖；requirements.txt 只该有这些内容。")

-e git+https://... 这类行必须删掉：它表示「从 git 直接装」，而云上构建环境既没有你的私有仓库凭据、也不该联网拉你的 fork。这段的实跑结果是 4 个依赖（Django==4.2.10 出现两次被合并成一条），剔除 1 行 -e ...。

还有一类依赖只该在线上装：gunicorn 和 psycopg2。gunicorn 是生产级 WSGI 服务器（本地用 runserver，线上必须换它）；psycopg2 是 PostgreSQL 的驱动，本地用 SQLite 根本不需要。教材的做法是同目录再建一个 requirements_remote.txt：

示例# Requirements for live project.
gunicorn
psycopg2

这两个文件都会在 .platform.app.yaml 的 build 钩子里被 pip install -r，下一节就能看到。

2.5 三个配置文件：一个描述应用，一个描述路由（对应教材 20.2）

这是本单元最需要建立宏观认识的部分。部署时你要告诉平台三件事：跑什么、怎么跑、从哪进。对应三个文件：

示例learning_log/
├── .platform.app.yaml      ← ① 应用清单：用什么运行、依赖什么、构建/部署时执行什么
├── manage.py
└── .platform/              ← 注意：这是个以点开头的隐藏文件夹
    ├── routes.yaml         ← ② 路由：域名怎么指过来
    └── services.yaml       ← ③ 服务：数据库容器怎么开

一次完整的请求这样流转：

示例浏览器访问 https://learning-log-main-xxxx.us-3.platformsh.site/
        │
        ▼
① .platform/routes.yaml ：「这个域名该转给谁？」
        │   "https://{default}/" → upstream: "ll_project:http"
        ▼
② .platform.app.yaml ：「应用怎么启动？」
        │   start: gunicorn ... ll_project.wsgi:application
        ▼
   gunicorn（WSGI 服务器）───► Django（ll_project/wsgi.py）
                          settings.py（platformshconfig 在运行时改写它）
                                    │
                                    ▼
                        ③ PostgreSQL（services.yaml 里定义的 db 容器）

.platform.app.yaml（和 manage.py 同级，注意别漏开头的点）：

YAMLname: "ll_project"                 # 应用名，routes.yaml 要靠它对上暗号
type: "python:3.12"                # 用什么语言、什么版本（教材写 3.10，以平台文档为准）

relationships:                     # 应用依赖哪些外部服务
    database: "db:postgresql"      # 叫 database 的关系 → 指向 services.yaml 里的 db

web:                               # 暴露到 Web 的配置
    upstream:
        socket_family: unix
    commands:
        start: "gunicorn -w 4 -b unix:$SOCKET ll_project.wsgi:application"   # 启动命令
    locations:
        "/":
            passthru: true         # 动态请求交给 gunicorn/Django
        "/static":
            root: "static"         # 静态文件直接由 Web 服务器发，不麻烦 Django

hooks:                             # 生命周期钩子：构建时和部署时各执行一批命令
    build: |
        pip install --upgrade pip
        pip install -r requirements.txt        # 本地依赖清单
        pip install -r requirements_remote.txt # 线上专用依赖清单
        python manage.py collectstatic --noinput   # ★ 收集静态文件（2.7 节细说）
    deploy: |
        python manage.py migrate               # 每次部署自动应用数据库迁移

.platform/routes.yaml：路由只干一件事——把域名指到应用。

YAML"https://{default}/":
    type: upstream
    upstream: "ll_project:http"    # ← 这个名字必须和 app.yaml 的 name 一致

"https://www.{default}/":
    type: redirect
    to: "https://{default}/"       # 带 www 的访问跳到主域名

.platform/services.yaml：服务清单，每个服务以独立容器部署。

YAMLdb:
    type: postgresql:16            # 开一个 PostgreSQL 容器（版本以平台文档为准）
    disk: 1024

app.yaml 的 relationships 说「我需要一个叫 database 的数据库」，services.yaml 说「我开一个叫 db 的 PostgreSQL」，两边用 "db:postgresql" 这个暗号对上；routes.yaml 的 upstream: "ll_project:http" 则要和 app.yaml 的 name 一致。两处暗号对不上，部署直接失败。

「对暗号」这件事不需要平台也能查——三个 yaml 都是文本，正则一比就知道：

Python# 三个 yaml 的「暗号」对不对得上，用字符串就能查
import re

APP = 'name: "ll_project"\nrelationships:\n    database: "db:postgresql"\n'
ROUTES = '"https://{default}/":\n    upstream: "ll_project:http"\n'
SERVICES = "db:\n    type: postgresql:16\n"


def audit(app_yaml, routes_yaml, services_yaml):
    """三处暗号：应用名 ↔ upstream、关系名 ↔ 服务名、关系类型 ↔ 服务类型。"""
    app_name = re.search(r'name:\s*"([^"]+)"', app_yaml)
    upstream = re.search(r'upstream:\s*"([^":]+)', routes_yaml)
    relation = re.search(r'database:\s*"([^":]+):([^"]+)"', app_yaml)
    service = re.search(r"^(\w+):", services_yaml, re.M)
    kind = re.search(r"type:\s*(\w+)", services_yaml)
    return [
        ("应用名 ↔ routes.upstream",
         app_name.group(1) == upstream.group(1),
         f"{app_name.group(1)} / {upstream.group(1)}"),
        ("关系名 ↔ services 服务名",
         relation.group(1) == service.group(1),
         f"{relation.group(1)} / {service.group(1)}"),
        ("关系类型 ↔ services 服务类型",
         relation.group(2) == kind.group(1),
         f"{relation.group(2)} / {kind.group(1)}"),
    ]


for label, ok, detail in audit(APP, ROUTES, SERVICES):
    print(f"[{'✓' if ok else '✗'}] {label}：{detail}")

print("\n改坏一处试试（把 routes 的 upstream 改成 app）：")

2.6 platformshconfig：一份代码怎么知道自己在哪（对应教材 20.2）

现在到本单元最烧脑的地方。难点先说在前面：settings.py 只有一份，但它要在两个完全不同的环境里给出两套完全不同的配置。 就像同一个人，在家穿拖鞋、在工地戴安全帽——他没变，是环境变了，他自己能感觉到。

Django 的感觉器官就是环境变量。Platform.sh 运行你的应用时，会往环境变量里注入一大堆信息，其中最关键的一个叫 PLATFORM_APPLICATION——只要这个变量存在，就说明代码正跑在 Platform.sh 的云上。platformshconfig 这个库，本质就是把这一大堆环境变量（有的还是 base64 编码的 JSON）包装成几个好用的方法。

教材的做法是在 settings.py 的末尾追加一段（导入语句没放在文件开头，而是和「远程专属设置」放在一起，方便一眼看出哪些配置是云上才生效的）：

顺带回答一个可能的疑问：密钥怎么办？ SECRET_KEY 写进代码、传上公开仓库，别人理论上能拿着它伪造会话 cookie。Platform.sh 的答案是 projectEntropy——平台给每个项目生成一个足够随机的字符串，通过环境变量提供，代码里根本不出现密钥本身。这就是「配置与代码分离」在部署层的落地。

2.7 三大部署坑：ALLOWED_HOSTS、collectstatic、DEBUG（对应教材 20.2）

坑一：ALLOWED_HOSTS 不改，线上直接 400。 Django 会检查每个请求的 Host 头在不在 ALLOWED_HOSTS 名单里，不在就返回 400 Bad Request——连你的视图代码都不会执行。默认的 ALLOWED_HOSTS = [] 只放行 localhost，线上域名 100% 被拒。修复就是 2.6 里那行 ALLOWED_HOSTS.append('.platformsh.site')（开头带点表示「匹配所有子域名」，你的项目域名类似 xxx.us-3.platformsh.site）。

坑二：DEBUG = False 之后，不 collectstatic 就是一个白脸页面。 DEBUG = True 时开发服务器会顺带帮你发静态文件；一旦关掉，静态文件必须由真正的 Web 服务器发。所以 app.yaml 的 build 钩子里有 python manage.py collectstatic --noinput：它把各个应用的 static/ 目录全部汇总到 STATIC_ROOT，再由 routes 里 /static 那条规则直接发文件。忘了这一步，HTML 能出来但 CSS/JS 全丢，页面就是个没化妆的素颜。

「谁在发这个 CSS」决定了页面有没有样式，把四种组合列出来就一目了然：

def is_host_allowed(host, allowed_hosts):
    """Django 校验 Host 的核心规则（教学简化版）。"""
    if "*" in allowed_hosts:
        return True
    host = host.split(":")[0]          # 去掉端口号：localhost:8000 → localhost

        if pattern == host:
            return True
        if pattern.startswith(".") and host.endswith(pattern):

    return False

from pathlib import Path
import shutil


def collect_static(app_names, project_root, static_root):
    """模拟 python manage.py collectstatic：
    把每个应用的 static/ 目录，原样汇总到 STATIC_ROOT。
    """
    if static_root.exists():
        shutil.rmtree(static_root)
    static_root.mkdir(parents=True)
    copied = []
    for app_name in app_names:
        source = project_root / app_name / "static"
        if not source.exists():
            continue
        for file in sorted(source.rglob("*")):

def read(path):
    try:
        return path.read_text(encoding="utf-8")
    except OSError:
        return ""


def unpinned(text):
    return [ln.strip() for ln in text.splitlines()
            if ln.strip() and not ln.startswith("#") and "==" not in ln]


def checks(root=ROOT, env=None):
    """八道闸门，每项返回 (是否通过, 说明)。顺序就是踩坑频率的顺序。"""
    env = os.environ if env is None else env
    app_yaml = read(root / ".platform.app.yaml")
    routes = read(root / ".platform/routes.yaml")
    services = read(root / ".platform/services.yaml")
    settings = read(root / "ll_project/settings.py")
    gitignore = read(root / ".gitignore")
    app_name = re.search(r'name:\s*"([^"]+)"', app_yaml)
    upstream = re.search(r'upstream:\s*"([^":]+)', routes)
    return [
        ("依赖清单锁版本", not unpinned(read(root / "requirements.txt"))
         and (root / "requirements.txt").exists()),
        ("线上依赖齐全", all(pkg in read(root / "requirements_remote.txt")
                            for pkg in ("gunicorn", "psycopg2"))),
        ("路由暗号对齐", bool(app_name and upstream)
         and app_name.group(1) == upstream.group(1)),
        ("数据库服务存在", "postgresql" in services and "db:" in services),
        ("忽略清单到位", "*.sqlite3" in gitignore and "ll_env/" in gitignore),
        ("云上放行域名且关调试", ".platformsh.site" in settings and "DEBUG = False" in settings),
        ("错误页成对", (root / "templates/404.html").exists()
         and (root / "templates/500.html").exists()),
        ("静态文件已收集", "collectstatic" in app_yaml),
    ]


def static_inventory(root=ROOT):
    """pathlib 遍历：collectstatic 到底会把哪些文件搬到 STATIC_ROOT。"""
    found = []
    for app_dir in sorted(root.iterdir()):
        static = app_dir / "static"
        if static.is_dir():
            for file in sorted(static.rglob("*")):
                if file.is_file():
                    found.append(str(file.relative_to(root)).replace("\\", "/"))
    return found


def allowed_hosts_from_env(env):
    """ALLOWED_HOSTS 不该写死：线上域名从环境变量来，本地给默认值。"""
    raw = env.get("DJANGO_ALLOWED_HOSTS", "localhost,127.0.0.1")
    return [host.strip() for host in raw.split(",") if host.strip()]

Python# env_switch.py —— 不装 platformshconfig，纯 os.environ 模拟双环境配置
import os

def build_settings():
    """模拟 settings.py：同一份逻辑，两套配置。

    platformshconfig 的 is_valid_platform() 底层就是在查
    PLATFORM_APPLICATION：Platform.sh 运行应用时一定会注入它，
    本地没有——所以「变量存在与否」就是「我在哪」的判据。
    """
    on_platform = os.environ.get("PLATFORM_APPLICATION") == "1"
    return {
        "DEBUG": not on_platform,
        "数据库": "PostgreSQL（credentials('database')）" if on_platform else "SQLite（db.sqlite3）",
        "ALLOWED_HOSTS": ["localhost", ".platformsh.site"] if on_platform else ["localhost"],
        "STATIC_ROOT": "/app/static" if on_platform else None,
        "SECRET_KEY": "config.projectEntropy" if on_platform else "settings.py 里的字符串",
        "错误页面": "定制 404/500" if on_platform else "Django 调试页（DEBUG=True）",
    }


if __name__ == "__main__":
    label = "Platform.sh 云环境" if os.environ.get("PLATFORM_APPLICATION") else "本地开发"
    print(f"=== 当前环境：{label} ===")
    for key, value in build_settings().items():
        print(f"  {key:<14} = {value}")

在示例 5 基础上新增一项「依赖体检」（完整脚本 = 示例 5 + 下面新增部分），其余方向（测试文件有无、build 钩子是否含 collectstatic）思路相同，都是「读文件内容 → 判断关键词」：

Python# 新增检查：requirements.txt 是否锁版本 + 线上依赖齐全
def check_requirements(root):
    results = []
    main_file = root / "requirements.txt"
    if not main_file.exists():
        return [("✗", "requirements.txt 不存在")]
    text = main_file.read_text(encoding="utf-8")
    unpinned = [
        line for line in text.splitlines()
        if line.strip() and not line.strip().startswith("#") and "==" not in line
    ]
    if unpinned:
        results.append(("✗", f"有未锁版本的依赖：{unpinned}"))
    remote = root / "requirements_remote.txt"
    remote_text = remote.read_text(encoding="utf-8") if remote.exists() else ""
    for pkg in ("gunicorn", "psycopg2"):
        if pkg not in remote_text.lower():
            results.append(("✗", f"requirements_remote.txt 缺少 {pkg}（线上跑不起来）"))
    if not results:
        results.append(("✓", "依赖清单：版本已锁，线上依赖齐全"))
    return results

六、常见错误清单（务必逐条自查）

错误 1：★ ALLOWED_HOSTS 没加平台域名，线上 400

现象：部署成功、日志没报错，但一打开网址就是 400 Bad Request。原因：Django 校验每个请求的 Host 头，不在 ALLOWED_HOSTS 就直接 400，视图根本不执行。修复：settings.py 的 Platform.sh 段加 ALLOWED_HOSTS.append('.platformsh.site')，提交后重新 push。

错误 2：忘了注册 django_bootstrap5，模板报 Invalid block tag

现象：页面 500，报 TemplateSyntaxError: Invalid block tag: 'bootstrap_form'。原因：{% load %} 只是「打开工具包」，包本身要在 INSTALLED_APPS 注册。修复：INSTALLED_APPS 加 'django_bootstrap5'。

错误 3：DEBUG 关了却没收静态文件，白脸页面

现象：线上页面结构都在，但没有样式。原因：DEBUG = False 后 Django 不再代发静态文件；collectstatic 没跑，或 STATIC_ROOT 没设置。修复：build 钩子确保有 python manage.py collectstatic --noinput，云上段设置 STATIC_ROOT。

错误 4：requirements.txt 漏了 gunicorn 或 psycopg2

现象：部署日志 ModuleNotFoundError: No module named 'gunicorn'，或连不上数据库。原因：本地用 runserver + SQLite，这两个包本地没装过，pip freeze 不会列出来。修复：建 requirements_remote.txt 写上两者，并在 build 钩子里 pip install -r requirements_remote.txt。

错误 5：.gitignore 缺失，虚拟环境和本地数据库被推上云

现象：push 奇慢，仓库几百 MB；甚至线上用了你本地带数据的 SQLite 文件。原因：没有 .gitignore，git add . 把 ll_env/、__pycache__/、db.sqlite3 全提交了。修复：补写 .gitignore，用 git rm -r --cached 把已跟踪文件撤出索引，再提交。

错误 6：新文件忘了 git add，推送后线上缺东西

现象：本地明明建了 templates/404.html，线上还是默认错误页。原因：git commit -am 只提交已跟踪文件的修改，新文件必须先 git add。修复：只要产生了新文件（包括 makemigrations 生成的迁移文件），先 git add . 再 commit。

七、本单元验收自测

1. 简答题：{% load django_bootstrap5 %} 和 {% bootstrap_form form %} 分别负责什么？只写后者不写前者会怎样？

要点：load 把模板标签库加载进当前模板，是「拿工具」；bootstrap_form 把字段逐个渲染成带 Bootstrap 类名的 HTML，是「干活的」。只写后者会报 TemplateSyntaxError: Invalid block tag——INSTALLED_APPS 注册和模板 load 缺一不可。

2. 判断题：requirements.txt 里写 Django（不带 == 版本号）也能正常部署，只是不优雅。

要点：错误。不带 == 意味着装最新版。大版本升级经常带不兼容改动，半年后平台重建环境时可能直接启动失败。锁版本是部署的纪律，不是风格问题。

3. 简答题：relationships: database: "db:postgresql" 里的暗号怎么读？routes.yaml 的 upstream: "ll_project:http" 又和谁对应？

要点："db:postgresql" 冒号前是 services.yaml 里的服务名（db），冒号后是服务类型；config.credentials('database') 读的就是这份关系。routes 的 upstream 必须和 .platform.app.yaml 的 name 一致——路由按应用名转发域名。两处暗号对不上，部署直接失败。

4. 改错题：下面这段被加进 settings.py 的 Platform.sh 段，但部署后数据库连不通。为什么？

Python# settings_snippet.py —— INTENTIONALLY-BROKEN 演示用：改错题，数据库配置连不通
from platformshconfig import Config

config = Config()
if config.is_valid_platform():
    db_settings = config.credentials('database')
    # 有 bug：引擎写死 SQLite，读来的 PostgreSQL 连接信息一个都没用
    DATABASES = {'default': {'ENGINE': 'django.db.backends.sqlite3', 'NAME': 'db.sqlite3'}}

要点：引擎写死了 SQLite，读来的 PostgreSQL 连接信息（host/port/username/password）一个都没用。云上必须用 'django.db.backends.postgresql'，并把 db_settings 的字段填进 NAME/USER/PASSWORD/HOST/PORT。另外 credentials('database') 要放在 if not config.in_build(): 里——构建阶段连不上数据库。

5. 简答题：DEBUG = False 之后，本地看到的报错页发生了什么变化？为什么定制 404/500 要求 DEBUG = False？

要点：DEBUG = False 后 Django 不再显示带堆栈信息的黄色调试页，而是渲染 templates/404.html/500.html。调试页会泄露配置细节（设置项、SQL、文件路径），只适合本地；线上关闭调试后，友好的定制错误页才出场。

6. 简答题：描述一次「加功能」的完整部署流程，从本地改第一行代码到线上验证。

要点：① 本地改代码并跑通；② 产生了新文件（含迁移文件）就 git add .；③ git commit -am "提交说明"；④ platform push（平台自动执行 build 钩子装依赖、collectstatic，再执行 deploy 钩子 migrate）；⑤ platform url 打开线上网址验证；出问题先看部署日志，修好再走一遍 ③④。
