# 单元 10 · 并发模型与执行器

> 教材第 19–20 章 ｜ 4 节课 × 90 分钟 ｜ 建议 1–2 周

## 单元导入

并发不是「同时做很多事」，而是「让等待重叠」。判断该用什么工具，只看一个问题：**瓶颈在 CPU 还是在 IO？**

- CPU 密集：计算、压缩、图像处理 → 多进程；
- IO 密集：网络、磁盘、数据库 → 线程或协程；
- 既有计算又有等待 → 拆开，或进程池 + 异步 IO 组合。

CPython 默认构建有 GIL：同一时刻只有一个线程执行 Python 字节码。它保护了解释器内部状态，但也意味着多线程不能加速纯 Python 计算。本单元先把这件事讲透，再进入 `concurrent.futures` 的两种执行器。

学完本单元，你应该能：

- 用「CPU 密集 / IO 密集」判断并发方案；
- 写出线程安全的计数器，解释竞态与锁；
- 用 `ThreadPoolExecutor` 并发下载，用 `ProcessPoolExecutor` 并行计算；
- 正确处理超时、异常、取消与资源回收。

## 第 37 课 · 并发全景：GIL、线程、进程

> 本节目标：能解释 GIL 的作用与边界，判断一个任务是 CPU 密集还是 IO 密集，并选出对应的并发模型。

### 讲解

并发（concurrency）是「多个任务在重叠的时间段内推进」，并行（parallelism）是「同一时刻真正同时执行」。单核也能并发，靠的是切换。

GIL（Global Interpreter Lock）是 CPython 解释器的一把全局锁：

- 同一进程内，同一时刻只有一个线程在执行 Python 字节码；
- 线程执行 IO（网络、文件、`sleep`）时会释放 GIL；
- 某些 C 扩展（NumPy 的部分运算、压缩库）会在计算时释放 GIL。

因此：

| 任务类型 | 多线程 | 多进程 | 异步 IO |
|---|---|---|---|
| CPU 密集（纯 Python） | ❌ 几乎无加速 | ✅ 接近线性 | ❌ |
| IO 密集（网络/磁盘） | ✅ | ✅（但开销大） | ✅ 最轻 |
| 大量短连接 | 一般 | ❌ | ✅ |

```python
import time

def cpu_task(n):
    return sum(i * i for i in range(n))

t0 = time.perf_counter()
for _ in range(4):
    cpu_task(2_000_000)
print("serial", time.perf_counter() - t0)
```

把这段改成 4 个线程跑，通常不会更快；改成 4 个进程才会。

### 延伸：GIL 到底卡住什么

一句话：同一时刻只有一个线程在执行 Python 字节码。但下面这些会**主动释放 GIL**：

- `time.sleep`、文件读写、socket 收发（等 IO 时释放）
- 大量 C 扩展在长计算中释放（NumPy 大矩阵、`zlib`、`hashlib`）
- 任何 `Py_BEGIN_ALLOW_THREADS` 包裹的 C 代码

所以「IO 密集用线程有效、纯 Python 计算密集用线程更慢」不是玄学，是释放点在哪的问题。

```python
import sys
sys.setswitchinterval(0.001)      # 默认 0.005 秒，调小切换更频繁
print(sys.getswitchinterval())
```

CPython 3.13 起提供 free-threaded 构建（PEP 703，`python3.13t`），可以真正并行，但单线程性能有折损、第三方扩展的兼容仍在推进。写库时的正确姿势是「假设 GIL 可能存在也可能不存在」：不要依赖它做原子性保证，`+=` 在自由线程下不是原子的。

### 关键点

- **GIL 不是 Python 语言规范**，是 CPython 的实现；3.13 起提供实验性的 free-threaded 构建，但默认构建仍有 GIL。
- **GIL 不保证线程安全**：`x += 1` 仍是「读—改—写」三步，可能被切换。
- **进程有独立内存**，通信要序列化（pickle），启动成本高。
- **线程适合 IO，不是因为线程快，而是因为等待时不占 CPU**。

## 第 38 课 · 线程与锁：竞态、队列与退出

> 本节目标：能复现一次竞态，用 Lock 修复，用 Queue 做生产者—消费者，并让线程正确退出。

### 讲解

竞态来自「读—改—写」不是原子操作：

```python
import threading

counter = 0

def worker():
    global counter
    for _ in range(100_000):
        counter += 1          # 可能被切换

ts = [threading.Thread(target=worker) for _ in range(4)]
[t.start() for t in ts]
[t.join() for t in ts]
print(counter)                # 通常小于 400000
```

加锁修复：

```python
lock = threading.Lock()
counter = 0

def worker():
    global counter
    for _ in range(100_000):
        with lock:
            counter += 1
```

生产者—消费者用 `queue.Queue`，它内部已经处理好同步：

```python
import queue, threading

q = queue.Queue(maxsize=100)

def producer():
    for i in range(1000):
        q.put(i)
    q.put(None)               # 哨兵：通知消费者结束

def consumer():
    while True:
        item = q.get()
        if item is None:
            break
        process(item)
        q.task_done()
```

### 延伸：进程池的两个硬约束

```python
import multiprocessing as mp

def work(x):
    return x * x

if __name__ == "__main__":
    with mp.Pool(4) as pool:
        print(pool.map(work, range(5)))    # [0, 1, 4, 9, 16]
```

两个约束：

1. **启动方式**：Linux 默认 `fork`（复制父进程），Windows 与 macOS 默认 `spawn`（重新导入主模块）。用 spawn 时，启动代码必须放在 `if __name__ == "__main__":` 下，否则子进程导入模块时会再次创建进程，无限递归。
2. **必须可 pickle**：参数和返回值都要序列化，所以不能传 lambda、打开的文件、数据库连接、线程锁。函数本身也得是模块级可导入的，定义在函数内部的嵌套函数传不过去。

进程间默认不共享内存（`Value`、`Array`、`shared_memory` 例外）。这就是「进程绕过 GIL，但贵在序列化」的账：数据量大时，序列化开销可能吃掉并行收益。

### 关键点

- **锁要尽量短**，持锁做 IO 等于把并发退化成串行。
- **避免嵌套锁**，需要多把锁时固定获取顺序，否则会死锁。
- **`Queue` 的 `task_done()` 与 `join()` 配对**，忘了会让主线程永远等。
- **线程不能强杀**，用哨兵或 `Event` 通知退出，再 `join()`。

## 第 39 课 · 执行器：ThreadPoolExecutor 与 ProcessPoolExecutor

> 本节目标：能用两种执行器提交任务、收集结果、处理异常，并知道各自的启动成本与限制。

### 讲解

`concurrent.futures` 把线程/进程池抽象成同一套 API：

```python
from concurrent.futures import ThreadPoolExecutor, as_completed

def fetch(url):
    ...

with ThreadPoolExecutor(max_workers=8) as pool:
    futures = {pool.submit(fetch, u): u for u in urls}
    for fut in as_completed(futures):
        url = futures[fut]
        try:
            print(url, fut.result())
        except Exception as e:
            print(url, "failed:", e)
```

`ProcessPoolExecutor` 用法几乎一样，但有两个硬限制：参数与返回值必须可 pickle，任务函数必须在模块顶层定义（`__main__` 里直接跑要加 `if __name__ == "__main__":`）。

```python
from concurrent.futures import ProcessPoolExecutor

def square(x):
    return x * x

if __name__ == "__main__":
    with ProcessPoolExecutor() as pool:
        print(list(pool.map(square, range(10))))
```

`map` 按输入顺序返回，`as_completed` 按完成顺序返回；需要「谁先好先处理谁」就用后者。

### 延伸：Executor.map 的返回顺序与异常时机

`map` 会**立刻提交所有任务**，返回按**输入顺序**产出结果的迭代器；异常不在提交时抛，而是等迭代到那一项：

```python
from concurrent.futures import ThreadPoolExecutor

def bad(x):
    if x == 2:
        raise ValueError(x)
    return x

with ThreadPoolExecutor() as ex:
    for v in ex.map(bad, [1, 2, 3]):
        print(v)          # 打印 1，然后抛 ValueError(2)
```

它不会取消后面已提交的任务——3 和 3 之后的任务照样在跑，只是结果没人取。要边完成边处理就用 `as_completed`。`map(..., timeout=n)` 的计时从**迭代开始**算，超时抛 `TimeoutError`，但后台任务仍在运行（Python 无法安全中断线程）。

### 关键点

- **线程池大小不是越大越好**：IO 密集可以 2–4 倍 CPU 核数，CPU 密集取核数。
- **`with` 退出会等待所有任务结束**；要提前取消用 `shutdown(cancel_futures=True)`。
- **异常存到 Future 里**，只有调用 `result()` 时才抛出。
- **进程池启动慢**，任务太短（毫秒级）时开销大于收益。

## 第 40 课 · 实战：并发下载与错误处理

> 本节目标：能把一个串行下载脚本改造成并发版，处理超时、重试、限速与部分失败，并给出可观测的进度。

### 讲解

需求：下载 50 个 URL，超时 5 秒，失败重试 2 次，输出成功/失败数量与耗时。

```python
import time
from concurrent.futures import ThreadPoolExecutor, as_completed
import urllib.request

def fetch(url, timeout=5, retries=2):
    for attempt in range(retries + 1):
        try:
            with urllib.request.urlopen(url, timeout=timeout) as r:
                return len(r.read())
        except Exception:
            if attempt == retries:
                raise
            time.sleep(0.5 * (attempt + 1))

def download_all(urls, workers=8):
    ok, failed = 0, []
    with ThreadPoolExecutor(max_workers=workers) as pool:
        futures = {pool.submit(fetch, u): u for u in urls}
        for i, fut in enumerate(as_completed(futures), 1):
            url = futures[fut]
            try:
                fut.result()
                ok += 1
            except Exception as e:
                failed.append((url, repr(e)))
            print(f"\r{i}/{len(urls)}", end="")
    return ok, failed
```

这个脚本的关键不是「用了线程池」，而是**失败不会拖垮整体**：单个 URL 抛异常只记录，不中断其他任务。

### 延伸：as_completed 与取消的边界

```python
from concurrent.futures import ThreadPoolExecutor, as_completed

with ThreadPoolExecutor(4) as ex:
    futs = {ex.submit(pow, i, 2): i for i in range(4)}
    for f in as_completed(futs):
        print(futs[f], f.result())
```

按完成先后产出，适合进度条和「先到先用」。`future.cancel()` 只对「还没开始执行」的任务生效，返回布尔值表示是否取消成功；已经在跑的线程取消不了——线程没有安全的中断点。所以「取消」在并发里通常意味着「设一个标志位，让任务自己检查后退出」，而不是强行掐断。

`shutdown(cancel_futures=True)`（3.9+）批量取消排队中的任务；`with` 退出时默认 `wait=True`，会等所有任务跑完，这点在服务优雅关闭时要注意。

### 关键点

- **超时必须显式设置**，默认无超时会让线程永久挂起。
- **重试要退避**，固定间隔会在服务端故障时形成雪崩。
- **并发度要有限制**，无上限会耗尽文件描述符或被目标限流。
- **进度输出要可关闭**，日志环境里 `\r` 会污染输出。
