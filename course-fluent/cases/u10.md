# 单元 10 综合案例 · 并发抓取：串行慢，乱并发更糟

> 20 个资源要抓，个别会失败。先串行跑一遍看耗时，再用线程池加进度、重试与失败分类。

### 重构前（串行 + 一失败就中断）

`for` 循环逐个抓，单个失败只能靠外层 `try` 兜住，没有进度、没有重试；20 个请求就是 20 个延迟相加。

```python
import time

TRIES = {}


def fetch(url):
    time.sleep(0.01)                 # 模拟网络往返
    if url.endswith("7"):
        raise OSError("connection reset")
    return f"{url}:200"


urls = [f"/p/{i}" for i in range(20)]

start = time.perf_counter()
results = []
for u in urls:
    try:
        results.append(fetch(u))
    except OSError as e:
        results.append(f"{u}:failed")
print("串行耗时", round(time.perf_counter() - start, 3), "s")
print("成功", sum(1 for r in results if r.endswith("200")),
      "失败", sum(1 for r in results if r.endswith("failed")))
```

### 重构后（线程池 + 完成即处理 + 任务内重试）

`as_completed` 谁先好谁先出，进度才是真实的；重试放在任务内部，避免「整体重跑」把已成功的又跑一遍；单个失败被收集，不影响其他任务。

```python
import time
from concurrent.futures import ThreadPoolExecutor, as_completed

TRIES = {}


def fetch(url, retries=2):
    for attempt in range(retries):
        TRIES[url] = TRIES.get(url, 0) + 1
        time.sleep(0.01)
        if url == "/p/13":
            continue                                  # 永久失败
        if url == "/p/7" and attempt < 1:
            continue                                  # 第一次失败，第二次成功
        return f"{url}:200"
    raise OSError(f"{url} failed after {retries} tries")


urls = [f"/p/{i}" for i in range(20)]
ok, bad = [], []

start = time.perf_counter()
with ThreadPoolExecutor(max_workers=8) as pool:
    futures = {pool.submit(fetch, u): u for u in urls}
    for done, fut in enumerate(as_completed(futures), 1):
        try:
            ok.append(fut.result())
        except OSError as e:
            bad.append(str(e))
        if done % 5 == 0:
            print(f"进度 {done}/{len(urls)}")

elapsed = time.perf_counter() - start
print("并发耗时", round(elapsed, 3), "s")
print("成功", len(ok), "失败", len(bad))
print("失败明细", bad)
print("重试过的地址数", sum(1 for v in TRIES.values() if v > 1))
```

### 差异说明

| 问题 | 重构前 | 重构后 | 收益 | 代价 |
|---|---|---|---|---|
| 耗时 | 20 个请求串行相加 | 8 路并发，约 1/5 | 延迟被重叠 | 线程与连接有开销 |
| 进度 | 全部跑完才知道 | 每完成 5 个打印一次 | 可观察、可中断 | 需要计数与输出节流 |
| 重试 | 没有，失败即记失败 | 任务内重试 2 次 | 瞬时故障自愈 | 失败慢任务会拖长整体 |
| 单点失败 | 被 `except` 吞掉，明细丢失 | 收集异常文本 | 能定位哪个地址 | 代码多一层分类 |
| 顺序 | 天然有序 | 完成顺序（乱序） | 谁快谁先出 | 需要保序时得自己排序 |
| 资源上限 | 天然 1 路 | `max_workers=8` | 不会打爆对方 | 墙钟时间受最慢任务影响 |

### 再往前一步

把重试加指数退避与随机抖动（`0.05 * 2**i + random.random()*0.01`），避免重试风暴；`max_workers` 应按「对方限流」定，不是按 CPU 核数。真要百万级任务，线程池会吃内存，应该换 `asyncio` + 信号量（下一单元），或用生产者-消费者队列控流。
