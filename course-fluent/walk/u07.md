@@u07|接口、协议与继承：三种「多态」的边界在哪
> 原书第 13 章与第 14 章其实在回答同一个问题：什么时候用抽象基类、什么时候用 Protocol、什么时候什么都不用。这一篇让三种写法同时处理同一件事，再比较它们的运行时行为。

## 程序

```python
from abc import ABC, abstractmethod
from typing import Protocol, runtime_checkable


# ① 抽象基类：强制实现，也可以在基类里放共享代码
class Storage(ABC):
    def __init__(self, name):
        self.name = name

    @abstractmethod
    def put(self, key, value):
        ...

    @abstractmethod
    def get(self, key):
        ...

    def describe(self):                      # 共享实现，子类直接继承
        return f"<{type(self).__name__} {self.name}>"


class MemoryStorage(Storage):
    def __init__(self):
        super().__init__("memory")
        self._data = {}

    def put(self, key, value):
        self._data[key] = value

    def get(self, key):
        return self._data.get(key)


# ② Protocol：只要「长得像」，不要求继承
@runtime_checkable
class KeyValue(Protocol):
    def put(self, key, value) -> None: ...
    def get(self, key): ...


class ThirdParty:                            # 完全不知道 Storage / KeyValue 的存在
    def __init__(self):
        self.d = {}

    def put(self, key, value):
        self.d[key] = value

    def get(self, key):
        return self.d.get(key)


# ③ 继承中的协作式 super()：菱形里每个父类只初始化一次
class A:
    def __init__(self):
        super().__init__()
        self.trace = ["A"]
        print("  init A")


class B(A):
    def __init__(self):
        super().__init__()
        self.trace.append("B")
        print("  init B")


class C(A):
    def __init__(self):
        super().__init__()
        self.trace.append("C")
        print("  init C")


class D(B, C):
    def __init__(self):
        super().__init__()
        self.trace.append("D")


print("MRO     ", [k.__name__ for k in D.__mro__][:5])
print("构造顺序")
d = D()
print("trace   ", d.trace)

# ④ 三种多态的实际效果
mem = MemoryStorage()
mem.put("k", 1)
tp = ThirdParty()
tp.put("k", 2)
print("ABC     ", isinstance(mem, Storage), "| describe:", mem.describe())
print("Protocol", isinstance(tp, KeyValue), "| 结构匹配", hasattr(tp, "put") and hasattr(tp, "get"))
try:
    Storage("x")
except TypeError as e:
    print("抽象类  ", str(e)[:52])

# ⑤ 缺方法时的报错时机：ABC 在构造时，Protocol 在调用时
class HalfStorage(Storage):
    def put(self, key, value):
        pass

try:
    HalfStorage()
except TypeError as e:
    print("缺 get  ", str(e)[:52])
```

## 逐段走读

1. **ABC 的价值是「构造时就拦」和「能放共享代码」。** `Storage` 里既有抽象方法，也有 `describe()` 这样的具体方法——这是 ABC 相对 Protocol 的最大优势：它既是接口也是实现。最后一段就是证据：少实现一个方法，`HalfStorage()` 在**实例化**时直接报错，并点名 `get`。

2. **Protocol 的价值是「不侵入别人的类」。** `ThirdParty` 是从第三方库拿来的，不能改它的继承链，但它有 `put`/`get`，于是 `isinstance(tp, KeyValue)` 为 `True`——注意这里必须加 `@runtime_checkable`，否则 `isinstance` 会抛 `TypeError`。代价是运行时检查只看**方法名是否存在**，不看签名和类型，比 ABC 弱。

3. **结构匹配（鸭子类型）是三者的公共底座。** 即使不写 `isinstance`，`tp.put(...)` 照样能调用。Protocol 只是把「我以为它有这个方法」变成可检查、可被静态类型检查器理解的声明；运行时行为并没有变。

4. **协作式 `super()` 保证菱形只初始化一次。** `D(B, C)` 的 MRO 是 `D → B → C → A → object`，`super().__init__()` 每次都去找 MRO 里的**下一个**类，所以 `A.__init__` 只执行一次——但注意顺序：先到最底层的 `A`，再依次回到 `C`、`B`、`D`。输出里的 `trace` 是 `['A', 'C', 'B', 'D']`，初始化像栈一样从底往上冒。如果哪个类忘了写 `super().__init__()`，链条就断了，后面的类不会被初始化（也很少报错，属于隐蔽 bug）。

5. **MRO 的顺序由 C3 线性化决定。** 写 `class D(B, C)` 时，`B` 的所有祖先必须排在 `C` 之前，所以是 `D B C A`。如果 `B` 和 `C` 都直接继承 `A` 且顺序冲突，Python 会拒绝创建类并抛 `TypeError: Cannot create a consistent MRO`——这是设计层面的保护。

6. **`isinstance` 与 `issubclass` 对 Protocol 有额外规则。** `runtime_checkable` 的 Protocol 只支持 `isinstance`，`issubclass` 对带数据成员的 Protocol 会报错；ABC 则两者都支持，因为它是真的继承关系。

## 跑通之后改三处

- 把 `class D(B, C)` 改成 `class D(C, B)`：`trace` 变成 `['A', 'B', 'C', 'D']`，说明 MRO 顺序直接决定初始化顺序。
- 删掉 `B.__init__` 里的 `super().__init__()`：`trace` 里 `A` 消失，`C` 也不会被初始化——断链的后果一目了然。
- 去掉 `@runtime_checkable`：`isinstance(tp, KeyValue)` 立刻抛 `TypeError`。
