@@37|GIL 到底卡住什么
一句话：同一时刻只有一个线程在执行 Python 字节码。但下面这些会**主动释放 GIL**：

- `time.sleep`、文件读写、socket 收发（等 IO 时释放）
- 大量 C 扩展在长计算中释放（NumPy 大矩阵、`zlib`、`hashlib`）
- 任何 `Py_BEGIN_ALLOW_THREADS` 包裹的 C 代码

所以「IO 密集用线程有效、纯 Python 计算密集用线程更慢」不是玄学，是释放点在哪的问题。

```python
import sys
sys.setswitchinterval(0.001)      # 默认 0.005 秒，调小切换更频繁
print(sys.getswitchinterval())
```

CPython 3.13 起提供 free-threaded 构建（PEP 703，`python3.13t`），可以真正并行，但单线程性能有折损、第三方扩展的兼容仍在推进。写库时的正确姿势是「假设 GIL 可能存在也可能不存在」：不要依赖它做原子性保证，`+=` 在自由线程下不是原子的。

@@38|进程池的两个硬约束
```python
import multiprocessing as mp

def work(x):
    return x * x

if __name__ == "__main__":
    with mp.Pool(4) as pool:
        print(pool.map(work, range(5)))    # [0, 1, 4, 9, 16]
```

两个约束：

1. **启动方式**：Linux 默认 `fork`（复制父进程），Windows 与 macOS 默认 `spawn`（重新导入主模块）。用 spawn 时，启动代码必须放在 `if __name__ == "__main__":` 下，否则子进程导入模块时会再次创建进程，无限递归。
2. **必须可 pickle**：参数和返回值都要序列化，所以不能传 lambda、打开的文件、数据库连接、线程锁。函数本身也得是模块级可导入的，定义在函数内部的嵌套函数传不过去。

进程间默认不共享内存（`Value`、`Array`、`shared_memory` 例外）。这就是「进程绕过 GIL，但贵在序列化」的账：数据量大时，序列化开销可能吃掉并行收益。

@@39|Executor.map 的返回顺序与异常时机
`map` 会**立刻提交所有任务**，返回按**输入顺序**产出结果的迭代器；异常不在提交时抛，而是等迭代到那一项：

```python
from concurrent.futures import ThreadPoolExecutor

def bad(x):
    if x == 2:
        raise ValueError(x)
    return x

with ThreadPoolExecutor() as ex:
    for v in ex.map(bad, [1, 2, 3]):
        print(v)          # 打印 1，然后抛 ValueError(2)
```

它不会取消后面已提交的任务——3 和 3 之后的任务照样在跑，只是结果没人取。要边完成边处理就用 `as_completed`。`map(..., timeout=n)` 的计时从**迭代开始**算，超时抛 `TimeoutError`，但后台任务仍在运行（Python 无法安全中断线程）。

@@40|as_completed 与取消的边界
```python
from concurrent.futures import ThreadPoolExecutor, as_completed

with ThreadPoolExecutor(4) as ex:
    futs = {ex.submit(pow, i, 2): i for i in range(4)}
    for f in as_completed(futs):
        print(futs[f], f.result())
```

按完成先后产出，适合进度条和「先到先用」。`future.cancel()` 只对「还没开始执行」的任务生效，返回布尔值表示是否取消成功；已经在跑的线程取消不了——线程没有安全的中断点。所以「取消」在并发里通常意味着「设一个标志位，让任务自己检查后退出」，而不是强行掐断。

`shutdown(cancel_futures=True)`（3.9+）批量取消排队中的任务；`with` 退出时默认 `wait=True`，会等所有任务跑完，这点在服务优雅关闭时要注意。

@@41|协程、Task、Future 的分工
- **协程（coroutine）**：`async def` 调出来的对象，**还没开始执行**，需要被 `await` 或被包装成 Task。
- **Task**：把协程排进事件循环的执行单元，`asyncio.create_task()` 之后它就在后台跑了。
- **Future**：更低层的「结果占位符」，Task 是它的子类；回调式 API 用它。

```python
import asyncio

async def work():
    return 1

async def main():
    coro = work()                      # 协程，未执行
    task = asyncio.create_task(coro)   # 交给循环调度
    print(await task)                  # 1

asyncio.run(main())
```

`asyncio.run` 每次创建新循环、跑完关闭。已经处在循环里（Jupyter、框架回调、另一个协程）不能调它，否则报 `RuntimeError: asyncio.run() cannot be called from a running event loop`，要用 `await`。需要自己管循环时：

```python
loop = asyncio.new_event_loop()
try:
    loop.run_until_complete(main())
finally:
    loop.close()
```

@@42|to_thread 是什么，以及它的上限
```python
import asyncio, time

def blocking(x):
    time.sleep(x)
    return x

async def main():
    r = await asyncio.to_thread(blocking, 0.1)    # 3.9+
    print(r)

asyncio.run(main())
```

`asyncio.to_thread` 就是 `loop.run_in_executor(None, partial(fn, *args))` 的语法糖，用的是默认 `ThreadPoolExecutor`，线程上限 `min(32, os.cpu_count() + 4)`。所以它是「把阻塞挪走」，不是「变出并行」：CPU 密集还是得 `ProcessPoolExecutor`。

反例最典型：协程里直接 `time.sleep(1)`，整个事件循环停 1 秒，所有并发任务一起卡住。判断标准是「这段代码会不会占住线程超过 ~10ms」，会就挪走。`gather` 里塞一万个任务也不行，那是「用并发打爆对方」，要配 `Semaphore`。

@@43|start_server 与异步迭代协议
```python
import asyncio

async def handle(reader, writer):
    data = await reader.readline()
    writer.write(b"echo: " + data)
    await writer.drain()          # 背压点：等缓冲区可写
    writer.close()

async def main():
    srv = await asyncio.start_server(handle, "127.0.0.1", 8888)
    async with srv:
        await srv.serve_forever()
```

`start_server` 是回调式：每来一个连接，事件循环调一次 `handle` 生成协程。`writer.drain()` 是背压点，漏了会在对方读得慢时把数据堆在内存里。

异步迭代协议是 `__aiter__` 返回自身、`__anext__` 是协程，结束时抛 `StopAsyncIteration`；`async for` 就是它的语法糖。异步上下文管理器对应 `__aenter__`/`__aexit__`。数据库/HTTP 客户端的 `async with` 全是这两组协议。

@@44|协作式调度的真实代价
异步不是「多线程的轻量版」，而是「单线程 + 主动让出」。只有 `await` 处才可能切换，所以任何一段不让出的代码都会独占循环：

- 大循环、`sum(huge_list)`、正则灾难性回溯
- `json.loads` 一个 100 MB 的响应
- 同步库的 `requests.get`、`pandas.read_csv`

它们不会报错，只会让所有并发任务一起变慢，排查时表现为「QPS 上不去、延迟全是整数倍」。三个手段：`to_thread` 挪走、分片 `await asyncio.sleep(0)` 让出、换异步原生库。

调试：`PYTHONASYNCIODEBUG=1` 或 `loop.set_debug(True)` 会打印「Executing <Task> took 2.3 seconds」的慢回调警告，比猜快得多。

@@45|property 的三个角色与特性工厂
```python
class Temp:
    def __init__(self, c):
        self._c = c

    @property
    def c(self):
        return self._c

    @c.setter
    def c(self, v):
        if v < -273.15:
            raise ValueError("below absolute zero")
        self._c = v

    @c.deleter
    def c(self):
        del self._c
```

三者共享同一个名字，后定义的两个用 `@名字.setter` / `@名字.deleter`。只定义 getter 就是只读；只定义 setter 而没有 getter 会得到一个写不进也读不出的怪东西，别这么写。

特性工厂用闭包批量生成校验属性：

```python
def positive(name):
    def get(self):
        return getattr(self, "_" + name)
    def set(self, v):
        if v <= 0:
            raise ValueError(f"{name} must be positive")
        setattr(self, "_" + name, v)
    return property(get, set)

class Order:
    qty = positive("qty")
```

代价是 IDE 跳转和类型检查变弱，字段少时手写更清楚。字段多、校验规则一致时才值得上工厂。

@@46|函数就是非数据描述符
函数只实现 `__get__`（没有 `__set__`），属于**非数据描述符**，被存在类上；实例访问时 `__get__` 返回绑定方法。这解释了两件事：

```python
class C:
    def m(self): return "method"

c = C()
print(c.m())                 # method
c.m = lambda: "instance"
print(c.m())                 # instance ← 实例字典盖住了方法
```

1. 为什么实例属性可以「盖住」方法（非数据描述符优先级低于实例字典）。
2. 为什么 `property` 盖不住（它是**数据**描述符，优先级最高）。

完整优先级：**数据描述符 > 实例字典 > 非数据描述符 > 类属性**。这条规则是所有「属性拦截」方案的地基：想拦住赋值就必须实现 `__set__`（或 `__delete__`）。

`__set_name__`（3.6+）在类创建时被调用，描述符靠它知道自己叫 `name`，不用再手动传名字：

```python
class Field:
    def __set_name__(self, owner, name):
        self.name = name
```

@@47|type 是类工厂，__prepare__ 换命名空间
`type(name, bases, ns)` 三参数形式就是类工厂，`class` 语句本质是它的语法糖：

```python
def make(name, **attrs):
    return type(name, (), attrs)

P = make("P", x=1)
print(P.x, type(P))      # 1 <class 'type'>
```

元类里三个钩子的分工：

- `__prepare__(mcls, name, bases)`：决定类体写入哪个命名空间，默认普通 dict。返回 `OrderedDict` 或自定义映射就能记录定义顺序（早期 dataclass 这么干过），甚至做「禁止重复字段名」的检查。
- `__new__(mcls, name, bases, ns)`：真正造类，改类结构（加方法、收集字段）在这里做。
- `__init__(cls, name, bases, ns)`：类造好后的收尾，一般只做注册。

顺序是 `__prepare__` → 执行类体 → `__new__` → `__init__`。想「在类体执行时就拦截名字」只能用 `__prepare__` 返回自定义映射，`__new__` 已经太晚了。

@@48|四类钩子的检索法
拿到陌生框架，按四个关键词搜源码，基本能画出扩展点地图：

| 关键词 | 机制 | 典型用途 |
|---|---|---|
| `__get__` | 描述符 | 字段 / 属性拦截、惰性加载、ORM 列 |
| `__set_name__` | 类创建回调 | 字段注册、知道自己叫什么 |
| `__init_subclass__` | 子类定义回调 | 插件注册、自动加功能 |
| `metaclass=` | 元类 | 整类改造、接口约束 |

```python
class Plugin:
    registry = {}
    def __init_subclass__(cls, **kw):
        super().__init_subclass__(**kw)
        Plugin.registry[cls.__name__] = cls

class JsonPlugin(Plugin):
    pass

print(Plugin.registry)      # {'JsonPlugin': <class 'JsonPlugin'>}
```

`__init_subclass__` 是「不需要元类就能在子类定义时拿到钩子」的正规做法，1980 年代的元类需求里有一大半它能替代。判断该不该上元类：只需要「子类定义时做一件事」就用 `__init_subclass__`；需要改类的创建过程本身（换命名空间、改 `__call__`）才用元类。

读框架的顺序：先找钩子 → 再顺着钩子看调用链 → 最后才读工具函数。看不懂就先写 20 行最小复现，把框架剥到只剩钩子。
