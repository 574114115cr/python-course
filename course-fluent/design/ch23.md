@@ch23|描述符
> 描述符是「属性访问为什么能定制」的答案，也是 property 的实现机制——懂它，但少用它。

| 项 | 内容 |
|---|---|
| 选择 | `__get__` / `__set__` / `__delete__` 协议，挂在类属性上生效 |
| 主要替代 | `property`、`__getattr__` 钩子、类装饰器 |
| 替代为何落选 | `property` 是描述符的语法糖，已覆盖多数场景；钩子粒度太粗；装饰器改不了访问语义 |
| 付出的代价 | 概念门槛高；数据/非数据描述符的优先级规则必须背下来 |

## 当时的约束

Python 2.2 引入新式类时，需要一个统一机制来实现「函数为什么能变成绑定方法」「property」「classmethod」「staticmethod」。它们的共同点是：定义在类上的东西，通过实例访问时行为不同。逐特性各做一套语法糖可以解决问题，但机制会越攒越乱。

## 候选方案

每种特性单独实现（早期确实如此）；或者抽出一个通用协议——只要对象定义了 `__get__`，访问时就把它「激活」。Guido 选了后者。

## 为什么选它

一个协议同时支撑了绑定方法、`property`、`classmethod`/`staticmethod`，以及后来 ORM 的字段。因为描述符是类属性，同一个实例能被所有对象共享，也能在类级别做校验、缓存和文档。理解了描述符，Python 属性访问的整张图（实例 `__dict__` → 类型 `__dict__` → MRO）才真正对上。

## 代价与反例

优先级规则是最大的坑：数据描述符（定义了 `__set__`）优先级高于实例 `__dict__`，非数据描述符（只有 `__get__`）反而低于实例 `__dict__`——顺序记反，就会出现「设置了属性却不生效」的诡异 Bug。描述符做不到「每个实例一套不同规则」（它是类级共享），要实例级定制得回到 `__getattr__`。另外栈跟踪里看不出描述符被调用了，调试时凭空多出一层。

## 如果重来

仍然保留它作为底层机制，但会把「什么时候该自己写描述符」的回答写得更刺眼：几乎永远不用。除非你在写框架——ORM 的字段绑定、校验层、类型系统，那才是它的主场。业务代码里 `property` 就够了。
