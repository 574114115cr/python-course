@@ch19|并发模型
> 一个解释器一把 GIL：CPU 密集用进程，IO 密集用线程——这是分工，不是缺陷。

| 项 | 内容 |
|---|---|
| 选择 | 全局解释器锁（GIL）：同一时刻只有一个线程执行 Python 字节码 |
| 主要替代 | 无 GIL 的自由线程构建、多进程、每线程一个解释器 |
| 替代为何落选 | 无 GIL 要所有 C 扩展重写引用计数；多进程每次交互都要序列化 |
| 付出的代价 | 纯 Python 的 CPU 密集任务无法用线程提速，得搬 multiprocessing |

## 当时的约束

CPython 靠引用计数回收对象，而引用计数的增减不是原子操作。1990 年代的诉求是「让 C 扩展好写」：与其要求每个扩展自己加锁，不如解释器拿一把大锁，把线程安全这件事从扩展作者的待办清单里划掉。与此同时，操作系统线程已经能很好地处理 IO 阻塞。

## 候选方案

细粒度锁（每对象一把，复杂度与性能双输）、无 GIL（Greg Stein 当年的实验版慢了近一倍）、多进程（fork 便宜，但数据要 pickle）、GIL + 线程池。

## 为什么选它

早期 Python 的负载以 IO 密集为主：系统脚本、CGI、后来的 Web 前端。这些场景下线程照样并发——一个线程等 socket，另一个跑字节码，GIL 只在「都要跑 Python 代码」时互斥。CPU 密集的部分交给进程，`multiprocessing` 把接口做得和线程差不多。用一把锁换来整个 C 生态不需要考虑线程安全，这个交易在当时是赚的。

## 代价与反例

一个纯 Python 的密集计算能把整个进程卡死，`sys.setswitchinterval()` 只能调节线程让出的频率，治标不治本。多线程改写同一个 `list` 在字节码层是原子的，但 `x += 1` 不是——「看起来是一行」和「原子」是两回事。3.13 起的自由线程构建需要单独编译，且生态远未就绪，生产环境暂时别赌。

## 如果重来

仍然从 GIL 出发，但会更早提供开箱即用的进程池，并把「哪些标准库是线程安全的」写进文档首页，而不是让用户靠试错和古老的口头传说。
