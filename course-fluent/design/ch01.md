@@ch01|数据模型
> 让对象接入语言本身的语法，而不是让调用方记住你的方法名。

| 项 | 内容 |
|---|---|
| 选择 | 特殊方法协议（`__len__`、`__getitem__`、`__iter__`…） |
| 主要替代 | 显式方法：`obj.size()`、`obj.get(i)`（Java / C++ 容器风格） |
| 替代为何落选 | 语法位置只认特殊方法：`len()`、`for`、`[]`、`+`、`with` 都不会去看 `size()` |
| 付出的代价 | 调用隐式、栈里看不到调用点；C 层有时绕过你重写的方法 |

## 当时的约束

Python 从 1991 年就选择了「内置类型与用户类型尽量同权」。如果列表能 `len()` 而自定义容器只能 `.size()`，标准库、`for`、切片、解包就得为两套接口各写一遍。

## 候选方案

一是显式接口方法，调用方自己记名字；二是强制继承某个 `Collection` 基类；三是特殊方法协议——名字固定、由解释器在语法位置调用。

## 为什么选它

因为「语法位置」本身就是最强的契约：写 `for x in obj` 的人不需要知道你有没有 `.items()`。内置函数还带 C 层快速路径，`len(x)` 比 `x.__len__()` 快，这是显式方法拿不到的。

## 代价与反例

隐式调用让栈变浅，出问题时要靠 `__repr__` 和日志。C 实现有时跳过重写的方法：`dict.update()` 就不一定走你重写的 `__setitem__`。另外成对协议容易漏：只写 `__eq__` 不写 `__hash__`，对象立刻不可哈希。

## 如果重来

仍然是特殊方法，但会把「必须成对实现」写成检查规则（`__eq__`/`__hash__`、`__enter__`/`__exit__`、`__iter__`/`__next__`），并默认给容器类补 `__repr__`。
