## 二、核心知识点讲解

### 2.1 django-bootstrap5：一行代码让表单变漂亮（对应教材 20.1）

先回忆「学习笔记」的登录页面现在长什么样：光秃秃的输入框、光秃秃的按钮，像 1998 年的网页。原因很简单——Django 只负责把表单渲染成**合法**的 HTML，好不好看它一概不管：`{{ form.as_p }}` 渲染出的控件上没有任何 CSS 类，浏览器就用默认样式显示。生活化类比：**Django 是裁缝，只保证衣服合身；好不好看是造型师的事，django-bootstrap5 就是那位造型师。**

第 3 版教材用的是 **django-bootstrap5**（注意：不是第 2 版的 django-bootstrap4，Bootstrap 4 到 5 是不小的升级，库名也跟着换了）。用法分三步，一步都不能少：

```bash
# 1. 安装（在虚拟环境里）
(ll_env)learning_log$ pip install django-bootstrap5
```

```python
# 2. settings.py 的 INSTALLED_APPS 里注册（不注册，模板标签不生效）
INSTALLED_APPS = [
    'learning_logs',
    'accounts',
    'django_bootstrap5',      # ← 加这一行
    # ……（Django 自带的应用略）
]
```

```html
{% load django_bootstrap5 %}

<form action="{% url 'login' %}" method="post">
    {% csrf_token %}
    {% bootstrap_form form %}
    <button name="submit" class="btn btn-primary">登录</button>
</form>
```

两行模板标签的分工一定要分清：

- `{% load django_bootstrap5 %}`：**把工具包拿到这个模板里**。不 load 就用 `bootstrap_form`，Django 会报 `Invalid block tag`——就像工具落在家里，活儿没法干。它只负责加载，不改变任何输出。
- `{% bootstrap_form form %}`：**一键美颜**。它内部遍历表单的每个字段，给它们包上 Bootstrap 需要的 `div` 和 `form-control` 等类名。输出的还是同一个表单，但浏览器一渲染就有了圆角、间距、聚焦高亮。

★ 这里对新手最难的是：**模板标签不是 Python 函数**。你没法在 `{% bootstrap_form %}` 里写 `if`、传变量、或者 `print` 它看看结构。Django 模板语言是故意设计得「不会写代码」的，复杂逻辑必须提到视图函数里做好、用上下文传进来。想搞清楚它到底输出了什么，老办法：浏览器里右键「查看网页源代码」。

### 2.2 改造「学习笔记」的界面（对应教材 20.1 各小节）

讲 Django 项目，每动一个文件都要先说清：**这个文件是干什么的、改了它会影响什么**。这是新手在框架里最大的迷茫——「我不知道我改的东西在哪生效」。

先建静态文件目录。静态文件指 CSS、JavaScript、图片这类「不需要服务器计算、原样发给浏览器」的文件：

```text
learning_log/                  ← 项目根目录（manage.py 所在处）
├── ll_project/                ← 项目配置包（settings.py、urls.py 在这）
├── learning_logs/             ← 应用：主题和条目
│   ├── templates/learning_logs/   ← 这个应用专用模板
│   ├── static/css/styles.css      ← ★ 新建：我们自己写的样式
│   └── views.py
├── accounts/                  ← 应用：用户账户
├── templates/                 ← 项目级模板（404/500 放这，2.8 节用）
├── manage.py
└── db.sqlite3                 ← 本地开发数据库（不能传上云！）
```

各文件的职责和影响范围：

| 文件 | 干什么用 | 改了它影响什么 |
|---|---|---|
| `static/css/styles.css` | 补 Bootstrap 没有的样式（如 `.jumbotron`） | 引入了这个 CSS 的页面（base.html 引了就全站） |
| `templates/learning_logs/base.html` | 全站骨架：导航条 + 内容占位区 | **所有页面**，改坏了全站 500 |
| `templates/registration/login.html` | 登录页 | 只有登录页 |
| `templates/learning_logs/index.html` | 主页 | 只有主页 |
| `templates/learning_logs/topics.html` | 主题列表页 | 只有该页 |

**base.html 是「继承树」的根**：其他模板都 `{% extends %}` 它，所以 Bootstrap 的 CSS 链接写在 base.html 里，一次引入全站生效。导航条部分长这样：

```html
<nav class="navbar navbar-expand-md bg-body-tertiary mb-4 border">
  <div class="container-fluid">
    <a class="navbar-brand" href="{% url 'learning_logs:index' %}">学习笔记</a>
    <ul class="navbar-nav me-auto">
      <li class="nav-item"><a class="nav-link" href="{% url 'learning_logs:topics' %}">主题</a></li>
    </ul>
    <ul class="navbar-nav ms-auto">
      {% if user.is_authenticated %}
        <li class="nav-item"><span class="navbar-text">你好，{{ user.username }}。</span></li>
        <li class="nav-item">
          <form action="{% url 'logout' %}" method="post">
            {% csrf_token %}
            <button class="btn nav-link" type="submit">退出</button>
          </form>
        </li>
      {% else %}
        <li class="nav-item"><a class="nav-link" href="{% url 'login' %}">登录</a></li>
      {% endif %}
    </ul>
  </div>
</nav>

<main class="container">
  {% block page_header %}{% endblock page_header %}
  {% block content %}{% endblock content %}
</main>
```

注意 `{% if user.is_authenticated %}`：登录和未登录的人看到不同导航，这个判断用的是 Django 自动塞进每个模板的 `user` 对象，视图里什么都不用做。

**jumbotron**：教材给主页用了一个居中的大卡片当「门面」。这里有个版本细节——jumbotron 是 Bootstrap 4 时代的组件名，**Bootstrap 5 已经把它删掉了**（补充说明，教材未涉及），所以第 3 版的做法是在 `static/css/styles.css` 里自己写一个 `.jumbotron` 类，把当年的效果补回来：

```css
.jumbotron {
    padding: 2rem 1rem;
    margin-bottom: 2rem;
    background-color: #e9ecef;
    border-radius: 0.3rem;
}
```

登录页的表单用 `{% bootstrap_form form %}` 美颜，主题列表页用 Bootstrap 列表组（`list-group`）逐行列出主题。这些改动的共同点是：**只动模板和 CSS，不动任何 Python 代码**——这就是「样式」和「逻辑」分离的好处。

「改了它会影响什么」这张表，底层数据结构其实就是一条 `{% extends %}` 链。把模板当字符串读一遍，就能自动算出影响范围：

```python
# 模板继承链：谁 extends 谁，渲染时从最外层往里套
import re

TEMPLATES = {
    "learning_logs/base.html":
        "<nav>导航条</nav>{% block content %}{% endblock content %}",
    "learning_logs/topics.html":
        '{% extends "learning_logs/base.html" %}{% block content %}<h2>主题</h2>{% endblock %}',
    "registration/login.html":
        '{% extends "learning_logs/base.html" %}{% block content %}<form>…</form>{% endblock %}',
}


def chain(name, depth=0):
    """顺着 extends 往上找，返回 [(模板名, 缩进层级)]。"""
    body = TEMPLATES[name]
    found = re.search(r'{%\s*extends\s+"([^"]+)"\s*%}', body)
    me = [(name, depth)]
    return me + (chain(found.group(1), depth + 1) if found else [])


for page in ("learning_logs/topics.html", "registration/login.html"):
    print(f"{page} 的继承链：")
    for name, depth in chain(page):
        print("  " + "    " * depth + ("└─ " if depth else "") + name)

print("\n改 base.html 的导航条 = 改全站；改 topics.html 只影响一个页面。")
print("这就是 unit 20 里「改了它影响什么」那张表能一眼看懂的底层原因。")
```

跑出来两条链都指向同一个根 `learning_logs/base.html`——**它被全站每个页面 extends，所以它坏了就是全站 500**；而 `topics.html` 只出现在自己的链里。凡是「有几个模板 extends 我」这个数大的文件，改动前都该多跑一次测试。

### 2.3 部署是什么：从「只有你能跑」到「谁都能访问」（对应教材 20.2）

到目前为止，「学习笔记」只活在你这台电脑上。**部署（deploy）就是把它搬到一个 7×24 小时开机的云服务器上，让任何人输入网址都能访问。**

先建立本地与云环境的差异感，这张表是后面所有操作的「为什么」：

| 事项 | 本地开发 | Platform.sh 云环境 |
|---|---|---|
| 数据库 | SQLite（一个文件） | PostgreSQL（独立数据库容器） |
| Web 服务器 | `manage.py runserver`（仅供开发调试） | gunicorn（生产级 WSGI 服务器） |
| 静态文件 | 直接读 `static/` 目录 | 构建时 `collectstatic` 汇总到 STATIC_ROOT |
| `DEBUG` | `True`（报错显示详细信息） | **必须 `False`**（否则泄露配置、拖慢速度） |
| 依赖来源 | 你手动 `pip install` 的现成环境 | 一台**干干净净的新机器**，全靠 `requirements.txt` 重建 |
| `ALLOWED_HOSTS` | `localhost` 就行 | 必须写上平台的域名，否则一律 400 |

生活化类比：本地开发像在自家厨房练手，油盐酱醋随手就有；部署像去美食广场开店，**一切都是陌生的、干净的，你必须带一张采购清单（requirements.txt），否则连盐都买不到。**

Platform.sh 是一个「平台即服务」（PaaS）：你不用自己买服务器、装系统，把代码推给它，它负责在容器里构建、运行。上手三步：浏览器访问 https://platform.sh 注册账户；安装 Platform.sh CLI（`curl -fsS https://platform.sh/cli/installer | php`，需要 PHP 环境，Windows 上跑不动时可用 Git Bash 或 WSL——补充说明，教材未涉及）；`pip install platformshconfig` 让 Django 在云上读取平台配置。装完 CLI 先 `platform --version` 验证。

### 2.4 requirements.txt：云环境的采购清单（对应教材 20.2）

为什么它是部署必需品？因为云环境是一台**全新的、干净的机器**，它不知道你的项目用过 Django，更不会知道你要 4.2 版还是 5.0 版。你要把所有依赖和精确版本写在清单里，平台构建时照着装：

```bash
# freeze = 冻结当前环境的所有包及版本
(ll_env)learning_log$ pip freeze > requirements.txt
```

生成的内容大致这样（具体以你机器上的实际输出为准）：

```text
asgiref==3.7.2
Django==4.2.10
django-bootstrap5==23.4
platformshconfig==2.4.0
sqlparse==0.4.4
```

两个细节：

1. **`==` 是版本锁**。写 `Django==4.2.10`，云上装的就是 4.2.10，一分不差。没有 `==` 意味着「最新版就行」，半年后平台装到一个大版本更新，项目可能直接崩。锁版本不是洁癖，是纪律。
2. **清单里也会有间接依赖**（如 asgiref、sqlparse 是 Django 带进来的）。这正是 `pip freeze` 的价值：它冻结的是**整棵依赖树**，换一台机器能原样重建。

`pip freeze` 的输出不能照抄，先规范化一遍再提交——大小写、多余空格、`-e` 可编辑安装都是坑：

```python
# pip freeze 的原始输出要先规范化，再比对
RAW = """Django==4.2.10
  django-bootstrap5==23.4
asgiref==3.7.2
# 下面这行是本地可编辑安装，推上云会直接失败
-e git+https://github.com/me/django-bootstrap5#egg=django-bootstrap5
sqlparse==0.4.4
Django==4.2.10
"""


def normalize(text):
    """返回 ({包名小写: 版本}, [被剔除的行])。"""
    packages, dropped = {}, []
    for line in text.splitlines():
        line = line.strip()
        if not line or line.startswith("#"):
            continue
        if line.startswith("-e ") or line.startswith("--"):
            dropped.append(line)
            continue
        if "==" not in line:
            dropped.append(line + "（没锁版本）")
            continue
        name, version = line.split("==", 1)
        packages[name.strip().lower()] = version.strip()
    return packages, dropped


packages, dropped = normalize(RAW)
print("规范化后的依赖（小写键，重复的自动合并）：")
for name, version in sorted(packages.items()):
    print(f"  {name:<20}{version}")
print("\n被剔除的行：")
for line in dropped:
    print("  ", line)
print(f"\n共 {len(packages)} 个依赖；requirements.txt 只该有这些内容。")
```

`-e git+https://...` 这类行必须删掉：它表示「从 git 直接装」，而云上构建环境既没有你的私有仓库凭据、也不该联网拉你的 fork。这段的实跑结果是 4 个依赖（`Django==4.2.10` 出现两次被合并成一条），剔除 1 行 `-e ...`。

还有一类依赖只该在线上装：**gunicorn 和 psycopg2**。gunicorn 是生产级 WSGI 服务器（本地用 `runserver`，线上必须换它）；psycopg2 是 PostgreSQL 的驱动，本地用 SQLite 根本不需要。教材的做法是同目录再建一个 `requirements_remote.txt`：

```text
# Requirements for live project.
gunicorn
psycopg2
```

这两个文件都会在 `.platform.app.yaml` 的 build 钩子里被 `pip install -r`，下一节就能看到。

### 2.5 三个配置文件：一个描述应用，一个描述路由（对应教材 20.2）

这是本单元最需要建立宏观认识的部分。部署时你要告诉平台三件事：**跑什么、怎么跑、从哪进**。对应三个文件：

```text
learning_log/
├── .platform.app.yaml      ← ① 应用清单：用什么运行、依赖什么、构建/部署时执行什么
├── manage.py
└── .platform/              ← 注意：这是个以点开头的隐藏文件夹
    ├── routes.yaml         ← ② 路由：域名怎么指过来
    └── services.yaml       ← ③ 服务：数据库容器怎么开
```

一次完整的请求这样流转：

```text
浏览器访问 https://learning-log-main-xxxx.us-3.platformsh.site/
        │
        ▼
① .platform/routes.yaml ：「这个域名该转给谁？」
        │   "https://{default}/" → upstream: "ll_project:http"
        ▼
② .platform.app.yaml ：「应用怎么启动？」
        │   start: gunicorn ... ll_project.wsgi:application
        ▼
   gunicorn（WSGI 服务器）───► Django（ll_project/wsgi.py）
                          settings.py（platformshconfig 在运行时改写它）
                                    │
                                    ▼
                        ③ PostgreSQL（services.yaml 里定义的 db 容器）
```

**`.platform.app.yaml`（和 manage.py 同级，注意别漏开头的点）**：

```yaml
name: "ll_project"                 # 应用名，routes.yaml 要靠它对上暗号
type: "python:3.12"                # 用什么语言、什么版本（教材写 3.10，以平台文档为准）

relationships:                     # 应用依赖哪些外部服务
    database: "db:postgresql"      # 叫 database 的关系 → 指向 services.yaml 里的 db

web:                               # 暴露到 Web 的配置
    upstream:
        socket_family: unix
    commands:
        start: "gunicorn -w 4 -b unix:$SOCKET ll_project.wsgi:application"   # 启动命令
    locations:
        "/":
            passthru: true         # 动态请求交给 gunicorn/Django
        "/static":
            root: "static"         # 静态文件直接由 Web 服务器发，不麻烦 Django

hooks:                             # 生命周期钩子：构建时和部署时各执行一批命令
    build: |
        pip install --upgrade pip
        pip install -r requirements.txt        # 本地依赖清单
        pip install -r requirements_remote.txt # 线上专用依赖清单
        python manage.py collectstatic --noinput   # ★ 收集静态文件（2.7 节细说）
    deploy: |
        python manage.py migrate               # 每次部署自动应用数据库迁移
```

**`.platform/routes.yaml`**：路由只干一件事——**把域名指到应用**。

```yaml
"https://{default}/":
    type: upstream
    upstream: "ll_project:http"    # ← 这个名字必须和 app.yaml 的 name 一致

"https://www.{default}/":
    type: redirect
    to: "https://{default}/"       # 带 www 的访问跳到主域名
```

**`.platform/services.yaml`**：服务清单，每个服务以独立容器部署。

```yaml
db:
    type: postgresql:16            # 开一个 PostgreSQL 容器（版本以平台文档为准）
    disk: 1024
```

app.yaml 的 `relationships` 说「我需要一个叫 database 的数据库」，services.yaml 说「我开一个叫 db 的 PostgreSQL」，两边用 `"db:postgresql"` 这个暗号对上；routes.yaml 的 `upstream: "ll_project:http"` 则要和 app.yaml 的 `name` 一致。**两处暗号对不上，部署直接失败。**

「对暗号」这件事不需要平台也能查——三个 yaml 都是文本，正则一比就知道：

```python
# 三个 yaml 的「暗号」对不对得上，用字符串就能查
import re

APP = 'name: "ll_project"\nrelationships:\n    database: "db:postgresql"\n'
ROUTES = '"https://{default}/":\n    upstream: "ll_project:http"\n'
SERVICES = "db:\n    type: postgresql:16\n"


def audit(app_yaml, routes_yaml, services_yaml):
    """三处暗号：应用名 ↔ upstream、关系名 ↔ 服务名、关系类型 ↔ 服务类型。"""
    app_name = re.search(r'name:\s*"([^"]+)"', app_yaml)
    upstream = re.search(r'upstream:\s*"([^":]+)', routes_yaml)
    relation = re.search(r'database:\s*"([^":]+):([^"]+)"', app_yaml)
    service = re.search(r"^(\w+):", services_yaml, re.M)
    kind = re.search(r"type:\s*(\w+)", services_yaml)
    return [
        ("应用名 ↔ routes.upstream",
         app_name.group(1) == upstream.group(1),
         f"{app_name.group(1)} / {upstream.group(1)}"),
        ("关系名 ↔ services 服务名",
         relation.group(1) == service.group(1),
         f"{relation.group(1)} / {service.group(1)}"),
        ("关系类型 ↔ services 服务类型",
         relation.group(2) == kind.group(1),
         f"{relation.group(2)} / {kind.group(1)}"),
    ]


for label, ok, detail in audit(APP, ROUTES, SERVICES):
    print(f"[{'✓' if ok else '✗'}] {label}：{detail}")

print("\n改坏一处试试（把 routes 的 upstream 改成 app）：")
bad = audit(APP, ROUTES.replace("ll_project:http", "app:http"), SERVICES)
for label, ok, detail in bad:
    print(f"[{'✓' if ok else '✗'}] {label}：{detail}")
print("第一项立刻变 ✗ —— 部署会报「找不到应用 app」，但本地 runserver 一切正常。")
```

### 2.6 platformshconfig：一份代码怎么知道自己在哪（对应教材 20.2）

现在到本单元**最烧脑**的地方。难点先说在前面：**settings.py 只有一份，但它要在两个完全不同的环境里给出两套完全不同的配置。** 就像同一个人，在家穿拖鞋、在工地戴安全帽——他没变，是环境变了，他自己能感觉到。

Django 的感觉器官就是环境变量。Platform.sh 运行你的应用时，会往环境变量里注入一大堆信息，其中最关键的一个叫 `PLATFORM_APPLICATION`——**只要这个变量存在，就说明代码正跑在 Platform.sh 的云上**。platformshconfig 这个库，本质就是把这一大堆环境变量（有的还是 base64 编码的 JSON）包装成几个好用的方法。

教材的做法是在 **settings.py 的末尾**追加一段（导入语句没放在文件开头，而是和「远程专属设置」放在一起，方便一眼看出哪些配置是云上才生效的）：

```python
# settings.py —— 文件末尾追加的片段（完整文件以上方已有配置为基础）

# Platform.sh settings.
from platformshconfig import Config

config = Config()
if config.is_valid_platform():                    # ① 在云上才为 True（底层就是查 PLATFORM_APPLICATION）
    ALLOWED_HOSTS.append('.platformsh.site')     # ② 放行平台域名（见 2.7 第一个坑）
    DEBUG = False                                # ③ 云上必须关调试模式

    if config.appDir:                            # ④ 应用在云上的绝对路径
        STATIC_ROOT = Path(config.appDir) / 'static'
    if config.projectEntropy:                    # ⑤ 平台为项目生成的随机串，拿来当 SECRET_KEY
        SECRET_KEY = config.projectEntropy

    if not config.in_build():                    # ⑥ 构建阶段连不上数据库，只有运行期才配
        db_settings = config.credentials('database')   # ⑦ 读 relationships 里 database 的连接信息
        DATABASES = {
            'default': {
                'ENGINE': 'django.db.backends.postgresql',
                'NAME': db_settings['path'],
                'USER': db_settings['username'],
                'PASSWORD': db_settings['password'],
                'HOST': db_settings['host'],
                'PORT': db_settings['port'],
            },
        }
```

★ **为什么难**：你要同时记住「两份配置」和「一个开关」。建议这样建心智模型——把 `if config.is_valid_platform():` 想象成一道**旋转门**：代码走到这儿，本地身份的人直接走旁边的小门（沿用上面写的 SQLite 配置），云上身份的人转进门里，换上 PostgreSQL 的行头。门后面每一行，都是「仅云上生效」的覆写。

顺带回答一个可能的疑问：**密钥怎么办？** `SECRET_KEY` 写进代码、传上公开仓库，别人理论上能拿着它伪造会话 cookie。Platform.sh 的答案是 `projectEntropy`——平台给每个项目生成一个足够随机的字符串，通过环境变量提供，代码里根本不出现密钥本身。这就是「配置与代码分离」在部署层的落地。

`Config` 看起来很神奇，其实它只是把一堆环境变量包装成方法。用 30 行替身就能把「本地 / 云上运行期 / 云上构建期」三种状态都跑一遍：

```python
# platformshconfig 的替身：它只是把环境变量包装成好用的方法
import json


class FakeConfig:
    """真的 Config 读的是环境变量与 base64 的 PLATFORM_RELATIONSHIPS。"""

    def __init__(self, env):
        self.env = env

    def is_valid_platform(self):
        return "PLATFORM_APPLICATION" in self.env     # ★ 唯一的判据

    @property
    def appDir(self):
        return self.env.get("PLATFORM_APP_DIR")

    @property
    def projectEntropy(self):
        return self.env.get("PLATFORM_PROJECT_ENTROPY")

    def in_build(self):
        return self.env.get("PLATFORM_PHASE") == "build"

    def credentials(self, name):
        raw = self.env.get("PLATFORM_RELATIONSHIPS", "{}")
        return json.loads(raw).get(name)


def build_settings(env):
    """这就是 settings.py 末尾那段：本地走小门，云上换行头。"""
    settings = {"DEBUG": True, "ENGINE": "sqlite3", "ALLOWED_HOSTS": ["localhost"],
                "SECRET_KEY": "写死的开发密钥", "STATIC_ROOT": None}
    config = FakeConfig(env)
    if config.is_valid_platform():
        settings["DEBUG"] = False
        settings["ALLOWED_HOSTS"].append(".platformsh.site")
        settings["SECRET_KEY"] = config.projectEntropy
        settings["STATIC_ROOT"] = f"{config.appDir}/static"
        if not config.in_build():
            db = config.credentials("database")
            settings["ENGINE"] = f"postgresql://{db['username']}@{db['host']}"
        else:
            settings["ENGINE"] = "（构建阶段不连数据库）"
    return settings


CLOUD_ENV = {
    "PLATFORM_APPLICATION": "eyJ...", "PLATFORM_APP_DIR": "/app",
    "PLATFORM_PROJECT_ENTROPY": "a1b2c3d4", "PLATFORM_PHASE": "runtime",
    "PLATFORM_RELATIONSHIPS": json.dumps(
        {"database": {"username": "main", "host": "postgresql.internal"}}),
}

for label, env in [("本地（没有 PLATFORM_APPLICATION）", {}),
                   ("云上运行期", CLOUD_ENV),
                   ("云上构建期", {**CLOUD_ENV, "PLATFORM_PHASE": "build"})]:
    print(f"--- {label} ---")
    for key, value in build_settings(env).items():
        print(f"  {key:<14}= {value}")
```

三段输出最关键的区别在 `ENGINE`：本地是 `sqlite3`、云上运行期是 `postgresql://main@postgresql.internal`、云上**构建期**是「（构建阶段不连数据库）」。最后一段正对应教材那句 `if not config.in_build():`——**`collectstatic` 和 `migrate` 跑在构建阶段，那时数据库容器还没起来**，此刻去读 `credentials()` 只会拿到空值。

### 2.7 三大部署坑：ALLOWED_HOSTS、collectstatic、DEBUG（对应教材 20.2）

**坑一：ALLOWED_HOSTS 不改，线上直接 400。** Django 会检查每个请求的 `Host` 头在不在 `ALLOWED_HOSTS` 名单里，不在就返回 `400 Bad Request`——**连你的视图代码都不会执行**。默认的 `ALLOWED_HOSTS = []` 只放行 `localhost`，线上域名 100% 被拒。修复就是 2.6 里那行 `ALLOWED_HOSTS.append('.platformsh.site')`（开头带点表示「匹配所有子域名」，你的项目域名类似 `xxx.us-3.platformsh.site`）。

**坑二：`DEBUG = False` 之后，不 collectstatic 就是一个白脸页面。** `DEBUG = True` 时开发服务器会顺带帮你发静态文件；一旦关掉，静态文件必须由真正的 Web 服务器发。所以 app.yaml 的 build 钩子里有 `python manage.py collectstatic --noinput`：它把**各个应用的 `static/` 目录全部汇总到 `STATIC_ROOT`**，再由 routes 里 `/static` 那条规则直接发文件。忘了这一步，HTML 能出来但 CSS/JS 全丢，页面就是个没化妆的素颜。

「谁在发这个 CSS」决定了页面有没有样式，把四种组合列出来就一目了然：

```python
# DEBUG 与静态文件：谁在发 CSS，决定了页面有没有样式
def serve_static(url, debug, static_root_files):
    """返回 (谁负责发这个文件, 结果)。"""
    if not url.startswith("/static/"):
        return "Django 视图", "200"
    if debug:
        return "Django 开发服务器（DEBUG=True 才代发）", "200"
    name = url[len("/static/"):]
    if name in static_root_files:
        return "Web 服务器直接读 STATIC_ROOT", "200"
    return "Web 服务器", "404（没有样式，白脸页面）"


STATIC_ROOT = {"css/styles.css", "css/login.css", "js/app.js"}

cases = [
    ("/static/css/styles.css", True, STATIC_ROOT),
    ("/static/css/styles.css", False, STATIC_ROOT),
    ("/static/css/styles.css", False, set()),          # 忘了 collectstatic
    ("/topics/", False, STATIC_ROOT),
]
for url, debug, files in cases:
    who, result = serve_static(url, debug, files)
    print(f"{url:<24} DEBUG={debug!s:<6}{result}")
    print(f"   发送方：{who}")

print("\n★ 本地永远正常（DEBUG=True 兜底），线上才会暴露——这就是部署坑的典型形态。")
```

注意第 3 行：同样的网址、同样的 `DEBUG=False`，只因为 `STATIC_ROOT` 里没有那个文件，结果就从 `200` 变成 `404`。**这正是「页面能打开但没有样式」的全部原因**——HTML 由 Django 生成（200），CSS 由 Web 服务器读文件（404），两件事彻底解耦了。

**坑三：把本地数据库和虚拟环境传上云。** 必须写 `.gitignore`：

```text
ll_env/            # 虚拟环境：几百 MB，平台要自己建
__pycache__/       # Python 的编译缓存
*.sqlite3          # 本地数据库：平台上用 PostgreSQL，带上只会混淆视听
```

macOS 用户再加一行 `.DS_Store`。这三个坑是部署新手踩坑率最高的前三名。

### 2.8 定制错误页面与「继续开发」（对应教材 20.2）

线上出了 404（页面不存在）或 500（服务器内部错误），用户看到的不该是 Django 那个灰白的调试页，而应该是一个「说人话」的页面。做法是建两个模板，放到**项目级 templates 目录**：

```html
<!-- templates/404.html -->
{% extends "learning_logs/base.html" %}

{% block page_header %}
<h2>你访问的页面不存在。(404)</h2>
{% endblock page_header %}
```

500.html 做法完全类似（把文字换成「服务器内部错误」即可）。光放文件还不够，Django 得知道去**项目级** templates 目录找——修改 settings.py 的 `TEMPLATES`，把 `DIRS` 从空列表改成 `[BASE_DIR / 'templates']`。Django 查找模板的顺序是：先 `DIRS`（项目级），再各应用的 `templates/`，所以放项目级最稳妥。

**如果想更精细地控制错误行为**（比如 404 时也要查数据库、按不同错误码返回不同页面），可以在 `urls.py` 里用 `handler404` / `handler500` 指定专门的视图函数：

```python
# ll_project/urls.py —— 可选项：定制错误处理器
handler404 = 'learning_logs.views.my_404'    # 访问不存在的页面时调用这个视图
handler500 = 'learning_logs.views.my_500'    # 服务器内部错误时调用这个视图
```

不写这两个赋值时，Django 的默认行为就是「找 `templates/404.html` / `500.html`」，对大多数项目已经够用。**注意：定制错误页只在 `DEBUG = False` 时生效**——本地默认开着调试模式，看到的仍是详细报错页（练习 20-5 会做本地验证）。

「找 `404.html`」这个动作的查找顺序值得单独跑一遍，因为它解释了一个高频困惑——**为什么我把 404.html 放在 app 的 templates 下却没用**：

```python
# 404/500 模板去哪找：DIRS 先，应用目录后
# 用字符串模拟两处目录里各有哪些模板文件
EXISTING = {
    "templates/404.html",                        # 项目级 DIRS 里
    "learning_logs/templates/learning_logs/topics.html",
}


def find_error_template(code, dirs, app_dirs):
    """按 Django 的顺序找：先 DIRS，再各应用的 templates/。"""
    name = f"{code}.html"
    for base in list(dirs) + list(app_dirs):
        candidate = f"{base}/{name}"
        if candidate in EXISTING:
            return candidate
    return None


DIRS = ["templates"]
APP_DIRS = ["learning_logs/templates", "accounts/templates"]

for code in (404, 500):
    found = find_error_template(code, DIRS, APP_DIRS)
    print(f"{code}: {found or '没找到 -> 用 Django 自带的默认错误页'}")

print("\n★ 两个前提条件，缺一个定制页都不生效：")
print("  1. settings.py 的 TEMPLATES['DIRS'] = [BASE_DIR / 'templates']")
print("  2. DEBUG = False —— 本地默认 True，看到的永远是黄色调试页")

print("\n想更精细地控制（比如 404 时还要查库）：")
print("  ll_project/urls.py 里写 handler404 = 'learning_logs.views.my_404'")
```

输出里 404 找到了 `templates/404.html`，500 显示「没找到」——因为那个假项目只放了 404。**这就是为什么两个页面必须成对写**：只做一个，另一个就退回 Django 的默认灰白页，线上看起来像「没做完」。

**「继续开发」的流程**是部署之后最重要的工作流。首次上线只是开始，之后每次改 bug、加功能，都是这一个循环：

```text
① 本地改代码 → ② git add .（有新文件才需要）→ ③ git commit -am "说明"
        ↓                                                          ↓
⑥ 访问线上 URL 验证 ← ⑤ platform push（平台自动 build + deploy）← ④
```

```bash
(ll_env)learning_log$ git add .                        # 有新文件/迁移文件时才需要
(ll_env)learning_log$ git commit -am "Added custom 404 and 500 error pages."
(ll_env)learning_log$ platform push                    # 推送并触发部署
(ll_env)learning_log$ platform url                     # 查看线上项目的网址
```

**你的代码库里同时住着两个环境，git 提交是本地唯一的真相来源，platform push 是把真相同步到云上的仪式。** 项目不想要了，删除分两步：`platform project:delete` 删除平台上的项目（交互式确认），再 `git remote remove platform` 删掉本地 git 里指向平台的 remote——线上删了，本地仓库还留着。

### 2.9 上线之后出问题怎么办：部署故障排除（教材附录 E）

本地一切正常，推到线上就白屏——这是部署的常态，不是你的代码烂。差别在于：**线上你看不到 traceback**。所以排查的第一件事不是改代码，而是**把日志拿出来**。

#### 2.9.1 先学会看日志

```bash
# Platform.sh 看最近的应用日志
platform log -p <项目ID> --lines 200

# 其他平台的等价操作都差不多：找「Logs」面板，或用各自的 CLI tail
```

日志里真正有用的是 **Traceback 的最后几行**——和本地报错一模一样，读法完全一致（见单元 11 的 2.4）。
如果日志里只有一行 `500 Internal Server Error` 而没有 traceback，说明 `DEBUG=False` 时 Django 把错误**只写进日志、不发到页面**——这正是"线上白屏、本地正常"的原因。

> 一条硬规矩：**线上永远不要靠 `DEBUG=True` 来"看一眼报错"**。那会把数据库配置、密钥全暴露给访问者。要看报错就看日志。

日志动辄几百行，真正要找的只有 traceback 的最后一行。写个小工具把这一行挑出来：

```python
# log_extract.py —— 从一坨日志里挑出「该拿去搜的那一行」
def last_error(log_text):
    """返回日志里最后一条 traceback 的**最后一行**——那才是该拿去搜的一行。

    不能简单找「含 Error 的最后一行」：日志里常有
    `Internal Server Error: /topics/1/` 这种 HTTP 状态行，它只是说"挂了"，
    没说为什么挂。真正的原因在 Traceback 块的**最后一行**。
    """
    lines = log_text.splitlines()
    start = None
    for i, ln in enumerate(lines):
        if ln.strip().startswith("Traceback"):
            start = i                                  # 取最后一个 Traceback 块
    if start is None:                                  # 没有 traceback 就退回模糊找
        for ln in reversed(lines):
            if "Error" in ln or "Exception" in ln:
                return ln.strip()
        return None
    # 块内逐行：跳过 File "..." 栈帧行，遇到 [web] 这类新日志段就停，
    # 剩下的最后一行就是异常行（注意它可能是顶格的，不能靠缩进来判断）
    hit = None
    for j in range(start + 1, len(lines)):
        s = lines[j].strip()
        if not s:
            continue
        if s.startswith("["):                          # 新的日志段落，traceback 结束
            break
        if s.startswith('File "'):                     # 栈帧行，不是原因
            continue
        hit = s
    return hit


def search_query(err_line):
    """把报错行变成搜索词：去掉自己的路径和变量名，只留异常类型 + 关键信息。"""
    import re
    line = err_line.split(": ", 1)[-1] if ": " in err_line else err_line
    line = re.sub(r"File \"[^\"]+\"", 'File "..."', line)   # 抹掉本机路径
    line = re.sub(r"'[^']*'", "'...'", line)                # 抹掉具体的值
    return line.strip()


SAMPLE = """
[web] Starting gunicorn 21.2.0
[web] Listening at: http://0.0.0.0:8888
Internal Server Error: /topics/1/
Traceback (most recent call last):
  File "/app/learning_logs/views.py", line 42, in topic
    entry = topic.entry_set.get(id=entry_id)
  File "/app/.venv/lib/python3.12/site-packages/django/db/models/query.py", line 637, in get
    raise self.model.DoesNotExist(
learning_logs.models.Entry.DoesNotExist: Entry matching query does not exist.
[web] 10.0.3.7 - - "GET /topics/1/ HTTP/1.1" 500
"""

err = last_error(SAMPLE)
print("报错行：", err)
print("该搜的是：", search_query(err))
print()
print("★ 看清楚：日志里唯一的线索是最后那行 DoesNotExist，")
print("  而原因在它上面两行——get() 没找到匹配的记录，要换成 get_object_or_404 或先 exists() 判断。")
```

#### 2.9.2 症状对照表

| 现象 | 最可能的原因 | 怎么确认 / 怎么修 |
|---|---|---|
| 打开就是 `400 Bad Request` | `ALLOWED_HOSTS` 不含当前域名 | 看日志有没有 `Invalid HTTP_HOST`；补上域名（见 2.6） |
| 页面能开，**样式全丢**（素颜白脸） | 没跑 `collectstatic`，或 Web 服务器没配 `/static` | 直接访问 `/static/css/styles.css`，404 就是没收集到 |
| 页面 500，日志有 `DisallowedHost` | 同上，只是触发点不同 | 同上 |
| 500，日志有 `OperationalError: no such table` / `relation does not exist` | 线上没跑 `migrate` | 部署钩子或 SSH 里补 `python manage.py migrate` |
| 500，日志有 `ModuleNotFoundError: No module named 'xxx'` | `requirements.txt` 漏了这个包 | 本地 `pip freeze > requirements.txt` 重新生成（见 2.4） |
| 提交表单 403，提示 CSRF 失败 | `CSRF_TRUSTED_ORIGINS` 没配，或用了 http 访问 https 站点 | 加上 `CSRF_TRUSTED_ORIGINS = ['https://你的域名']` |
| 改了代码推上去，**线上没变化** | 平台没重新构建，或浏览器缓存了旧静态文件 | 看部署日志的 build 步骤有没有跑；静态文件用指纹名（见示例 13） |
| 静态文件 404，但 `collectstatic` 明明跑了 | `STATIC_ROOT` 与 Web 服务器读的目录不是同一个 | 打印 `STATIC_ROOT` 的实际路径对比服务器配置 |

**八条里有五条是配置问题，不是代码问题。** 部署排错的绝大部分时间应该花在"两边配置是否一致"上。

把上面这张表写成脚本，就是一份**上线前的配置体检**：

```python
# deploy_doctor.py —— 上线前跑一遍，把配置类问题一次性挑出来
def check_config(cfg, host, static_ready):
    """cfg 是 settings 里的关键项；返回 [(级别, 问题, 怎么改)]。"""
    issues = []
    if cfg.get("DEBUG"):
        issues.append(("严重", "DEBUG 还是 True，报错会连同密钥一起显示在页面上",
                       "线上改成 False"))
        # DEBUG=True 时 Django 自动放行 localhost / 127.0.0.1 / [::1]，
        # 所以本地怎么访问都不会 400——这个坑只有到了线上才暴露
        issues.append(("提示", "DEBUG=True 时 ALLOWED_HOSTS 被自动放行，本地试不出来",
                       "把 ALLOWED_HOSTS 的问题留到线上前单独确认"))
    elif not any(host == h or (h.startswith(".") and host.endswith(h[1:]))
                 for h in cfg.get("ALLOWED_HOSTS", [])):
        issues.append(("严重", f"ALLOWED_HOSTS 不含 {host}，访问会被 400 拦下",
                       f"ALLOWED_HOSTS.append('{host}')"))
    if not cfg.get("STATIC_ROOT"):
        issues.append(("警告", "没设 STATIC_ROOT，collectstatic 不知道往哪汇总",
                       "STATIC_ROOT = BASE_DIR / 'staticfiles'"))
    elif not static_ready:
        issues.append(("警告", "STATIC_ROOT 是空的，线上会变成没样式的白脸页面",
                       "python manage.py collectstatic --noinput"))
    if cfg.get("SECRET_KEY", "").startswith("django-insecure"):
        issues.append(("严重", "还在用开发用的 SECRET_KEY，会话和签名可被伪造",
                       "从环境变量读一个随机长字符串"))
    return issues


def report(issues):
    if not issues:

        return True
    for level, what, how in issues:
        print(f"[{level}] {what}\n      改法：{how}\n")
    return not any(lv == "严重" for lv, _, _ in issues)


# 三种典型现场
cases = [
    ("本地开发", {"DEBUG": True, "ALLOWED_HOSTS": [], "SECRET_KEY": "django-insecure-xxx"},
     "127.0.0.1:8000", False),
    ("刚推上线（忘了改配置）",
     {"DEBUG": True, "ALLOWED_HOSTS": [], "SECRET_KEY": "django-insecure-xxx"},

     "abc.us-3.platformsh.site", True),
]

    print(f"── {name} ──")
    ok = report(check_config(cfg, host, ready))
    print(f"结论：{'可以上线' if ok else '先修完再上线'}\n")

print("★ 注意第二种：本地全绿，上线全红——差别只在于配置，不在代码。")
```

#### 2.9.3 用 WhiteNoise 让 Django 自己发静态文件

如果你的平台配 Web 服务器路由（routes）比较麻烦，有个省事得多的办法：装 `whitenoise`，让 Django 应用**自己**发静态文件。

```bash
pip install whitenoise
pip freeze > requirements.txt
```

```python
# settings.py —— 三处改动
MIDDLEWARE = [
    "django.middleware.security.SecurityMiddleware",
    "whitenoise.middleware.WhiteNoiseMiddleware",   # ① 紧跟 SecurityMiddleware，在其他中间件之前
    # ... 其余中间件
]

STATIC_ROOT = BASE_DIR / "staticfiles"              # ② collectstatic 汇总到这里

STORAGES = {                                        # ③ Django 4.2+ 的写法
    "default": {"BACKEND": "django.core.files.storage.FileSystemStorage"},
    "staticfiles": {
        "BACKEND": "whitenoise.storage.CompressedManifestStaticFilesStorage",
    },
}
```

> Django 4.2 之前没有 `STORAGES`，老写法是单独一行
> `STATICFILES_STORAGE = "whitenoise.storage.CompressedManifestStaticFilesStorage"`。

第 ③ 步那个存储后端会做两件事：**压缩**（gzip/brotli）和**给文件名加内容哈希**（`base.a4ef2389.css`）。有了哈希名就可以放心让浏览器永久缓存，文件内容一变名字就变，缓存自动失效——这就是示例 13 说的"静态资源指纹"。

**怎么确认装好了**：本地把 `DEBUG` 改成 `False`，跑 `collectstatic` 再 `runserver`，静态文件照样能加载就是成功了：

```bash
python manage.py collectstatic
# settings.py: DEBUG = False
python manage.py runserver
```

这一步能在**推上云之前**就把"线上没样式"这个最常见的坑消灭掉。

#### 2.9.4 四步排查法与「先回滚」

线上出问题时按顺序来，不要上来就改代码：

1. **看日志**，拿到真正的 traceback（没有 traceback 就先把日志级别调详细）
2. **本地用线上配置复现**：`DEBUG=False` + 线上同样的环境变量，看能不能重现
3. **对比两边差异**：Python 版本、包版本、环境变量、`ALLOWED_HOSTS`、数据库是不是同一个
4. **只改一处就重新部署一次**，确认这一处有没有效果——一次改五处等于没改

如果站点已经不能对外服务，**先把服务恢复，再慢慢修**：

```bash
git log --oneline -5          # 找到上一个能用的提交
git revert <出问题的提交>      # 生成一个"撤销"提交（不要 reset，团队协作要保留历史）
git push                      # 重新部署，服务先恢复
```

回滚之后再从容排查。这跟单元 0 的 Git 是同一套思路：**代码有版本，就有退路**。

### 示例 2：给 requirements.txt 做入职体检（requirements_tools.py）

```python
# requirements_tools.py —— 检查依赖清单：版本锁、重复项、关键包是否齐全
from pathlib import Path

# 云端跑起来必不可少的包（gunicorn/psycopg2 在 requirements_remote.txt 里）
NEEDED = {"django", "django-bootstrap5", "gunicorn", "psycopg2", "platformshconfig"}

REQUIREMENTS_TXT = """asgiref==3.7.2
Django==4.2.10
django-bootstrap5==23.4
platformshconfig==2.4.0
sqlparse==0.4.4
"""

REQUIREMENTS_REMOTE_TXT = """# Requirements for live project.
gunicorn
psycopg2
"""


def parse(text, source):
    """解析一份依赖清单，返回 {包名: 版本} 和问题列表。"""
    packages, problems = {}, []
    for lineno, raw in enumerate(text.splitlines(), 1):
        line = raw.strip()
        if not line or line.startswith("#"):
            continue
        if "==" not in line:
            problems.append(f"{source} 第{lineno}行「{line}」没锁版本，云端可能装到不兼容的新版")
            continue
        name, version = line.split("==", 1)
        name = name.strip().lower()
        if name in packages:
            problems.append(f"{source} 第{lineno}行「{name}」重复了")
        packages[name] = version.strip()
    return packages, problems


def check():
    packages, problems = parse(REQUIREMENTS_TXT, "requirements.txt")
    remote_packages, _ = parse(REQUIREMENTS_REMOTE_TXT, "requirements_remote.txt")
    print(f"共解析出 {len(packages)} 个本地依赖、{len(remote_packages)} 个线上依赖")

    missing = NEEDED - set(packages) - set(remote_packages)
    if missing:
        problems.append(f"缺少部署必需包：{sorted(missing)}")
    if problems:
        print(f"发现 {len(problems)} 个问题：")
        for item in problems:
            print(f"  [问题] {item}")
    else:
        print("体检通过：版本都已锁定，部署必需包齐全。")

    # 反面教材：requests 没锁版本 + Django 重复出现
    _, bad = parse("requests\nDjango==4.2\nDjango==5.0\n", "坏例子.txt")
    for item in bad:
        print(f"  [反面教材] {item}")


if __name__ == "__main__":
    check()
```

### 示例 3：400 Bad Request 是怎么来的（host_check.py）

用 20 行复现 Django 的 `ALLOWED_HOSTS` 校验逻辑，你会立刻明白为什么线上域名被拒之门外。

```python
# host_check.py —— 复现 Django 的主机校验，看懂 400 从哪来

def is_host_allowed(host, allowed_hosts):
    """Django 校验 Host 的核心规则（教学简化版）。"""
    if "*" in allowed_hosts:
        return True
    host = host.split(":")[0]          # 去掉端口号：localhost:8000 → localhost
    for pattern in allowed_hosts:
        if pattern == host:
            return True
        if pattern.startswith(".") and host.endswith(pattern):
            return True                # ".platformsh.site" 匹配所有子域名
    return False


if __name__ == "__main__":
    local_only = ["localhost", "127.0.0.1"]
    online = "learning-log-main-abc123.us-3.platformsh.site"
    print("场景一：ALLOWED_HOSTS =", local_only)
    print("  本地域名 ->", "200 OK" if is_host_allowed("localhost:8000", local_only) else "400")
    print("  线上域名 ->", "200 OK" if is_host_allowed(online, local_only) else "400 Bad Request（DisallowedHost）")

    # 场景二：加上 .platformsh.site（对应 settings.py 里 append 的那行）
    fixed = local_only + [".platformsh.site"]
    print("\n场景二：ALLOWED_HOSTS =", fixed)
    print("  线上域名 ->", "200 OK" if is_host_allowed(online, fixed) else "400 Bad Request")
```

### 示例 4：collectstatic 到底在搬什么（static_collector.py）

```python
# static_collector.py —— 用 30 行代码看懂 collectstatic 的核心动作
from pathlib import Path
import shutil


def collect_static(app_names, project_root, static_root):
    """模拟 python manage.py collectstatic：
    把每个应用的 static/ 目录，原样汇总到 STATIC_ROOT。
    """
    if static_root.exists():
        shutil.rmtree(static_root)
    static_root.mkdir(parents=True)
    copied = []
    for app_name in app_names:
        source = project_root / app_name / "static"
        if not source.exists():
            continue
        for file in sorted(source.rglob("*")):
            if file.is_file():
                dest = static_root / file.relative_to(source)
                dest.parent.mkdir(parents=True, exist_ok=True)
                shutil.copy2(file, dest)
                copied.append(dest)
    return copied


if __name__ == "__main__":
    root = Path("data/learning_log")
    # 造两个应用，各带自己的 static/ 目录
    (root / "learning_logs/static/css").mkdir(parents=True, exist_ok=True)
    (root / "accounts/static/css").mkdir(parents=True, exist_ok=True)
    (root / "learning_logs/static/css/styles.css").write_text(
        ".jumbotron { padding: 2rem; }", encoding="utf-8")
    (root / "accounts/static/css/login.css").write_text(
        ".form-label { font-weight: bold; }", encoding="utf-8")

    copied = collect_static(["learning_logs", "accounts"], root, root / "static")
    print(f"共收集 {len(copied)} 个静态文件到 STATIC_ROOT：")
    for path in copied:
        print("  static/" + str(path.relative_to(root / "static")).replace("\\", "/"))
    # 跑完可以删掉 data/ 目录
```

### 示例 6：上线前 8 道闸门 + 静态文件清单（deploy_gate.py）

示例 5 的清单只查「文件在不在」。真正 push 之前，你还想确认**文件内容对不对**：依赖锁没锁版本、两处暗号是否对齐、`ALLOWED_HOSTS` 有没有放行域名、错误页是不是成对、静态文件到底会被搬几个。这个示例把这三类检查（文件存在 / 内容正确 / 产物清单）压进一个脚本，**并且故意留一个缺口**——让你看见 `✗` 长什么样，而不是一路 `✓` 就以为万事大吉。

```python
# deploy_gate.py —— 上线前 8 道闸门 + 静态文件清单，全用标准库
import os
import re
from pathlib import Path

ROOT = Path("data/ll_project")


def make_demo_project(root=ROOT):
    """造一个「差两项」的假项目，这样能同时看到 ✓ 和 ✗。"""
    files = {
        "requirements.txt": "asgiref==3.7.2\nDjango==4.2.10\ndjango-bootstrap5==23.4\n",
        "requirements_remote.txt": "# 线上专用\ngunicorn==21.2.0\npsycopg2==2.9.9\n",
        ".platform.app.yaml": 'name: "ll_project"\nrelationships:\n    database: "db:postgresql"\n'
                              'hooks:\n    build: python manage.py collectstatic --noinput\n',
        ".platform/routes.yaml": '"https://{default}/":\n    upstream: "ll_project:http"\n',
        ".platform/services.yaml": "db:\n    type: postgresql:16\n",
        ".gitignore": "ll_env/\n__pycache__/\n*.sqlite3\n",
        "ll_project/settings.py": "ALLOWED_HOSTS = ['localhost', '.platformsh.site']\n"
                                  "DEBUG = False\n",
        "learning_logs/static/css/styles.css": ".jumbotron { padding: 2rem; }\n",
        "accounts/static/css/login.css": ".form-label { font-weight: bold; }\n",
        "templates/404.html": "404\n",
        # ★ 故意不写 templates/500.html，看第 7 项能不能抓出来
    }
    for rel, text in files.items():
        path = root / rel
        path.parent.mkdir(parents=True, exist_ok=True)
        path.write_text(text, encoding="utf-8")


def read(path):
    try:
        return path.read_text(encoding="utf-8")
    except OSError:
        return ""


def unpinned(text):
    return [ln.strip() for ln in text.splitlines()
            if ln.strip() and not ln.startswith("#") and "==" not in ln]


def checks(root=ROOT, env=None):
    """八道闸门，每项返回 (是否通过, 说明)。顺序就是踩坑频率的顺序。"""
    env = os.environ if env is None else env
    app_yaml = read(root / ".platform.app.yaml")
    routes = read(root / ".platform/routes.yaml")
    services = read(root / ".platform/services.yaml")
    settings = read(root / "ll_project/settings.py")
    gitignore = read(root / ".gitignore")
    app_name = re.search(r'name:\s*"([^"]+)"', app_yaml)
    upstream = re.search(r'upstream:\s*"([^":]+)', routes)
    return [
        ("依赖清单锁版本", not unpinned(read(root / "requirements.txt"))
         and (root / "requirements.txt").exists()),
        ("线上依赖齐全", all(pkg in read(root / "requirements_remote.txt")
                            for pkg in ("gunicorn", "psycopg2"))),
        ("路由暗号对齐", bool(app_name and upstream)
         and app_name.group(1) == upstream.group(1)),
        ("数据库服务存在", "postgresql" in services and "db:" in services),
        ("忽略清单到位", "*.sqlite3" in gitignore and "ll_env/" in gitignore),
        ("云上放行域名且关调试", ".platformsh.site" in settings and "DEBUG = False" in settings),
        ("错误页成对", (root / "templates/404.html").exists()
         and (root / "templates/500.html").exists()),
        ("静态文件已收集", "collectstatic" in app_yaml),
    ]


def static_inventory(root=ROOT):
    """pathlib 遍历：collectstatic 到底会把哪些文件搬到 STATIC_ROOT。"""
    found = []
    for app_dir in sorted(root.iterdir()):
        static = app_dir / "static"
        if static.is_dir():
            for file in sorted(static.rglob("*")):
                if file.is_file():
                    found.append(str(file.relative_to(root)).replace("\\", "/"))
    return found


def allowed_hosts_from_env(env):
    """ALLOWED_HOSTS 不该写死：线上域名从环境变量来，本地给默认值。"""
    raw = env.get("DJANGO_ALLOWED_HOSTS", "localhost,127.0.0.1")
    return [host.strip() for host in raw.split(",") if host.strip()]


make_demo_project()
results = checks()
print("=== 部署前自查（8 项）===")
for index, (label, ok) in enumerate(results, 1):
    print(f"  [{index}] [{'✓' if ok else '✗'}] {label}")
failed = [label for label, ok in results if not ok]
passed = len(results) - len(failed)
if failed:
    print(f"\n通过 {passed}/{len(results)} 项；未通过：{'、'.join(failed)}")
else:
    print(f"\n通过 {passed}/{len(results)} 项，可以 platform push。")

print("\n=== 静态文件清单（collectstatic 的搬运目标）===")
for rel in static_inventory():
    print("  ", rel)
print(f"  共 {len(static_inventory())} 个文件 -> STATIC_ROOT")

print("\n=== ALLOWED_HOSTS 从环境变量来，不写死 ===")
print("  本地：", allowed_hosts_from_env({}))
print("  线上：", allowed_hosts_from_env(
    {"DJANGO_ALLOWED_HOSTS": "learning-log-abc.us-3.platformsh.site,.platformsh.site"}))

import shutil
shutil.rmtree("data", ignore_errors=True)      # 演示完删掉
```

三条解读：

1. **检查要分三层，只查「文件在不在」是不够的**：`requirements.txt` 存在但没锁版本、`settings.py` 存在但没放行域名、`routes.yaml` 存在但 `upstream` 写错——这三种「文件齐全、内容不对」的情况，示例 5 的清单一个都抓不到。第 1/3/6 项就是专门补这个洞。
2. **`static_inventory()` 让你在 push 之前就知道网上会有几个 CSS**：它遍历每个应用的 `static/` 目录，把相对路径打出来。**线上样式丢失时，第一个该问的就是「这个数是不是 0」**；如果清单是 2 个、线上还是白脸，问题在 `/static` 路由或 `STATIC_ROOT`，不在文件本身。
3. **把 `templates/500.html` 补上会怎样**：第 7 项立刻从 `✗` 变 `✓`，汇总行变成「通过 8/8 项，可以 platform push」。反过来，把 `requirements_remote.txt` 里的 `psycopg2` 删掉再跑，第 2 项会变 `✗` 并提示「线上依赖齐全」不通过——**每条检查都能被构造出的错误单独触发，这才叫测试过。**

### 示例 9：collectstatic 到底在做什么

它就是把散在各 app 里的静态文件复制到一个目录；这里用临时目录模拟一遍。

```python
import os
import shutil
import tempfile

root = tempfile.mkdtemp()
for app in ("blog", "accounts"):
    d = os.path.join(root, app, "static", app)
    os.makedirs(d, exist_ok=True)
    open(os.path.join(d, "style.css"), "w", encoding="utf-8").write("body{}")

STATIC_ROOT = os.path.join(root, "staticfiles")
os.makedirs(STATIC_ROOT, exist_ok=True)
for cur, _dirs, files in os.walk(root):
    if "staticfiles" in cur:
        continue
    for f in files:
        rel = os.path.relpath(cur, root).replace(os.sep, "_")
        shutil.copy2(os.path.join(cur, f), os.path.join(STATIC_ROOT, rel + "_" + f))

print("收集结果:", sorted(os.listdir(STATIC_ROOT)))
print("文件数:", len(os.listdir(STATIC_ROOT)))
```

### 示例 13：静态资源指纹：让缓存失效可控

改了 CSS 用户却看到旧样式，是因为文件名没变；加内容指纹就能强制刷新。

```python
import hashlib


def fingerprint(path_like, size=8):
    return hashlib.md5(path_like.encode()).hexdigest()[:size]


assets = ["style.css", "app.js", "style.css"]
names = {a: fingerprint(a) for a in assets}
print(names)
print("style.css 加指纹后:", f"style.{names['style.css']}.css")
print("内容相同 → 指纹相同:", fingerprint("style.css") == fingerprint("style.css"))
```

运行结果：

```text
{'style.css': 'da232d78', 'app.js': '0364f57f'}
style.css 加指纹后: style.da232d78.css
内容相同 → 指纹相同: True
```

### 参考答案 20-6（检查清单增强版）

在示例 5 基础上新增一项「依赖体检」（完整脚本 = 示例 5 + 下面新增部分），其余方向（测试文件有无、build 钩子是否含 collectstatic）思路相同，都是「读文件内容 → 判断关键词」：

```python
# 新增检查：requirements.txt 是否锁版本 + 线上依赖齐全
def check_requirements(root):
    results = []
    main_file = root / "requirements.txt"
    if not main_file.exists():
        return [("✗", "requirements.txt 不存在")]
    text = main_file.read_text(encoding="utf-8")
    unpinned = [
        line for line in text.splitlines()
        if line.strip() and not line.strip().startswith("#") and "==" not in line
    ]
    if unpinned:
        results.append(("✗", f"有未锁版本的依赖：{unpinned}"))
    remote = root / "requirements_remote.txt"
    remote_text = remote.read_text(encoding="utf-8") if remote.exists() else ""
    for pkg in ("gunicorn", "psycopg2"):
        if pkg not in remote_text.lower():
            results.append(("✗", f"requirements_remote.txt 缺少 {pkg}（线上跑不起来）"))
    if not results:
        results.append(("✓", "依赖清单：版本已锁，线上依赖齐全"))
    return results
```

调用时把新检查加进 `report()`（片段，需与示例 6 合在一起运行）：

```text
results = check_files(root) + check_contents(root)
```

## 六、常见错误清单（务必逐条自查）

### 错误 1：★ ALLOWED_HOSTS 没加平台域名，线上 400

**现象**：部署成功、日志没报错，但一打开网址就是 `400 Bad Request`。**原因**：Django 校验每个请求的 `Host` 头，不在 `ALLOWED_HOSTS` 就直接 400，视图根本不执行。**修复**：settings.py 的 Platform.sh 段加 `ALLOWED_HOSTS.append('.platformsh.site')`，提交后重新 push。

### 错误 2：忘了注册 django_bootstrap5，模板报 Invalid block tag

**现象**：页面 500，报 `TemplateSyntaxError: Invalid block tag: 'bootstrap_form'`。**原因**：`{% load %}` 只是「打开工具包」，包本身要在 `INSTALLED_APPS` 注册。**修复**：`INSTALLED_APPS` 加 `'django_bootstrap5'`。

### 错误 3：DEBUG 关了却没收静态文件，白脸页面

**现象**：线上页面结构都在，但没有样式。**原因**：`DEBUG = False` 后 Django 不再代发静态文件；collectstatic 没跑，或 `STATIC_ROOT` 没设置。**修复**：build 钩子确保有 `python manage.py collectstatic --noinput`，云上段设置 `STATIC_ROOT`。

### 错误 4：requirements.txt 漏了 gunicorn 或 psycopg2

**现象**：部署日志 `ModuleNotFoundError: No module named 'gunicorn'`，或连不上数据库。**原因**：本地用 `runserver` + SQLite，这两个包本地没装过，`pip freeze` 不会列出来。**修复**：建 `requirements_remote.txt` 写上两者，并在 build 钩子里 `pip install -r requirements_remote.txt`。

### 错误 5：.gitignore 缺失，虚拟环境和本地数据库被推上云

**现象**：push 奇慢，仓库几百 MB；甚至线上用了你本地带数据的 SQLite 文件。**原因**：没有 `.gitignore`，`git add .` 把 `ll_env/`、`__pycache__/`、`db.sqlite3` 全提交了。**修复**：补写 `.gitignore`，用 `git rm -r --cached` 把已跟踪文件撤出索引，再提交。

### 错误 6：新文件忘了 git add，推送后线上缺东西

**现象**：本地明明建了 `templates/404.html`，线上还是默认错误页。**原因**：`git commit -am` 只提交**已跟踪**文件的修改，新文件必须先 `git add`。**修复**：只要产生了新文件（包括 `makemigrations` 生成的迁移文件），先 `git add .` 再 commit。

## 七、本单元验收自测

**1. 简答题**：`{% load django_bootstrap5 %}` 和 `{% bootstrap_form form %}` 分别负责什么？只写后者不写前者会怎样？
> **要点**：`load` 把模板标签库加载进当前模板，是「拿工具」；`bootstrap_form` 把字段逐个渲染成带 Bootstrap 类名的 HTML，是「干活的」。只写后者会报 `TemplateSyntaxError: Invalid block tag`——INSTALLED_APPS 注册和模板 load 缺一不可。

**2. 判断题**：`requirements.txt` 里写 `Django`（不带 `==` 版本号）也能正常部署，只是不优雅。
> **要点**：**错误**。不带 `==` 意味着装最新版。大版本升级经常带不兼容改动，半年后平台重建环境时可能直接启动失败。锁版本是部署的纪律，不是风格问题。

**3. 简答题**：`relationships: database: "db:postgresql"` 里的暗号怎么读？routes.yaml 的 `upstream: "ll_project:http"` 又和谁对应？
> **要点**：`"db:postgresql"` 冒号前是 services.yaml 里的服务名（`db`），冒号后是服务类型；`config.credentials('database')` 读的就是这份关系。routes 的 `upstream` 必须和 `.platform.app.yaml` 的 `name` 一致——路由按应用名转发域名。两处暗号对不上，部署直接失败。

**4. 改错题**：下面这段被加进 settings.py 的 Platform.sh 段，但部署后数据库连不通。为什么？

```python
# settings_snippet.py —— INTENTIONALLY-BROKEN 演示用：改错题，数据库配置连不通
from platformshconfig import Config

config = Config()
if config.is_valid_platform():
    db_settings = config.credentials('database')
    # 有 bug：引擎写死 SQLite，读来的 PostgreSQL 连接信息一个都没用
    DATABASES = {'default': {'ENGINE': 'django.db.backends.sqlite3', 'NAME': 'db.sqlite3'}}
```

> **要点**：引擎写死了 SQLite，读来的 PostgreSQL 连接信息（host/port/username/password）一个都没用。云上必须用 `'django.db.backends.postgresql'`，并把 `db_settings` 的字段填进 `NAME/USER/PASSWORD/HOST/PORT`。另外 `credentials('database')` 要放在 `if not config.in_build():` 里——构建阶段连不上数据库。

**5. 简答题**：`DEBUG = False` 之后，本地看到的报错页发生了什么变化？为什么定制 404/500 要求 `DEBUG = False`？
> **要点**：`DEBUG = False` 后 Django 不再显示带堆栈信息的黄色调试页，而是渲染 `templates/404.html`/`500.html`。调试页会泄露配置细节（设置项、SQL、文件路径），只适合本地；线上关闭调试后，友好的定制错误页才出场。

**6. 简答题**：描述一次「加功能」的完整部署流程，从本地改第一行代码到线上验证。
> **要点**：① 本地改代码并跑通；② 产生了新文件（含迁移文件）就 `git add .`；③ `git commit -am "提交说明"`；④ `platform push`（平台自动执行 build 钩子装依赖、collectstatic，再执行 deploy 钩子 migrate）；⑤ `platform url` 打开线上网址验证；出问题先看部署日志，修好再走一遍 ③④。
