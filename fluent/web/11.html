单元导入

asyncio 解决的是「单线程里同时等待很多个 IO」。它不加速计算，也不创建新线程；它把「等待」变成可挂起的点，让事件循环在等待期间去推进别的任务。

代价是传染性：一旦底层用了 await，调用链上的函数都要变成 async。这也是为什么异步代码不能和阻塞调用混用——一个 time.sleep() 就能卡死整个事件循环。

学完本单元，你应该能：

  • 写出 async def / await 的协程，并用 asyncio.run() 驱动；
  • 用 create_task、gather、TaskGroup 管理并发任务与异常；
  • 用 asyncio.timeout 控制超时，用 Semaphore 限制并发度；
  • 识别阻塞调用、忘记 await、任务泄漏等常见陷阱。

第 41 课 · 协程与事件循环

讲解

async def 定义的是协程函数，调用它不会执行函数体，而是返回协程对象：

Pythonimport asyncio

async def hello(name):
    print("start", name)
    await asyncio.sleep(1)      # 挂起，把控制权交回事件循环
    print("end", name)
    return name.upper()

coro = hello("a")
print(type(coro))               # <class 'coroutine'>，函数体没有执行
print(asyncio.run(hello("a")))  # 事件循环驱动，输出 START/END 与 'A'

要并发，必须把协程包装成 Task：

Pythonasync def main():
    t1 = asyncio.create_task(hello("a"))
    t2 = asyncio.create_task(hello("b"))
    print(await t1, await t2)

asyncio.run(main())

两个任务会几乎同时开始，1 秒后一起结束，而不是 2 秒。

延伸：协程、Task、Future 的分工

  • 协程（coroutine）：async def 调出来的对象，还没开始执行，需要被 await 或被包装成 Task。
  • Task：把协程排进事件循环的执行单元，asyncio.create_task() 之后它就在后台跑了。
  • Future：更低层的「结果占位符」，Task 是它的子类；回调式 API 用它。
Pythonimport asyncio

async def work():
    return 1

async def main():
    coro = work()                      # 协程，未执行
    task = asyncio.create_task(coro)   # 交给循环调度
    print(await task)                  # 1

asyncio.run(main())

asyncio.run 每次创建新循环、跑完关闭。已经处在循环里（Jupyter、框架回调、另一个协程）不能调它，否则报 RuntimeError: asyncio.run() cannot be called from a running event loop，要用 await。需要自己管循环时：

Pythonloop = asyncio.new_event_loop()
try:
    loop.run_until_complete(main())
finally:
    loop.close()

关键点

  • 协程对象不会自己运行，必须 await、create_task 或 gather。
  • await 只能在 async def 里用，普通函数里要 asyncio.run 或 run_coroutine_threadsafe。
  • Task 是协程的调度包装，创建后立即排队；Future 是更底层的「未来结果」。
  • 事件循环一个线程一个，不要在协程里再 asyncio.run。

动手

  1. 写 hello(name)，用 asyncio.run 跑一次，记录耗时。
  2. 用 create_task 并发跑 3 个 hello，验证总耗时约 1 秒。
  3. 故意直接调用 hello("a") 不 await，观察 RuntimeWarning: coroutine was never awaited。

验收清单

  • 能解释调用 async def 函数时发生了什么
  • 知道协程、Task、Future 三者的关系
  • 能写出最小可运行的 asyncio.run(main())

第 42 课 · 任务管理：gather、TaskGroup 与超时

讲解

gather 收集一组协程。默认情况下首个异常会立刻向上抛，其余任务仍在跑但结果拿不到；想收集全部结果（包括异常）要加 return_exceptions=True：

Pythonasync def main():
    results = await asyncio.gather(a(), b(), return_exceptions=True)
    for r in results:
        if isinstance(r, Exception):
            print("failed:", r)

asyncio.run(main())

TaskGroup（3.11+）是更现代的选择：任一任务失败会取消同组其他任务，并把异常包成 ExceptionGroup：

Pythonasync def main():
    async with asyncio.TaskGroup() as tg:
        t1 = tg.create_task(fetch("a"))
        t2 = tg.create_task(fetch("b"))
    print(t1.result(), t2.result())

超时用 asyncio.timeout（3.11+）：

Pythonasync def main():
    try:
        async with asyncio.timeout(3):
            await slow_operation()
    except TimeoutError:
        print("timed out")

延伸：to_thread 是什么，以及它的上限

Pythonimport asyncio, time

def blocking(x):
    time.sleep(x)
    return x

async def main():
    r = await asyncio.to_thread(blocking, 0.1)    # 3.9+
    print(r)

asyncio.run(main())

asyncio.to_thread 就是 loop.run_in_executor(None, partial(fn, *args)) 的语法糖，用的是默认 ThreadPoolExecutor，线程上限 min(32, os.cpu_count() + 4)。所以它是「把阻塞挪走」，不是「变出并行」：CPU 密集还是得 ProcessPoolExecutor。

反例最典型：协程里直接 time.sleep(1)，整个事件循环停 1 秒，所有并发任务一起卡住。判断标准是「这段代码会不会占住线程超过 ~10ms」，会就挪走。gather 里塞一万个任务也不行，那是「用并发打爆对方」，要配 Semaphore。

关键点

  • gather 不会自动取消其他任务（除非 return_exceptions=False 时首错向上抛，其余仍在跑）。
  • TaskGroup 的异常是 ExceptionGroup，要用 except* 分类型处理。
  • 取消是协作式的：任务要在 await 点才会响应 CancelledError。
  • 超时不是杀线程，只是取消当前任务；底层 IO 是否真的停止取决于库的实现。

动手

  1. 用 gather(return_exceptions=True) 跑 3 个任务（1 个失败），打印每个结果。
  2. 用 TaskGroup 跑同样 3 个任务，观察 ExceptionGroup 的结构，并用 except* 捕获。
  3. 用 asyncio.timeout(1) 包一个 sleep(5)，记录实际耗时。

验收清单

  • 能说出 gather 与 TaskGroup 在异常处理上的差异
  • 知道 ExceptionGroup 与 except* 的用法
  • 能写出带超时的异步调用

第 43 课 · 异步 IO：HTTP、上下文管理器与异步迭代

讲解

异步 HTTP 客户端（httpx）的基本用法：

Pythonimport asyncio
import httpx

async def fetch(client, url):
    r = await client.get(url)
    return r.status_code, len(r.text)

async def main(urls):
    async with httpx.AsyncClient(timeout=5) as client:
        return await asyncio.gather(*(fetch(client, u) for u in urls))

asyncio.run(main(["https://example.com"]))

async with 对应异步上下文管理器：

Pythonclass Conn:
    async def __aenter__(self):
        await asyncio.sleep(0.1)
        return self

    async def __aexit__(self, exc_type, exc, tb):
        await asyncio.sleep(0.1)
        return False

异步迭代器实现 __aiter__ / __anext__，用 async for 消费：

Pythonclass Ticker:
    def __init__(self, n):
        self.n = n

    def __aiter__(self):
        return self

    async def __anext__(self):
        if self.n <= 0:
            raise StopAsyncIteration
        self.n -= 1
        await asyncio.sleep(0.1)
        return self.n

并发度控制：

Pythonsem = asyncio.Semaphore(10)

async def limited(client, url):
    async with sem:
        r = await client.get(url)
        return r.status_code

延伸：start_server 与异步迭代协议

Pythonimport asyncio

async def handle(reader, writer):
    data = await reader.readline()
    writer.write(b"echo: " + data)
    await writer.drain()          # 背压点：等缓冲区可写
    writer.close()

async def main():
    srv = await asyncio.start_server(handle, "127.0.0.1", 8888)
    async with srv:
        await srv.serve_forever()

start_server 是回调式：每来一个连接，事件循环调一次 handle 生成协程。writer.drain() 是背压点，漏了会在对方读得慢时把数据堆在内存里。

异步迭代协议是 __aiter__ 返回自身、__anext__ 是协程，结束时抛 StopAsyncIteration；async for 就是它的语法糖。异步上下文管理器对应 __aenter__/__aexit__。数据库/HTTP 客户端的 async with 全是这两组协议。

关键点

  • httpx.AsyncClient 要复用，每次请求新建客户端会丢掉连接池。
  • async with 与 with 不能混用，异步资源必须用异步协议。
  • async for 只接受 __aiter__，普通生成器不行。
  • Semaphore 是限制并发不是限速，需要 QPS 限制得自己加时间窗。

动手

  1. 用 httpx.AsyncClient 并发请求 5 个 URL，打印状态码与耗时。
  2. 实现 Conn 异步上下文管理器，验证进入/退出顺序。
  3. 用 Ticker 异步迭代 3 次，再用 Semaphore(2) 限制 10 个任务的并发度。

验收清单

  • 能写出 async with 与 async for 的完整例子
  • 知道为什么要复用 AsyncClient
  • 能用 Semaphore 控制并发度

第 44 课 · 异步陷阱与选型

讲解

最常见的四个坑：

Pythonimport asyncio, time

# 1) 阻塞调用卡死事件循环
async def bad():
    time.sleep(3)          # 整个循环停 3 秒
    await asyncio.sleep(3)

# 2) 忘记 await：协程根本没跑
async def bad2():
    fetch(url)             # RuntimeWarning，且无结果

# 3) 任务泄漏：create_task 后不保存引用
async def bad3():
    asyncio.create_task(work())   # 任务可能被 GC，异常也没人收

# 4) 过度并发：10000 个任务同时打出去
async def bad4(urls):
    await asyncio.gather(*(fetch(u) for u in urls))   # 需要 Semaphore

修复方式分别是：阻塞调用放 asyncio.to_thread()、补 await、保存 Task 引用并 await、加 Semaphore。

选型判断：

场景 选择
纯 Python 计算 多进程
传统阻塞库、改动小 线程池
高并发网络 IO、全链路可控 asyncio
既有计算又有 IO asyncio + to_thread / 进程池

延伸：协作式调度的真实代价

异步不是「多线程的轻量版」，而是「单线程 + 主动让出」。只有 await 处才可能切换，所以任何一段不让出的代码都会独占循环：

  • 大循环、sum(huge_list)、正则灾难性回溯
  • json.loads 一个 100 MB 的响应
  • 同步库的 requests.get、pandas.read_csv

它们不会报错，只会让所有并发任务一起变慢，排查时表现为「QPS 上不去、延迟全是整数倍」。三个手段：to_thread 挪走、分片 await asyncio.sleep(0) 让出、换异步原生库。

调试：PYTHONASYNCIODEBUG=1 或 loop.set_debug(True) 会打印「Executing took 2.3 seconds」的慢回调警告，比猜快得多。

关键点

  • 异步不等于快：单次请求延迟不变，收益来自「同时等待很多个」。
  • 一个阻塞调用会拖垮全部并发，用 asyncio.to_thread 隔离。
  • 异常必须被 await 才可见，Task 要保存引用。
  • 调试用 asyncio.debug(True)，能提示慢回调与未回收任务。

动手

  1. 在协程里调用 time.sleep(3)，用两个并发任务验证总耗时变成 6 秒；再改成 to_thread 验证恢复。
  2. 写一个 create_task 不保存引用的例子，触发 Task was destroyed but it is pending 警告。
  3. 给 100 个请求加 Semaphore(10)，比较加与不加的内存占用。

验收清单

  • 能识别并修复四类异步陷阱
  • 能解释「异步不加速计算」的原因
  • 面对一个真实需求，能给出线程/进程/协程的选型理由

本节额外补充：协作式调度的真实代价

综合案例：异步抓取：把并发关进笼子

200 个地址要抓，先无脑 gather 一次，看它怎么把对方打挂、怎么一个异常全盘皆输，再加限流、超时与重试。

重构前（一次性全打出去）

gather 把 200 个协程同时排进循环，没有并发上限、没有超时；任何一个抛异常，整体直接失败，已完成的结果也拿不到。

Pythonimport asyncio

ACTIVE = {"now": 0, "max": 0}


async def client(url):
    ACTIVE["now"] += 1
    ACTIVE["max"] = max(ACTIVE["max"], ACTIVE["now"])
    await asyncio.sleep(0.001)
    ACTIVE["now"] -= 1
    if url.endswith("9"):
        raise OSError("connection reset")
    return 200


async def main():
    urls = [f"/p/{i}" for i in range(200)]
    try:
        codes = await asyncio.gather(*(client(u) for u in urls))
        print("成功", codes.count(200))
    except OSError as e:
        print("整体失败:", e)            # 一个失败，全部白跑
    print("最大同时在飞", ACTIVE["max"])   # 200：等于全量


asyncio.run(main())

重构后（信号量限流 + 单次超时 + 退避重试）

Semaphore(10) 控制同时在飞的数量；wait_for 只包住单次尝试（包住整个重试循环会把总时长当超时）；失败按 0.05 * 2**i 退避，最后把结果分成成功/失败两组。

Pythonimport asyncio

ACTIVE = {"now": 0, "max": 0}
CALLS = {}


async def client(url):
    CALLS[url] = CALLS.get(url, 0) + 1
    ACTIVE["now"] += 1
    ACTIVE["max"] = max(ACTIVE["max"], ACTIVE["now"])
    await asyncio.sleep(0.001)                 # 模拟网络
    ACTIVE["now"] -= 1
    if "dead" in url:
        raise OSError("gone")                  # 永久失败
    if "flaky" in url and CALLS[url] <= 2:
        raise OSError("reset")                 # 前两次失败
    return 200


async def fetch(url, sem, retries=3):
    async with sem:                            # 同时最多 N 个
        for attempt in range(retries):
            try:
                await asyncio.wait_for(client(url), timeout=1.0)
                return f"{url}:200"
            except (asyncio.TimeoutError, OSError):
                if attempt == retries - 1:
                    return f"{url}:failed"
                await asyncio.sleep(0.01 * (2 ** attempt))


async def main():
    urls = [f"/p/{i}" for i in range(200)] + ["/p/flaky-9", "/p/flaky-99", "/p/dead"]
    sem = asyncio.Semaphore(10)
    results = await asyncio.gather(*(fetch(u, sem) for u in urls))
    ok = [r for r in results if r.endswith(":200")]
    bad = [r for r in results if r.endswith(":failed")]
    print("总", len(results), "成功", len(ok), "失败", len(bad))   # 203 202 1
    print("失败样例", bad)                                      # ['/p/dead:failed']
    print("最大同时在飞", ACTIVE["max"])                          # 10


asyncio.run(main())

差异说明

问题 重构前 重构后 收益 代价
并发上限 200 个同时飞 Semaphore(10) 不打爆对方、内存可控 总耗时被限流拉长
超时 没有，慢请求挂住整体 wait_for 包单次尝试 单个慢请求不拖全局 超时值要按对方 P99 调
失败范围 一个异常全盘皆输 单个任务返回失败标记 部分成功可用 需要自己分类结果
重试 没有 指数退避 3 次 瞬时故障自愈 失败任务耗时变长
结果获取 gather 抛异常后全丢 每个任务自带结果 可统计、可重跑失败项 返回值要约定格式
协作让出 sleep(0) 也能让，但没有背压概念 信号量就是背压 系统整体可控 需要理解 async with 语义

再往前一步

把「结果格式」换成 dataclass Result(url, ok, status, tries, error)，就不用靠字符串后缀判断；限流从「任务数」升级成「每秒请求数」（令牌桶）；3.11+ 用 asyncio.timeout() 替代 wait_for，并用 TaskGroup 让「任一失败即取消同组」成为显式语义。
