动态属性与特性

原书这一章的写法，Python 为什么这样选、换别的要付什么代价。

property 管「存在的属性」，__getattr__ 管「不存在的属性」——两个钩子别混用。

项 内容
选择 property 描述符 + __getattr__ / __setattr__ 两级钩子
主要替代 显式 getXxx() / setXxx()、ORM 式字段声明、纯字典
替代为何落选 getter 让调用点变丑；字段声明要引入框架；字典丢掉了类型与文档
付出的代价 属性访问背后可能触发任意代码；拼错属性名不再立刻报错

当时的约束

用户想「像访问字段一样访问计算值」，又想「在赋值时做校验」，同时必须保住 obj.x = v 这个语法。Java Bean 式的 getter/setter 约定在 Python 社区被认为太吵——为了加一个校验就把所有调用点改一遍，代价和收益完全不成比例。

候选方案

getter/setter 命名约定；用 __getattr__ 一把梭（所有动态行为都塞进去）；property；以及更底层的描述符。

为什么选它

property 把「计算、缓存、校验」包在普通属性语法里，调用方零改动，日后想把直接字段换成计算值也不破坏 API。__getattr__ 只在常规查找失败后触发，这个「兜底」定位天生适合代理、懒加载和 ORM 字段——「我不存在，才问外面」。两级钩子各管一段，比一个万能钩子可控得多。

代价与反例

__getattr__ 里忘写 raise AttributeError，hasattr() 会永远返回真，copy/pickle 也会行为诡异。在 __getattr__ 里访问同一个属性会造成无限递归——这是动态属性最经典的事故。property 与 __slots__ 同名会直接冲突，报错还指向别处。拼错的属性名被 __getattr__ 静默接住，Bug 会推迟到很远的调用点才爆发。

如果重来

默认答案仍是 property（或 dataclass + __post_init__），把 __getattr__ 严格留给代理场景，并且强制配套实现 __dir__——让 IDE 补全和 dir() 还能发现这些「看不见的属性」，把可发现性还给用户。
