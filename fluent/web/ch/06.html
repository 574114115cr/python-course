对象引用、可变性与垃圾回收

原书这一章的写法，Python 为什么这样选、换别的要付什么代价。

引用计数负责「大多数立即回收」，分代 GC 只负责环。

项 内容
选择 引用计数 + 分代循环垃圾回收器
主要替代 纯 tracing GC（Java/Go 的分代或并发标记）
替代为何落选 C 扩展生态依赖确定性析构（文件句柄、锁、临时目录）
付出的代价 每个对象多一个引用计数字段；环要等 GC；__del__ 不可靠

当时的约束

CPython 要能被 C 扩展嵌入，扩展代码经常在对象析构时释放资源。如果回收时机不确定，with 之外的清理就没法写。

候选方案

纯引用计数（简单但有环泄漏）、纯 tracing（回收及时性差）、两者结合。最终选择结合：计数归零立即释放，环交给分代 GC。

为什么选它

确定性析构是 C 扩展的命脉：文件对象一出作用域就关，锁一释放就还。分代 GC 只需要偶尔扫描「可能成环」的容器对象，成本可控。

代价与反例

__del__ 在环里可能永不执行，解释器退出时也不保证；sys.getrefcount 看到的数字总比预期多 1（临时参数）；把大对象挂在全局缓存里，计数永远不归零。

如果重来

仍要确定性，但会把「不要依赖 __del__」写成硬规则，清理一律用上下文管理器；循环引用在数据结构设计阶段就避免（父子互指改成弱引用）。
