字典与集合

原书这一章的写法，Python 为什么这样选、换别的要付什么代价。

用哈希表换 O(1) 查找，并让「插入顺序」成为语言保证。

项 内容
选择 开放寻址哈希表 + 紧凑条目数组（3.6 起）
主要替代 平衡树（有序）、有序数组 + 二分
替代为何落选 树保序但常数大、实现复杂；有序数组插入 O(n)
付出的代价 键必须可哈希；扩容要重排；删除留墓碑

当时的约束

字典是 Python 最常用的数据结构（模块命名空间、关键字参数、对象属性都靠它），必须快；同时 3.7 起要求「插入顺序可预测」，否则 repr 与测试都不稳定。

候选方案

纯哈希表（无序）、哈希表 + 额外顺序链表、树。最终选了「索引数组 + 条目数组」：条目按插入顺序追加，索引数组做哈希定位。

为什么选它

查找仍是均摊 O(1)，遍历顺序天然等于插入顺序，而且条目数组紧凑、缓存友好。3.6 的实现意外带来内存下降，3.7 直接把顺序写进语言规范。

代价与反例

键必须可哈希且哈希稳定，可变对象当键是灾难。装载率到约 2/3 会扩容重排，单次插入可能 O(n)。删除只留墓碑，长期增删的字典会越来越慢。

如果重来

仍是哈希表，但会默认提供「有序映射」的显式替代（sortedcontainers 那类），并把「键必须不可变」写进类型提示（Hashable）。
