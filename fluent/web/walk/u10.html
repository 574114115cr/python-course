并发与执行器：线程池、进程池和 GIL 的分界线

一个可以整段复制运行的完整程序 + 逐段讲解 + 真实输出。 先跑一遍，再对着输出读讲解，最后做文末的三处改动。

原书第 19、20 章讲并发模型与执行器。这一篇用同一个任务跑三种方式（串行 / 线程池 / 进程池），并在线程里加锁验证竞态——所有结论都能在输出里看到。

程序

Pythonimport threading
import time
from concurrent.futures import ThreadPoolExecutor, as_completed


# ① 模拟 IO 任务：大部分时间在等，GIL 会在这时释放
def fetch(i):
    time.sleep(0.02)
    return i * i


# ② 模拟 CPU 任务：时间全花在字节码上
def burn(n):
    total = 0
    for i in range(n):
        total += i * i
    return total


def timed(label, fn):
    t0 = time.perf_counter()
    out = fn()
    return label, round((time.perf_counter() - t0) * 1000), out


serial_io = timed("串行 IO", lambda: [fetch(i) for i in range(8)])


def io_pool():
    with ThreadPoolExecutor(8) as pool:
        return list(pool.map(fetch, range(8)))


thread_io = timed("线程 IO", io_pool)
print("IO 任务 ", serial_io[0], serial_io[1], "ms |", thread_io[0], thread_io[1],
      "ms | 线程更快？", thread_io[1] < serial_io[1])
print("结果一致", serial_io[2] == thread_io[2])

serial_cpu = timed("串行 CPU", lambda: [burn(300_000) for _ in range(4)])


def cpu_pool():
    with ThreadPoolExecutor(4) as pool:
        return list(pool.map(burn, [300_000] * 4))


thread_cpu = timed("线程 CPU", cpu_pool)
print("CPU 任务", serial_cpu[0], serial_cpu[1], "ms |", thread_cpu[0], thread_cpu[1],
      "ms | 快到一半？", thread_cpu[1] < serial_cpu[1] * 0.5)

# ③ as_completed：谁先完成谁先处理，结果顺序与提交顺序无关
def jitter(i):
    time.sleep(0.01 * ((5 - i) % 5 + 1))
    return i


with ThreadPoolExecutor(4) as pool:
    futures = [pool.submit(jitter, i) for i in range(5)]
    done_order = [f.result() for f in as_completed(futures)]
print("完成顺序", done_order, "| 与提交顺序不同？", done_order != list(range(5)))

# ④ 线程不安全：读-改-写三步之间可能被切走
counter = {"n": 0}


def bump(times):
    for _ in range(times):
        v = counter["n"]
        time.sleep(0)                            # 主动让出，把竞态放大到必现
        counter["n"] = v + 1


threads = [threading.Thread(target=bump, args=(20_000,)) for _ in range(4)]
for t in threads:
    t.start()
for t in threads:
    t.join()
print("无锁计数", counter["n"], "| 正确结果应为 80000")

# ⑤ 加锁之后正确
lock = threading.Lock()
counter["n"] = 0


def bump_locked(times):
    for _ in range(times):
        with lock:
            counter["n"] += 1


threads = [threading.Thread(target=bump_locked, args=(20_000,)) for _ in range(4)]
for t in threads:
    t.start()
for t in threads:
    t.join()
print("加锁计数", counter["n"])

逐段走读

  1. IO 密集看线程，CPU 密集看进程。 第一组输出里线程池明显快于串行（8 个 20ms 的等待被重叠），因为 sleep 会释放 GIL；第二组里线程并没有带来加速——纯 Python 字节码同一时刻只能有一个线程在跑。这就是 GIL 的分界线：等待时可以并发，计算时不能。

  2. Executor.map 保序，as_completed 保快。 map 按提交顺序返回（内部会用 future 缓冲），所以第一组能直接比较结果列表；as_completed 谁先好谁先出，第三段里完成顺序和提交顺序不同，正是它的用途——处理「先到先得」的结果。

  3. 线程池要用 with 或手动 shutdown。 with 退出时会等所有任务跑完再关闭；如果忘了关闭，进程可能挂着不退出。进程池同理，而且它的启动开销大得多（Windows 上是 spawn，会重新导入模块），只适合「任务够重」的场景。

  4. 不加锁的 += 会丢更新。 counter["n"] = counter["n"] + 1 是「读 → 加 → 写」三步，线程切换可能发生在任意两步之间，于是两个线程读到同一个旧值。输出里的数字小于 80000 就是证据——这类 bug 不会报错，只会悄悄少算。

  5. 加锁之后「正确但更慢」。 with lock: 把三步包成临界区，结果精确等于 80000，代价是串行化。并发编程的本质就是这个交换：先保证正确，再谈性能；没有正确性的并发没有意义。

  6. 进程池不在这段可运行代码里，原因值得记一笔。 绕开 GIL 要用 ProcessPoolExecutor，写法几乎照抄线程池：

Pythonwith ProcessPoolExecutor(max_workers=2) as pool:
    list(pool.map(burn, [100_000, 100_000]))

但 Windows 的进程启动方式是 spawn：子进程会重新导入主模块。如果这段代码是直接粘贴到交互式环境或用 python -c 跑的，主模块无法被重新导入，就会抛错或卡住。所以它必须写在真实 .py 文件里，并且用 if __name__ == "__main__": 保护入口。另外参数与返回值都要能 pickle——lambda、文件句柄、锁、连接对象都过不去。

IO 任务  串行 IO 162 ms | 线程 IO 22 ms | 线程更快？ True
结果一致 True
CPU 任务 串行 CPU 28 ms | 线程 CPU 29 ms | 快到一半？ False
完成顺序 [0, 4, 3, 2, 1] | 与提交顺序不同？ True
无锁计数 20251 | 正确结果应为 80000
加锁计数 80000

跑通之后改三处

  • 把 fetch 里的 time.sleep(0.02) 换成 burn(100_000)：线程组的「更快？」会变成 False，GIL 的边界立刻显形。
  • 把 as_completed 换成 pool.map：完成顺序变回 0,1,2,3,4，但总耗时会等最慢的那个。
  • 把无锁的 bump 改成 counter["n"] += 1 并加大线程数：多数机器仍会丢更新（字节码边界不等于原子操作），说明「一行代码」和「原子」是两件事。
