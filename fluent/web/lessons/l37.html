并发全景：GIL、线程、进程

本节目标：能解释 GIL 的作用与边界，判断一个任务是 CPU 密集还是 IO 密集，并选出对应的并发模型。

讲解

并发（concurrency）是「多个任务在重叠的时间段内推进」，并行（parallelism）是「同一时刻真正同时执行」。单核也能并发，靠的是切换。

GIL（Global Interpreter Lock）是 CPython 解释器的一把全局锁：

  • 同一进程内，同一时刻只有一个线程在执行 Python 字节码；
  • 线程执行 IO（网络、文件、sleep）时会释放 GIL；
  • 某些 C 扩展（NumPy 的部分运算、压缩库）会在计算时释放 GIL。

因此：

任务类型 多线程 多进程 异步 IO
CPU 密集（纯 Python） ❌ 几乎无加速 ✅ 接近线性 ❌
IO 密集（网络/磁盘） ✅ ✅（但开销大） ✅ 最轻
大量短连接 一般 ❌ ✅ 
Pythonimport time

def cpu_task(n):
    return sum(i * i for i in range(n))

t0 = time.perf_counter()
for _ in range(4):
    cpu_task(2_000_000)
print("serial", time.perf_counter() - t0)

把这段改成 4 个线程跑，通常不会更快；改成 4 个进程才会。

延伸：GIL 到底卡住什么

一句话：同一时刻只有一个线程在执行 Python 字节码。但下面这些会主动释放 GIL：

  • time.sleep、文件读写、socket 收发（等 IO 时释放）
  • 大量 C 扩展在长计算中释放（NumPy 大矩阵、zlib、hashlib）
  • 任何 Py_BEGIN_ALLOW_THREADS 包裹的 C 代码

所以「IO 密集用线程有效、纯 Python 计算密集用线程更慢」不是玄学，是释放点在哪的问题。

Pythonimport sys
sys.setswitchinterval(0.001)      # 默认 0.005 秒，调小切换更频繁
print(sys.getswitchinterval())

CPython 3.13 起提供 free-threaded 构建（PEP 703，python3.13t），可以真正并行，但单线程性能有折损、第三方扩展的兼容仍在推进。写库时的正确姿势是「假设 GIL 可能存在也可能不存在」：不要依赖它做原子性保证，+= 在自由线程下不是原子的。

关键点

  • GIL 不是 Python 语言规范，是 CPython 的实现；3.13 起提供实验性的 free-threaded 构建，但默认构建仍有 GIL。
  • GIL 不保证线程安全：x += 1 仍是「读—改—写」三步，可能被切换。
  • 进程有独立内存，通信要序列化（pickle），启动成本高。
  • 线程适合 IO，不是因为线程快，而是因为等待时不占 CPU。

动手

  1. 写一个 cpu_task(n) 与一个 io_task(seconds)，分别用串行、4 线程、4 进程跑，记录耗时表。
  2. 用 sys.setswitchinterval(0.0001) 缩短切换间隔，观察竞态是否更容易复现。
  3. 查一下你机器上的 Python 是否是 free-threaded 构建（sys._is_gil_enabled()）。

  • 给定 5 个任务，能正确判断该用线程、进程还是协程
  • 知道多线程不能加速纯 Python 计算的原因
