执行器：ThreadPoolExecutor 与 ProcessPoolExecutor

本节目标：能用两种执行器提交任务、收集结果、处理异常，并知道各自的启动成本与限制。

讲解

concurrent.futures 把线程/进程池抽象成同一套 API：

Pythonfrom concurrent.futures import ThreadPoolExecutor, as_completed

def fetch(url):
    ...

with ThreadPoolExecutor(max_workers=8) as pool:
    futures = {pool.submit(fetch, u): u for u in urls}
    for fut in as_completed(futures):
        url = futures[fut]
        try:
            print(url, fut.result())
        except Exception as e:
            print(url, "failed:", e)

ProcessPoolExecutor 用法几乎一样，但有两个硬限制：参数与返回值必须可 pickle，任务函数必须在模块顶层定义（__main__ 里直接跑要加 if __name__ == "__main__":）。

Pythonfrom concurrent.futures import ProcessPoolExecutor

def square(x):
    return x * x

if __name__ == "__main__":
    with ProcessPoolExecutor() as pool:
        print(list(pool.map(square, range(10))))

map 按输入顺序返回，as_completed 按完成顺序返回；需要「谁先好先处理谁」就用后者。

延伸：Executor.map 的返回顺序与异常时机

map 会立刻提交所有任务，返回按输入顺序产出结果的迭代器；异常不在提交时抛，而是等迭代到那一项：

Pythonfrom concurrent.futures import ThreadPoolExecutor

def bad(x):
    if x == 2:
        raise ValueError(x)
    return x

with ThreadPoolExecutor() as ex:
    for v in ex.map(bad, [1, 2, 3]):
        print(v)          # 打印 1，然后抛 ValueError(2)

它不会取消后面已提交的任务——3 和 3 之后的任务照样在跑，只是结果没人取。要边完成边处理就用 as_completed。map(..., timeout=n) 的计时从迭代开始算，超时抛 TimeoutError，但后台任务仍在运行（Python 无法安全中断线程）。

关键点

  • 线程池大小不是越大越好：IO 密集可以 2–4 倍 CPU 核数，CPU 密集取核数。
  • with 退出会等待所有任务结束；要提前取消用 shutdown(cancel_futures=True)。
  • 异常存到 Future 里，只有调用 result() 时才抛出。
  • 进程池启动慢，任务太短（毫秒级）时开销大于收益。

动手

  1. 用 ThreadPoolExecutor 并发请求 10 个 URL，打印每个的耗时与总耗时。
  2. 用 ProcessPoolExecutor 计算 8 个 CPU 密集任务，比较串行耗时。
  3. 故意提交一个会抛异常的任务，分别用 map 与 submit 观察异常传播方式。

验收清单

  • 能写出两种执行器的最小可用代码
  • 知道进程池对参数、返回值、入口代码的要求
  • 能解释 map 与 as_completed 的返回顺序差异
