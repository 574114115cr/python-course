综合验收：读懂框架的 200 行

本节目标：能在一个真实框架的核心模块里定位「描述符 / 元类 / `__getattr__`」三种机制，并说清它们各自解决了什么问题。

讲解

拿一个你常用的库，按下面顺序读：

  1. 找入口：__init__.py 导出了什么，公开 API 是哪几个名字。
  2. 找类创建钩子：搜 metaclass=、__init_subclass__、__set_name__。
  3. 找属性访问钩子：搜 __getattr__、__getattribute__、__get__。
  4. 找注册表：搜全局 dict / list，看谁往里写、谁从里读。
  5. 画一张图：用户写一行代码 → 触发了哪条链 → 最终落到哪个函数。

以 ORM 为例：models.CharField() 返回一个描述符；模型类创建时元类收集所有字段；实例访问 user.name 时描述符从数据库行里取值。三件事分别对应本单元的三节课。

把钩子和本课程对照起来看：

钩子 触发时机 典型库 对应课节
__get__ / __set__ 访问/赋值实例属性 Django Field、SQLAlchemy Column 第 46 课
__set_name__ 类创建完成时 dataclasses.field、ORM 字段 第 46 课
__getattr__ 常规查找失败后 懒加载代理、配置对象 第 45 课
__init_subclass__ 子类定义完成时 插件注册、校验基类 第 47 课
元类 类创建过程中 Django ModelBase、pydantic ModelMetaclass 第 47 课

把这三节课拼起来，就是一个能跑的最小 ORM：

Pythonclass Field:
    def __set_name__(self, owner, name):
        self.name = name

    def __get__(self, obj, owner=None):
        if obj is None:
            return self
        return obj._data.get(self.name)

    def __set__(self, obj, value):
        obj._data[self.name] = value


class ModelMeta(type):
    def __new__(mcls, name, bases, ns):
        cls = super().__new__(mcls, name, bases, ns)
        fields = {}
        for base in bases:                       # 继承父类字段
            fields.update(getattr(base, "_fields", {}))
        fields.update({k: v for k, v in ns.items() if isinstance(v, Field)})
        cls._fields = fields
        return cls


class Model(metaclass=ModelMeta):
    def __init__(self, **kwargs):
        self._data = {}
        for k, v in kwargs.items():
            setattr(self, k, v)

    def __repr__(self):
        return f"{type(self).__name__}({self._data!r})"


class User(Model):
    name = Field()
    age = Field()


u = User(name="Ann", age=30)
print(u)              # User({'name': 'Ann', 'age': 30})
print(User._fields)   # {'name': <Field ...>, 'age': <Field ...>}

这段代码不到 40 行，但已经具备 ORM 的三个核心：字段描述符负责读写、元类负责收集字段、模型基类负责初始化。真实框架多出来的是 SQL 生成、关系映射、迁移，而不是另一套元编程。

延伸：四类钩子的检索法

拿到陌生框架，按四个关键词搜源码，基本能画出扩展点地图：

关键词 机制 典型用途
__get__ 描述符 字段 / 属性拦截、惰性加载、ORM 列
__set_name__ 类创建回调 字段注册、知道自己叫什么
__init_subclass__ 子类定义回调 插件注册、自动加功能
metaclass= 元类 整类改造、接口约束 
Pythonclass Plugin:
    registry = {}
    def __init_subclass__(cls, **kw):
        super().__init_subclass__(**kw)
        Plugin.registry[cls.__name__] = cls

class JsonPlugin(Plugin):
    pass

print(Plugin.registry)      # {'JsonPlugin': <class 'JsonPlugin'>}

__init_subclass__ 是「不需要元类就能在子类定义时拿到钩子」的正规做法，1980 年代的元类需求里有一大半它能替代。判断该不该上元类：只需要「子类定义时做一件事」就用 __init_subclass__；需要改类的创建过程本身（换命名空间、改 __call__）才用元类。

读框架的顺序：先找钩子 → 再顺着钩子看调用链 → 最后才读工具函数。看不懂就先写 20 行最小复现，把框架剥到只剩钩子。

关键点

  • 先看公开 API，再看实现，不要一头扎进工具函数。
  • 钩子比流程重要：找到钩子，就找到了框架的扩展点。
  • 画调用链比读注释有效，尤其是元编程代码。
  • 看不懂时先写最小复现，把框架剥到 20 行。

动手

  1. 选一个库（Django ORM、SQLAlchemy、pydantic、pytest 任选），定位至少两个钩子。
  2. 写一页笔记：钩子名、触发时机、解决的问题、对应的最小复现。
  3. 给上面的迷你 ORM 补三件事：字段类型校验、to_dict()、按 id 从字典里取一条记录。

验收清单

  • 能在真实代码里定位描述符、元类/__init_subclass__、__getattr__ 三类钩子
  • 能画出一条从用户 API 到内部实现的调用链
  • 能判断某个机制「该不该用元编程实现」，并给出更简单的替代方案
  • 迷你 ORM 能跑通 User(name="Ann")，并解释每个字段的读写走了哪个方法
