单元导入

dict 是 Python 里被用得最多、也最容易被误解的结构：它快，是因为哈希表；它「有序」，是因为 3.6 起换了紧凑布局并在 3.7 写进语言规范；它不能拿 list 当键，是因为 list 不可哈希。

本单元还会处理另一类高频事故：文本与字节的边界。str 是码点序列，bytes 是字节序列，两者之间只有一条桥——编码/解码。桥走错了，就会出现 UnicodeDecodeError、乱码、以及「看起来一样却不相等」的字符串。

学完本单元，你应该能：

  • 解释 dict 的查找、插入、扩容过程，并说清为什么键必须可哈希；
  • 熟练使用 |、**、setdefault、defaultdict、Counter、ChainMap；
  • 在 set / frozenset / MappingProxyType 之间按「是否需要可变、是否需要哈希」选型；
  • 独立定位一次编码错误，并用 unicodedata.normalize 统一文本。

第 5 课 · 哈希表：dict 为什么快，顺序为什么稳定

讲解

dict 的底层是哈希表。插入一个键时，解释器先算 hash(key)，再用它对表长取模得到槽位；查找时走同一条路径，所以平均复杂度是 O(1)。冲突用开放寻址解决——槽位被占就按探测序列找下一个空位。

Pythond = {"apple": 3, "banana": 5}
print(hash("apple"))        # 同一个进程内固定，跨进程会变（字符串哈希有随机化）
d["cherry"] = 7             # 插入：算 hash → 找槽位 → 写入
print("apple" in d)         # 查找：算 hash → 比对键 → 命中

3.6 起 CPython 把 dict 改成「紧凑 dict」：条目按插入顺序连续存放，另外维护一张稀疏索引表指向条目。这带来两个结果——内存更省，以及遍历顺序 = 插入顺序。3.7 起后者成为语言保证，可以依赖。

键必须可哈希，因为哈希表要靠 hash 定位。可变容器（list、dict、set）不可哈希；tuple 只有在所有元素都可哈希时才可哈希：

Pythonprint(hash((1, 2, 3)))       # ok
try:
    hash((1, [2, 3]))
except TypeError as e:
    print("TypeError:", e)   # unhashable type: 'list'

延伸：dict 的扩容：为什么插入偶尔变慢

dict 是开放寻址哈希表，装载率到约 2/3 就扩容：新建更大的表，把所有键重新插入。单次插入最坏 O(n)，均摊 O(1)。三条工程含义：

  • 已知规模就先构造，别边插边扩容。dict.fromkeys(keys) 或一次性字面量比循环赋值省。
  • 遍历中改大小会 RuntimeError: dictionary changed size during iteration；要改就先 list(d) 收集键。
  • 删除键会留下 dummy 标记（墓碑），越删越慢；长期增删的缓存适合定期重建一个新的 dict。

顺带一个事实：sys.getsizeof({}) 是 64 字节，空 dict 也不便宜。这就是「小对象用 __slots__ 或元组代替 dict」的动机之一。

关键点

  • 哈希值相等不代表对象相等：hash(a) == hash(b) 只说明可能落在同一槽位，最终还要 a == b。
  • 自定义类做键：默认按身份哈希；一旦重写 __eq__ 就必须同时重写 __hash__，否则类会变成不可哈希。
  • 顺序稳定 ≠ 可排序：dict 保留插入顺序，但不会替你排序；要排序得用 sorted(d.items())。
  • 扩容会重建索引表，这也是为什么「边遍历边增删键」会抛 RuntimeError，需要先复制键列表。

动手

  1. 用 time.perf_counter() 比较 x in list_of_100k 与 x in set_of_100k 的耗时，记录倍数。
  2. 自定义 Point 类，重写 __eq__ 与 __hash__，把它作为 dict 的键，验证两个相等实例能命中同一条目。
  3. 故意在 for k in d: 循环里 d[k + "_new"] = 1，观察报错并改成遍历 list(d)。

验收清单

  • 能用自己的话解释「索引数组 + 条目数组」如何同时保证速度和顺序
  • 能说出重写 __eq__ 后必须重写 __hash__ 的原因
  • 知道遍历 dict 时增删键会报错，并知道正确做法

第 6 课 · 映射的惯用法：合并、缺失键与视图

讲解

现代 Python 合并字典有两条路：| 运算符（3.9+，返回新字典）和 ** 拆包（构造时使用）。两者都是「右边的键覆盖左边」：

Pythondefaults = {"host": "localhost", "port": 8000}
override = {"port": 9000}
cfg = defaults | override            # {'host': 'localhost', 'port': 9000}
cfg2 = {**defaults, **override}      # 等价写法

缺失键的三种处理方式，差别在「是否会写入」和「代码是否可读」：

Pythonfrom collections import defaultdict, Counter

word_count = {}
word_count.setdefault("apple", 0)
word_count["apple"] += 1             # setdefault 会写入默认值

groups = defaultdict(list)           # 访问缺失键时自动建 list，不抛 KeyError
for name, dept in [("Ann", "R&D"), ("Bob", "Ops"), ("Cid", "R&D")]:
    groups[dept].append(name)

cnt = Counter("abracadabra")         # 计数专用，缺失键返回 0
print(cnt.most_common(2))            # [('a', 5), ('b', 2)]

collections.ChainMap 把多个映射串成一条查找链，适合「命令行参数 > 环境变量 > 默认配置」这种分层配置。

延伸：ChainMap 的写落在第一个映射

ChainMap 只是在查找时依次问每个映射，写操作永远落在第一个：

Pythonfrom collections import ChainMap
defaults = {"color": "red", "size": 10}
user = {"color": "blue"}
c = ChainMap(user, defaults)
print(c["color"], c["size"])   # blue 10
c["size"] = 12                 # 写进 user，不动 defaults
print(user, defaults)          # {'color': 'blue', 'size': 12} {'color': 'red', 'size': 10}

c.maps 能拿到映射列表，改优先级就调整顺序。shelve 用 pickle 存值，键必须是 str；pickle 跨 Python 大版本不保证兼容，长期存档应该换 JSON 或 SQLite。读回来的值已经是副本，改完要显式写回。

关键点

  • d[k] 缺失会抛 KeyError，d.get(k) 返回 None；需要区分「键不存在」和「值是 None」时用 if k in d。
  • defaultdict 的工厂函数每次缺失都会调用，用 lambda: [] 要小心闭包；直接用 list 更安全。
  • Counter 是 dict 的子类，可以做 +、-、&、| 合并计数。
  • 视图是动态的：d.keys()、d.values()、d.items() 不复制数据，字典变了视图也变。

动手

  1. 把三份配置（默认、文件、命令行）用 ChainMap 合成一份，验证优先级。
  2. 用 defaultdict(list) 按首字母给 20 个单词分组，再按组大小排序输出。
  3. 用 Counter 统计一段文本的词频，输出前 5 个词及其出现次数。

验收清单

  • 能说出 | 与 ** 合并的相同点和至少一个差异
  • 能解释 setdefault 与 defaultdict 在「是否写入」上的区别
  • 知道 d.items() 是视图而不是列表，需要排序时要显式转换

第 7 课 · 集合与不可变映射：用集合运算替代循环

讲解

集合的核心价值是成员测试 O(1) 和集合代数。很多「两层 for 循环 + if」的代码，都可以压成一次集合运算：

Pythona = {"alice", "bob", "cid"}
b = {"bob", "dave"}

print(a | b)      # 并集
print(a & b)      # 交集
print(a - b)      # 差集：在 a 不在 b
print(a ^ b)      # 对称差
print(a <= {"alice", "bob", "cid", "dave"})   # 子集判断

去重并保序是常见需求，标准写法是 list(dict.fromkeys(items))——利用 dict 的去重与插入顺序，而不是 list(set(...))（后者会打乱顺序）：

Pythonitems = ["b", "a", "b", "c", "a"]
print(list(dict.fromkeys(items)))   # ['b', 'a', 'c']

集合本身可变，因此不可哈希，不能作为 dict 的键；frozenset 不可变、可哈希，适合做「键」或「缓存标识」：

Pythoncache = {}
key = frozenset({"read", "write"})
cache[key] = "permission-set"

只读映射用 types.MappingProxyType 包一层，外部拿不到写接口：

Pythonfrom types import MappingProxyType
CONFIG = MappingProxyType({"debug": False})
# CONFIG["debug"] = True   → TypeError

延伸：视图做集合运算的前提

d.items() 返回视图，支持 &、|、- 做集合运算，但要求每个键值对可哈希——值里放 list 就直接 TypeError：

Pythona = {"x": 1, "y": 2}; b = {"y": 2, "z": 3}
print(a.items() & b.items())    # {('y', 2)}
print(a.keys() | b.keys())      # {'x', 'y', 'z'}

MappingProxyType 是只读代理，不是快照：底层 dict 一变，代理看到的就是新值。

Pythonfrom types import MappingProxyType
cfg = {"debug": True}
ro = MappingProxyType(cfg)
cfg["debug"] = False
print(ro["debug"])      # False

要真快照得 dict(cfg) 复制一份。

关键点

  • 集合元素必须可哈希，所以不能把 list 放进 set；需要放就用 tuple 或 frozenset。
  • &、| 对 set 是集合运算，对 dict 的键视图也能用：d1.keys() & d2.keys() 直接求共同键。
  • in 在 set 上是 O(1)，在 list 上是 O(n)；循环里做成员测试时先转 set。
  • 空集合只能写 set()，{} 是空字典。

动手

  1. 有两份用户名单（老用户、新用户），求「新增」「流失」「两边都有」三个集合。
  2. 用 frozenset 做缓存键，缓存「两个单词的字母集合是否相同」的判断结果。
  3. 把一个 10 万元素的 list 去重并保持原顺序，比较两种写法的耗时与结果差异。

验收清单

  • 能用集合运算重写一段「双层循环找共同元素」的代码
  • 知道 list(set(x)) 会丢顺序，并知道替代写法
  • 能解释为什么 frozenset 能当 dict 的键而 set 不能
教材对照第 3 章 §3.7–3.8、§3.10–3.12本节自足，无需回查原书

第 8 课 · 文本与字节：编码、解码与规范化

讲解

str 是 Unicode 码点序列，bytes 是 0–255 的字节序列。两者之间的唯一通道是编码：

Pythontext = "café"
raw = text.encode("utf-8")        # b'caf\xc3\xa9'
print(len(text), len(raw))        # 4 5（é 占两个字节）
print(raw.decode("utf-8"))        # café

中文的差异更明显："中文".encode("utf-8") 得到 6 个字节，而 len("中文") 是 2。所以「字符数」和「字节数」永远不要混用。

解码失败通常有两个原因：用错编码、数据被截断。排查顺序是：先确认来源编码（HTTP 头、文件声明、数据库列），再决定用哪个 codec：

Pythonraw = "café".encode("utf-8")
try:
    raw.decode("ascii")
except UnicodeDecodeError as e:
    print(e)                      # 'ascii' codec can't decode byte 0xc3 ...
print(raw.decode("ascii", errors="replace"))   # caf��
print(raw.decode("ascii", errors="ignore"))    # caf

errors= 是兜底，不是修复：replace 会留下替换符，ignore 会静默丢数据，只在「展示」场景用，不要用在数据管道里。

另一类坑是「看起来一样，实际不等」："café" 可能是 e + ́（组合字符）或 é（预组合字符）。用 unicodedata.normalize("NFC", s) 统一：

Pythonimport unicodedata as ud

a = "café"                     # 预组合
b = "cafe\u0301"               # e + 组合重音
print(a == b)                  # False
print(ud.normalize("NFC", a) == ud.normalize("NFC", b))   # True
print(ud.normalize("NFD", a))  # 分解形式，适合做搜索/排序键

延伸：unicodedata 与文件系统编码

unicodedata 能按名字查字符、查类别、做规范化：

Pythonimport unicodedata as ud
print(ud.lookup("GREEK SMALL LETTER ALPHA"))            # α
print(ud.name("é"))                                     # LATIN SMALL LETTER E WITH ACUTE
print(ud.normalize("NFC", "e\u0301") == "é")            # True
print(ud.category("α"), ud.category("1"), ud.category(" "))   # Ll Nd Zs

os.fsencode / os.fsdecode 处理的是文件系统编码，和 str.encode("utf-8") 不是一回事：Linux 上遇到无法解码的文件名字节时，会用 surrogateescape 把原始字节映射成孤立代理字符，来回转换不丢字节。处理「用户传了个奇怪文件名」的路径时必须用它，用 UTF-8 硬编码会抛 UnicodeDecodeError。

关键点

  • 打开文件永远显式写 encoding="utf-8"，不要依赖系统默认（Windows 默认 GBK，Linux 默认 UTF-8）。
  • BOM 不是内容：utf-8-sig 读取会吃掉 BOM；写 CSV 给 Excel 用时才需要加 BOM。
  • 大小写折叠用 str.casefold()，比 lower() 更适合做不区分大小写的比较（德语 ß、土耳其语 İ 等）。
  • 排序按码点，不按语言习惯：中文按拼音排序需要 locale.strxfrm 或第三方库，sorted() 做不到。

动手

  1. 写一个函数 safe_read(path)：用 UTF-8 读文件，遇到 UnicodeDecodeError 时打印出错字节位置和前后各 20 字节，再抛出自定义异常。
  2. 构造 "café" 的两种表示，验证不相等，再用 NFC 规范化后相等。
  3. 统计一段中英混排文本的「字符数」与「UTF-8 字节数」，解释差异来源。

验收清单

  • 能解释 len("中文") 与 len("中文".encode()) 为什么不同
  • 遇到 UnicodeDecodeError 会先查来源编码，而不是直接 errors="ignore"
  • 能用 NFC/NFD 解释并修复一次「字符串看起来一样却不相等」

本节额外补充：unicodedata 与文件系统编码

综合案例：中英混排词频：从 split 到规范化

统计多段中英混排文本的高频词，先写「一眼能用」的版本，再逐条修掉它的坑。

重构前（能跑但粗糙）

doc.split() 按空白切词，Counter 直接累加——对纯英文短句还行，对真实文本几乎全错。它连「按文档分组统计」都做不到，只能把全部单词堆进一个临时列表。

Pythonfrom collections import Counter

DOCS = [
    "The café is OPEN.",
    "数据 数据 结构，Python python PYTHON!",
]


def count_all(docs):
    words = []
    for doc in docs:
        for w in doc.split():
            words.append(w)
    return Counter(words)


def top_words(docs, n=5):
    return count_all(docs).most_common(n)


print(top_words(DOCS))
# [('数据', 2), ('The', 1), ('café', 1), ('is', 1), ('OPEN.', 1)]
print(top_words(DOCS, 3))
# [('数据', 2), ('The', 1), ('café', 1)]

四个问题一次暴露：大小写没合并（The / python / PYTHON 各算一次）、标点粘在词尾（OPEN.、结构，Python）、中文没有空格所以整句被当成一个词、café 若以 NFD 存储会被切成两个码位。

重构后（先规范化再切词，按文档合并）

三步：Unicode 规范化 → 大小写折叠 → 按「汉字块 / 字母块 / 数字块」切。中文仍然只能做到「连续汉字成块」，但英文与数字是干净的；再按文档分别计数后合并，就能顺手做「每篇文档的关键词」。

Pythonimport re
import unicodedata
from collections import Counter

DOCS = [
    "The café is OPEN.",
    "数据 数据 结构，Python python PYTHON!",
]
STOP = frozenset({"the", "is", "a", "an"})

# 词块：一段汉字、一段任意 Unicode 字母、一段数字
TOKEN = re.compile(r"[\u4e00-\u9fff]+|[^\W\d_]+|\d+")


def normalize(text):
    # NFC：把 e + 组合符合成单个码位，避免同一个字被算成两种
    text = unicodedata.normalize("NFC", text)
    # casefold 比 lower 更彻底：ß → ss，适合大小写无关的比较
    return text.casefold()


def tokens(text, stop=STOP):
    return [t for t in TOKEN.findall(normalize(text)) if t not in stop]


def count_docs(docs, stop=STOP):
    """每篇文档各自计数再合并，方便顺手算「本文关键词」。"""
    total = Counter()
    per_doc = []
    for doc in docs:
        c = Counter(tokens(doc, stop))
        per_doc.append(c)
        total += c
    return total, per_doc


total, per_doc = count_docs(DOCS)
print(total.most_common(5))
# [('python', 3), ('数据', 2), ('café', 1), ('open', 1), ('结构', 1)]

print(per_doc[0].most_common(2))
# [('café', 1), ('open', 1)]：第一段只剩两个实词

# 不做规范化与切词会怎样？直接看原始 split 的结果
print(Counter(DOCS[1].split()).most_common(2))
# [('数据', 2), ('结构，Python', 1)]：标点和整句都粘在一起

差异说明

问题 重构前 重构后 收益 代价
大小写 The / python / PYTHON 各算一次 casefold() 统一 词频不再被拆散 输出全小写，展示时要还原
标点 OPEN.、结构，Python 带着标点 正则只取词块 词表干净 丢掉 C++、node.js 这类记号
中文 整句当一个词 连续汉字成块 至少能按词块统计 仍不分词，数据结构 是一块
Unicode café 两种存储形态算两个词 NFC 规范化 同一字只算一次 每次统计多一次规范化开销

按文档统计 只能全局累加 count_docs 返回总量 + 每篇 可算关键词、可做 TF-IDF 多存一份 Counter
停用词 写死在逻辑里 STOP 参数传入 逻辑与词表分离，好测 调用方要自己维护词表

再往前一步

真做中文词频要上分词（jieba），并把「停用词表」与「同义词归一」做成独立步骤；英文则应按 word + lemma 归并（running / ran → run）。有了 per_doc，下一步就是算 TF-IDF：词频除以文档频率再取对数——十几行代码就能做一个「本文关键词」功能。
