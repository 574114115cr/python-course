单元导入

并发不是「同时做很多事」，而是「让等待重叠」。判断该用什么工具，只看一个问题：瓶颈在 CPU 还是在 IO？

  • CPU 密集：计算、压缩、图像处理 → 多进程；
  • IO 密集：网络、磁盘、数据库 → 线程或协程；
  • 既有计算又有等待 → 拆开，或进程池 + 异步 IO 组合。

CPython 默认构建有 GIL：同一时刻只有一个线程执行 Python 字节码。它保护了解释器内部状态，但也意味着多线程不能加速纯 Python 计算。本单元先把这件事讲透，再进入 concurrent.futures 的两种执行器。

学完本单元，你应该能：

  • 用「CPU 密集 / IO 密集」判断并发方案；
  • 写出线程安全的计数器，解释竞态与锁；
  • 用 ThreadPoolExecutor 并发下载，用 ProcessPoolExecutor 并行计算；
  • 正确处理超时、异常、取消与资源回收。

第 37 课 · 并发全景：GIL、线程、进程

讲解

并发（concurrency）是「多个任务在重叠的时间段内推进」，并行（parallelism）是「同一时刻真正同时执行」。单核也能并发，靠的是切换。

GIL（Global Interpreter Lock）是 CPython 解释器的一把全局锁：

  • 同一进程内，同一时刻只有一个线程在执行 Python 字节码；
  • 线程执行 IO（网络、文件、sleep）时会释放 GIL；
  • 某些 C 扩展（NumPy 的部分运算、压缩库）会在计算时释放 GIL。

因此：

任务类型 多线程 多进程 异步 IO
CPU 密集（纯 Python） ❌ 几乎无加速 ✅ 接近线性 ❌
IO 密集（网络/磁盘） ✅ ✅（但开销大） ✅ 最轻
大量短连接 一般 ❌ ✅ 
Pythonimport time

def cpu_task(n):
    return sum(i * i for i in range(n))

t0 = time.perf_counter()
for _ in range(4):
    cpu_task(2_000_000)
print("serial", time.perf_counter() - t0)

把这段改成 4 个线程跑，通常不会更快；改成 4 个进程才会。

延伸：GIL 到底卡住什么

一句话：同一时刻只有一个线程在执行 Python 字节码。但下面这些会主动释放 GIL：

  • time.sleep、文件读写、socket 收发（等 IO 时释放）
  • 大量 C 扩展在长计算中释放（NumPy 大矩阵、zlib、hashlib）
  • 任何 Py_BEGIN_ALLOW_THREADS 包裹的 C 代码

所以「IO 密集用线程有效、纯 Python 计算密集用线程更慢」不是玄学，是释放点在哪的问题。

Pythonimport sys
sys.setswitchinterval(0.001)      # 默认 0.005 秒，调小切换更频繁
print(sys.getswitchinterval())

CPython 3.13 起提供 free-threaded 构建（PEP 703，python3.13t），可以真正并行，但单线程性能有折损、第三方扩展的兼容仍在推进。写库时的正确姿势是「假设 GIL 可能存在也可能不存在」：不要依赖它做原子性保证，+= 在自由线程下不是原子的。

关键点

  • GIL 不是 Python 语言规范，是 CPython 的实现；3.13 起提供实验性的 free-threaded 构建，但默认构建仍有 GIL。
  • GIL 不保证线程安全：x += 1 仍是「读—改—写」三步，可能被切换。
  • 进程有独立内存，通信要序列化（pickle），启动成本高。
  • 线程适合 IO，不是因为线程快，而是因为等待时不占 CPU。

动手

  1. 写一个 cpu_task(n) 与一个 io_task(seconds)，分别用串行、4 线程、4 进程跑，记录耗时表。
  2. 用 sys.setswitchinterval(0.0001) 缩短切换间隔，观察竞态是否更容易复现。
  3. 查一下你机器上的 Python 是否是 free-threaded 构建（sys._is_gil_enabled()）。

验收清单

  • 能用自己的话解释 GIL 保护什么、不保护什么
  • 给定 5 个任务，能正确判断该用线程、进程还是协程
  • 知道多线程不能加速纯 Python 计算的原因

第 38 课 · 线程与锁：竞态、队列与退出

讲解

竞态来自「读—改—写」不是原子操作：

Pythonimport threading

counter = 0

def worker():
    global counter
    for _ in range(100_000):
        counter += 1          # 可能被切换

ts = [threading.Thread(target=worker) for _ in range(4)]
[t.start() for t in ts]
[t.join() for t in ts]
print(counter)                # 通常小于 400000

加锁修复：

Pythonlock = threading.Lock()
counter = 0

def worker():
    global counter
    for _ in range(100_000):
        with lock:
            counter += 1

生产者—消费者用 queue.Queue，它内部已经处理好同步：

Pythonimport queue, threading

q = queue.Queue(maxsize=100)

def producer():
    for i in range(1000):
        q.put(i)
    q.put(None)               # 哨兵：通知消费者结束

def consumer():
    while True:
        item = q.get()
        if item is None:
            break
        process(item)
        q.task_done()

延伸：进程池的两个硬约束

Pythonimport multiprocessing as mp

def work(x):
    return x * x

if __name__ == "__main__":
    with mp.Pool(4) as pool:
        print(pool.map(work, range(5)))    # [0, 1, 4, 9, 16]

两个约束：

  1. 启动方式：Linux 默认 fork（复制父进程），Windows 与 macOS 默认 spawn（重新导入主模块）。用 spawn 时，启动代码必须放在 if __name__ == "__main__": 下，否则子进程导入模块时会再次创建进程，无限递归。
  2. 必须可 pickle：参数和返回值都要序列化，所以不能传 lambda、打开的文件、数据库连接、线程锁。函数本身也得是模块级可导入的，定义在函数内部的嵌套函数传不过去。

进程间默认不共享内存（Value、Array、shared_memory 例外）。这就是「进程绕过 GIL，但贵在序列化」的账：数据量大时，序列化开销可能吃掉并行收益。

关键点

  • 锁要尽量短，持锁做 IO 等于把并发退化成串行。
  • 避免嵌套锁，需要多把锁时固定获取顺序，否则会死锁。
  • Queue 的 task_done() 与 join() 配对，忘了会让主线程永远等。
  • 线程不能强杀，用哨兵或 Event 通知退出，再 join()。

动手

  1. 复现计数器竞态，记录 10 次运行结果，再加锁验证稳定在 400000。
  2. 用 Queue 实现「2 个生产者 + 3 个消费者」，处理 1000 条任务后主线程退出。
  3. 用 threading.Event 实现一个可停止的后台轮询线程。

验收清单

  • 能解释 counter += 1 为什么不是原子操作
  • 会用 Queue 写生产者—消费者，并知道哨兵的作用
  • 知道如何让线程安全退出

第 39 课 · 执行器：ThreadPoolExecutor 与 ProcessPoolExecutor

讲解

concurrent.futures 把线程/进程池抽象成同一套 API：

Pythonfrom concurrent.futures import ThreadPoolExecutor, as_completed

def fetch(url):
    ...

with ThreadPoolExecutor(max_workers=8) as pool:
    futures = {pool.submit(fetch, u): u for u in urls}
    for fut in as_completed(futures):
        url = futures[fut]
        try:
            print(url, fut.result())
        except Exception as e:
            print(url, "failed:", e)

ProcessPoolExecutor 用法几乎一样，但有两个硬限制：参数与返回值必须可 pickle，任务函数必须在模块顶层定义（__main__ 里直接跑要加 if __name__ == "__main__":）。

Pythonfrom concurrent.futures import ProcessPoolExecutor

def square(x):
    return x * x

if __name__ == "__main__":
    with ProcessPoolExecutor() as pool:
        print(list(pool.map(square, range(10))))

map 按输入顺序返回，as_completed 按完成顺序返回；需要「谁先好先处理谁」就用后者。

延伸：Executor.map 的返回顺序与异常时机

map 会立刻提交所有任务，返回按输入顺序产出结果的迭代器；异常不在提交时抛，而是等迭代到那一项：

Pythonfrom concurrent.futures import ThreadPoolExecutor

def bad(x):
    if x == 2:
        raise ValueError(x)
    return x

with ThreadPoolExecutor() as ex:
    for v in ex.map(bad, [1, 2, 3]):
        print(v)          # 打印 1，然后抛 ValueError(2)

它不会取消后面已提交的任务——3 和 3 之后的任务照样在跑，只是结果没人取。要边完成边处理就用 as_completed。map(..., timeout=n) 的计时从迭代开始算，超时抛 TimeoutError，但后台任务仍在运行（Python 无法安全中断线程）。

关键点

  • 线程池大小不是越大越好：IO 密集可以 2–4 倍 CPU 核数，CPU 密集取核数。
  • with 退出会等待所有任务结束；要提前取消用 shutdown(cancel_futures=True)。
  • 异常存到 Future 里，只有调用 result() 时才抛出。
  • 进程池启动慢，任务太短（毫秒级）时开销大于收益。

动手

  1. 用 ThreadPoolExecutor 并发请求 10 个 URL，打印每个的耗时与总耗时。
  2. 用 ProcessPoolExecutor 计算 8 个 CPU 密集任务，比较串行耗时。
  3. 故意提交一个会抛异常的任务，分别用 map 与 submit 观察异常传播方式。

验收清单

  • 能写出两种执行器的最小可用代码
  • 知道进程池对参数、返回值、入口代码的要求
  • 能解释 map 与 as_completed 的返回顺序差异

第 40 课 · 实战：并发下载与错误处理

讲解

需求：下载 50 个 URL，超时 5 秒，失败重试 2 次，输出成功/失败数量与耗时。

Pythonimport time
from concurrent.futures import ThreadPoolExecutor, as_completed
import urllib.request

def fetch(url, timeout=5, retries=2):
    for attempt in range(retries + 1):
        try:
            with urllib.request.urlopen(url, timeout=timeout) as r:
                return len(r.read())
        except Exception:
            if attempt == retries:
                raise
            time.sleep(0.5 * (attempt + 1))

def download_all(urls, workers=8):
    ok, failed = 0, []
    with ThreadPoolExecutor(max_workers=workers) as pool:
        futures = {pool.submit(fetch, u): u for u in urls}
        for i, fut in enumerate(as_completed(futures), 1):
            url = futures[fut]
            try:
                fut.result()
                ok += 1
            except Exception as e:
                failed.append((url, repr(e)))
            print(f"\r{i}/{len(urls)}", end="")
    return ok, failed

这个脚本的关键不是「用了线程池」，而是失败不会拖垮整体：单个 URL 抛异常只记录，不中断其他任务。

延伸：as_completed 与取消的边界

Pythonfrom concurrent.futures import ThreadPoolExecutor, as_completed

with ThreadPoolExecutor(4) as ex:
    futs = {ex.submit(pow, i, 2): i for i in range(4)}
    for f in as_completed(futs):
        print(futs[f], f.result())

按完成先后产出，适合进度条和「先到先用」。future.cancel() 只对「还没开始执行」的任务生效，返回布尔值表示是否取消成功；已经在跑的线程取消不了——线程没有安全的中断点。所以「取消」在并发里通常意味着「设一个标志位，让任务自己检查后退出」，而不是强行掐断。

shutdown(cancel_futures=True)（3.9+）批量取消排队中的任务；with 退出时默认 wait=True，会等所有任务跑完，这点在服务优雅关闭时要注意。

关键点

  • 超时必须显式设置，默认无超时会让线程永久挂起。
  • 重试要退避，固定间隔会在服务端故障时形成雪崩。
  • 并发度要有限制，无上限会耗尽文件描述符或被目标限流。
  • 进度输出要可关闭，日志环境里 \r 会污染输出。

动手

  1. 把上面的脚本跑在 10 个真实 URL 上（含 1 个故意错误的），记录成功/失败。
  2. 去掉超时参数，观察一个不可达地址会挂多久。
  3. 给脚本加「最大并发 4」与「总耗时统计」，输出一张结果表。

验收清单

  • 能写出带超时、重试、部分失败处理的并发脚本
  • 知道并发度为什么必须限制
  • 能解释重试退避的作用

本节额外补充：as_completed 与取消的边界

综合案例：并发抓取：串行慢，乱并发更糟

20 个资源要抓，个别会失败。先串行跑一遍看耗时，再用线程池加进度、重试与失败分类。

重构前（串行 + 一失败就中断）

for 循环逐个抓，单个失败只能靠外层 try 兜住，没有进度、没有重试；20 个请求就是 20 个延迟相加。

Pythonimport time

TRIES = {}


def fetch(url):
    time.sleep(0.01)                 # 模拟网络往返
    if url.endswith("7"):
        raise OSError("connection reset")
    return f"{url}:200"


urls = [f"/p/{i}" for i in range(20)]

start = time.perf_counter()
results = []
for u in urls:
    try:
        results.append(fetch(u))
    except OSError as e:
        results.append(f"{u}:failed")
print("串行耗时", round(time.perf_counter() - start, 3), "s")
print("成功", sum(1 for r in results if r.endswith("200")),
      "失败", sum(1 for r in results if r.endswith("failed")))

重构后（线程池 + 完成即处理 + 任务内重试）

as_completed 谁先好谁先出，进度才是真实的；重试放在任务内部，避免「整体重跑」把已成功的又跑一遍；单个失败被收集，不影响其他任务。

Pythonimport time
from concurrent.futures import ThreadPoolExecutor, as_completed

TRIES = {}


def fetch(url, retries=2):
    for attempt in range(retries):
        TRIES[url] = TRIES.get(url, 0) + 1
        time.sleep(0.01)
        if url == "/p/13":
            continue                                  # 永久失败
        if url == "/p/7" and attempt < 1:
            continue                                  # 第一次失败，第二次成功
        return f"{url}:200"
    raise OSError(f"{url} failed after {retries} tries")


urls = [f"/p/{i}" for i in range(20)]
ok, bad = [], []

start = time.perf_counter()
with ThreadPoolExecutor(max_workers=8) as pool:
    futures = {pool.submit(fetch, u): u for u in urls}
    for done, fut in enumerate(as_completed(futures), 1):
        try:
            ok.append(fut.result())
        except OSError as e:
            bad.append(str(e))
        if done % 5 == 0:
            print(f"进度 {done}/{len(urls)}")

elapsed = time.perf_counter() - start
print("并发耗时", round(elapsed, 3), "s")
print("成功", len(ok), "失败", len(bad))
print("失败明细", bad)
print("重试过的地址数", sum(1 for v in TRIES.values() if v > 1))

差异说明

问题 重构前 重构后 收益 代价
耗时 20 个请求串行相加 8 路并发，约 1/5 延迟被重叠 线程与连接有开销
进度 全部跑完才知道 每完成 5 个打印一次 可观察、可中断 需要计数与输出节流
重试 没有，失败即记失败 任务内重试 2 次 瞬时故障自愈 失败慢任务会拖长整体
单点失败 被 except 吞掉，明细丢失 收集异常文本 能定位哪个地址 代码多一层分类
顺序 天然有序 完成顺序（乱序） 谁快谁先出 需要保序时得自己排序
资源上限 天然 1 路 max_workers=8 不会打爆对方 墙钟时间受最慢任务影响

再往前一步

把重试加指数退避与随机抖动（0.05 * 2**i + random.random()*0.01），避免重试风暴；max_workers 应按「对方限流」定，不是按 CPU 核数。真要百万级任务，线程池会吃内存，应该换 asyncio + 信号量（下一单元），或用生产者-消费者队列控流。

单元验收

  • 判断：给 6 个任务分类，说明各自该用线程、进程还是协程
