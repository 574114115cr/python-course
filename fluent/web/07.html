单元导入

「面向接口编程」在 Python 里有三种落地方式：鸭子类型（只看行为）、静态协议（结构化类型检查）、抽象基类（显式契约 + 运行时检查）。它们不是互相替代，而是三种不同强度的约束。

继承则是被滥用最多的特性。super() 不是「调用父类」，而是「沿 MRO 调用下一个类」；多重继承能解决混入问题，也能制造难以调试的菱形。本单元会给出判断标准：什么时候该继承，什么时候该组合。

学完本单元，你应该能：

  • 用鸭子类型写不依赖具体类型的函数；
  • 用 Protocol 给第三方类做结构化约束，不要求对方继承你的基类；
  • 用 ABC 定义「必须实现」的契约，并理解虚拟子类注册；
  • 画出 MRO，写出协作式 super().__init__()，判断多重继承是否值得。

第 25 课 · 鸭子类型与抽象基类

讲解

鸭子类型：不检查类型，只调用需要的方法。

Pythondef render_all(items):
    return "".join(item.render() for item in items)

任何有 render() 的对象都能传进来。缺点是错误发现得晚——直到运行时才炸。ABC 提供显式契约：

Pythonfrom abc import ABC, abstractmethod

class Exporter(ABC):
    @abstractmethod
    def export(self, rows: list[dict]) -> str:
        ...

    def export_all(self, batches):
        return "\n".join(self.export(b) for b in batches)

继承 Exporter 但没实现 export 的类无法实例化，错误提前到创建对象时。标准库的 collections.abc 全是这种契约：Sequence、Mapping、Iterable、Sized。

ABC 还支持虚拟子类：不继承也能被 isinstance 认可。

Pythonfrom collections.abc import Sequence

class Bag:
    def __init__(self, items):
        self._items = list(items)
    def __len__(self):
        return len(self._items)
    def __getitem__(self, i):
        return self._items[i]

Sequence.register(Bag)
print(isinstance(Bag([1, 2]), Sequence))   # True

延伸：subclasshook：结构匹配的幕后机制

collections.abc 里的 Iterable、Sized、Container 都实现了 __subclasshook__，所以一个类不必继承它们，只要实现了对应方法就能通过 isinstance：

Pythonfrom collections.abc import Sized, Iterable

class Bag:
    def __len__(self): return 3
    def __iter__(self): return iter([1, 2, 3])

b = Bag()
print(isinstance(b, Sized), isinstance(b, Iterable))   # True True
print(issubclass(Bag, Sized))                          # True

机制是：isinstance 走 __instancecheck__ → __subclasscheck__ → 最终调 __subclasshook__(cls, C)，默认实现检查 C 有没有所需方法名。注意它只检查方法名，不检查签名，所以「有 __len__ 但返回字符串」也会通过。Sequence 之类更严格的 ABC 会把 __iter__、__len__、__getitem__ 都列进检查集。

关键点

  • ABC 的方法用 @abstractmethod 标记，但只要还有一个抽象方法没实现，类就不能实例化。
  • ABC 可以有具体方法，export_all 就是模板方法，子类只实现变化点。
  • register() 是承诺不是检查：注册后 isinstance 通过，但你仍要自己保证方法齐全。
  • 不要给所有类都套 ABC，只有「多个实现共享同一契约」时才值得。

动手

  1. 写 Exporter ABC 与两个实现（CSV、JSON），验证未实现抽象方法的子类无法实例化。
  2. 用 Sequence.register 让一个自定义容器通过 isinstance(x, Sequence)。
  3. 写一个只依赖 __len__ 与 __getitem__ 的函数，分别传 list、str、自定义容器。

验收清单

  • 能说出鸭子类型与 ABC 各自解决什么问题
  • 会定义带具体方法的 ABC，并解释模板方法
  • 知道 register() 的语义与风险

第 26 课 · 静态协议：Protocol 与结构化类型

讲解

typing.Protocol 是静态检查器的结构化类型：只要对象有对应的方法/属性，就满足协议，不需要继承。

Pythonfrom typing import Protocol

class Renderable(Protocol):
    def render(self) -> str: ...

def render_all(items: list[Renderable]) -> str:
    return "".join(i.render() for i in items)

与 ABC 的区别：ABC 是名义子类型（必须继承或注册），Protocol 是结构子类型（方法对得上就行）。给第三方库的类加约束时，Protocol 是唯一不侵入的选择。

需要运行时 isinstance 时加 @runtime_checkable，但它只检查方法是否存在，不检查签名：

Pythonfrom typing import Protocol, runtime_checkable

@runtime_checkable
class Closeable(Protocol):
    def close(self) -> None: ...

class Conn:
    def close(self): ...

print(isinstance(Conn(), Closeable))    # True

延伸：Protocol 的运行时检查很浅

Protocol 是给静态检查器看的「结构化类型」，能写 Iterator[int] 这类泛型协议；加 @runtime_checkable 后才能 isinstance：

Pythonfrom typing import Protocol, runtime_checkable

@runtime_checkable
class Closeable(Protocol):
    def close(self) -> None: ...

class Conn:
    def close(self): pass

print(isinstance(Conn(), Closeable))    # True

关键限制：运行时只查成员名是否存在，不查签名和类型。所以下面这个也会返回 True，但用起来就崩：

Pythonclass Fake:
    def close(self, force): pass        # 参数不对
print(isinstance(Fake(), Closeable))    # 仍然是 True

结论：runtime_checkable 只适合做「粗筛」，真正的行为约束靠测试或显式 isinstance 对具体基类。泛型协议（Protocol[T]）在 3.12 前还不能 runtime_checkable。

关键点

  • Protocol 不能实例化，它只描述形状。
  • runtime_checkable 只检查成员名，参数类型、返回值都不查。
  • 协议要小：一个方法一个协议，组合优于大而全的接口。
  • 标准库已有大量协议：Iterable、Sized、SupportsInt，优先复用。

动手

  1. 定义 Closeable 协议，让一个没有继承关系的类通过 isinstance 检查。
  2. 用 mypy 验证：把 render 拼错成 renders，观察类型错误。
  3. 写一个 SupportsAdd 协议，约束「支持 + 的同类型对象」，并解释为什么它比 ABC 更适合数值库。

验收清单

  • 能说清 Protocol 与 ABC 的适用边界
  • 知道 runtime_checkable 检查的粒度
  • 能给第三方类加协议约束而不修改它的代码

第 27 课 · 继承与 super()：MRO 与协作式构造

讲解

super() 返回的是 MRO 中当前类之后的那个类，不是「父类」。单继承时两者相同，多继承时差别巨大。

Pythonclass A:
    def ping(self):
        print("A")

class B(A):
    def ping(self):
        print("B")
        super().ping()

class C(A):
    def ping(self):
        print("C")
        super().ping()

class D(B, C):
    pass

print([c.__name__ for c in D.__mro__])   # ['D', 'B', 'C', 'A', 'object']
D().ping()                                # B C A

协作式构造要求每一层都接收 **kwargs 并继续传递，否则链条会断：

Pythonclass Base:
    def __init__(self, **kwargs):
        super().__init__(**kwargs)

class Logged(Base):
    def __init__(self, verbose=False, **kwargs):
        self.verbose = verbose
        super().__init__(**kwargs)

class Tagged(Base):
    def __init__(self, tag="", **kwargs):
        self.tag = tag
        super().__init__(**kwargs)

class Item(Logged, Tagged):
    def __init__(self, name, **kwargs):
        self.name = name
        super().__init__(**kwargs)

print(vars(Item("x", verbose=True, tag="t")))
# {'name': 'x', 'verbose': True, 'tag': 't'}

延伸：dict 子类的 missing 管不到 get

__missing__ 只在 d[k] 时触发，get 和 in 都不走它：

Pythonclass D(dict):
    def __missing__(self, key):
        return f"<{key} 缺失>"

d = D(a=1)
print(d["b"])        # <b 缺失>
print(d.get("b"))    # None ← 没走 __missing__

想统一行为就同时重写 get；更省事的做法是继承 collections.UserDict——它是纯 Python 实现，内部一个 data 字典，重写 __getitem__、__setitem__ 时不会遇到 C 实现的绕过问题。子类化 dict/list 的真实麻烦在于：dict.update()、|=、list.__init__、切片赋值这些 C 层路径可能不调用你重写的方法，而 UserDict/UserList 全走 Python 层。

关键点

  • super() 沿 MRO 前进，不由「父类」决定；菱形继承里每个类只执行一次。
  • __mro__ 是 C3 线性化结果，可以用 Cls.mro() 查看。
  • 子类化内置类型要小心：dict.update()、|= 等 C 实现可能绕过你重写的 __setitem__；需要可靠拦截就改用 UserDict、UserList 或组合。
  • 协作式构造只传关键字，位置参数在多层继承里极易错位。

动手

  1. 构造上面的 A/B/C/D，打印 MRO 并预测 ping() 输出，再运行验证。
  2. 实现 Item 的多层初始化，打印 vars() 确认字段齐全。
  3. 继承 dict 并重写 __setitem__，观察 update() 是否绕过你的实现；再用 UserDict 复现并对比。

验收清单

  • 能手工画出四层菱形继承的 MRO
  • 能解释 super() 在多继承中的实际行为
  • 知道为什么不该直接继承 dict / list
教材对照第 14 章 §14.2–14.3本节自足，无需回查原书

第 28 课 · 多重继承与混入类：什么时候不该继承

讲解

混入类（mixin）是「只提供一组方法、不单独实例化」的类，通常不带状态、不做 __init__：

Pythonclass JsonMixin:
    def to_json(self):
        import json
        return json.dumps(self.__dict__, ensure_ascii=False)

class User(JsonMixin):
    def __init__(self, name):
        self.name = name

print(User("Ann").to_json())   # {"name": "Ann"}

判断标准：

判断项 倾向继承 倾向组合
子类真的是父类的一种？ ✅ 不是就别继承
需要复用父类的实现？ 可以用混入 委托通常更灵活
父类会独立变化？ 不适合 ✅
继承层级超过 2 层？ 重新设计 ✅

组合通常更灵活：

Pythonimport json

class JsonCodec:
    def encode(self, data):
        return json.dumps(data, ensure_ascii=False)

class User:
    def __init__(self, name):
        self.name = name
        self._json = JsonCodec()

    def to_json(self):
        return self._json.encode({"name": self.name})

延伸：混入类不要写 init

混入类（mixin）的职责是「加一小块能力」，不是「初始化状态」。三条铁律：

  1. 不写 __init__；确实需要时只接受 **kwargs 并原样转交 super().__init__(**kwargs)。
  2. 只依赖调用方已经有的方法或属性，不假设自己的初始化顺序。
  3. 一层混入别超过 3 个方法，超了说明它是基类，不是混入。
Pythonclass JsonMixin:
    def to_json(self):
        import json
        return json.dumps(self.__dict__, ensure_ascii=False, default=str)

class User(JsonMixin):
    def __init__(self, name):
        self.name = name

print(User("Ann").to_json())    # {"name": "Ann"}

MRO 是 C3 线性化，super() 不是「父类」而是「MRO 里的下一个」。所以混入里调 super() 会按 MRO 继续往下走，这也是混入能协作的基础；层级超过两层、开始需要记 MRO 顺序时，换组合更稳。

关键点

  • 混入类不写 __init__，也不假设 MRO 的位置。
  • 「is-a」不成立就不要继承，哪怕代码看起来能复用。
  • 继承是编译期最强的耦合，父类改一个方法可能影响所有子类。
  • 优先组合 + 协议：需要多态就实现同一组方法，不需要共享实现。

动手

  1. 找出你写过的一个继承层级，用上表逐条判断是否该改成组合。
  2. 用混入类给 3 个不相关的类加 to_json()，确认它们都不需要改 __init__。
  3. 把一段「继承 + 重写 5 个方法」的代码改成「组合 + 委托 2 个方法」，比较行数与可读性。

验收清单

  • 能说出混入类的三个特征
  • 能用「is-a / 复用实现 / 变化方向」判断继承是否合理
  • 完成过一次「继承 → 组合」的重构并说明收益

综合案例：存储后端：用 if/else 分派，还是用接口收口

业务代码要能换存储：今天内存、明天文件。先写 if/else，再换成抽象基类。

重构前（一个类装两种后端）

Store.kind 决定走哪个分支，读写都要 if 一次。加第三种后端（Redis）时，每个方法都要再改一遍；调用方还得知道 kind。

Pythonimport json
import io


class Store:
    def __init__(self, kind="mem", stream=None):
        self.kind = kind
        self.data = {}
        self.stream = stream or io.StringIO()

    def put(self, key, value):
        if self.kind == "mem":
            self.data[key] = value
        elif self.kind == "file":
            self.data[key] = value
            self.stream.seek(0)
            self.stream.truncate()
            json.dump(self.data, self.stream, ensure_ascii=False)
        else:
            raise ValueError(f"unknown kind: {self.kind}")

    def get(self, key):
        if self.kind in ("mem", "file"):
            return self.data.get(key)
        raise ValueError(f"unknown kind: {self.kind}")


mem = Store("mem")
mem.put("u1", {"name": "Ann"})
print(mem.get("u1"))

f = Store("file")
f.put("u1", {"name": "Bob"})
print(f.get("u1"), f.stream.getvalue())

try:
    Store("redis").put("u1", {})
except ValueError as e:
    print("失败:", e)

重构后（ABC 定接口，两个实现各自负责）

Storage 只声明「必须有什么」，两个实现各自处理序列化。业务函数 save_user 只依赖抽象，连 kind 都不用知道。

Pythonimport io
import json
from abc import ABC, abstractmethod
from typing import Optional


class Storage(ABC):
    @abstractmethod
    def get(self, key: str) -> Optional[dict]:
        ...

    @abstractmethod
    def put(self, key: str, value: dict) -> None:
        ...


class MemoryStorage(Storage):
    def __init__(self):
        self._data = {}

    def get(self, key):
        return self._data.get(key)

    def put(self, key, value):
        self._data[key] = dict(value)


class StreamStorage(Storage):
    """把整表序列化到任意可写流，测试里用 StringIO，生产里换真文件。"""

    def __init__(self, stream=None):
        self._data = {}
        self._stream = stream or io.StringIO()

    def get(self, key):
        return self._data.get(key)

    def put(self, key, value):
        self._data[key] = dict(value)
        self._stream.seek(0)
        self._stream.truncate()
        json.dump(self._data, self._stream, ensure_ascii=False)
        return None

    def dump(self):
        return self._stream.getvalue()


def save_user(store: Storage, uid: str, name: str) -> dict:
    store.put(uid, {"name": name})
    found = store.get(uid)
    assert found is not None, "刚写进去的读不到"
    return found


mem = MemoryStorage()
print(save_user(mem, "u1", "Ann"))          # {'name': 'Ann'}

stream = io.StringIO()
disk = StreamStorage(stream)
print(save_user(disk, "u2", "Bob"))         # {'name': 'Bob'}
print(disk.dump())                          # {"u2": {"name": "Bob"}}

# 抽象类在实例化阶段就拦住「没实现完」的后端
try:
    class Half(Storage):
        def get(self, key):
            return None

    Half()
except TypeError as e:
    print("拒绝实例化:", str(e)[:60])

差异说明

问题 重构前 重构后 收益 代价
新增后端 每个方法加 elif 新增一个 Storage 子类 不改老代码 多一个类
未实现完整 运行时才报 unknown kind 实例化时 TypeError 错误提前到启动 每加方法都要给实现
调用方耦合 要知道 kind 字符串 只依赖 Storage 可替换、可 mock 需要传对象而不是字符串
序列化 混在 put 的 if 里 StreamStorage 自己负责 关注点分离 每个后端重复一点逻辑
存储位置 硬编码写流 构造时注入流 测试用 StringIO，生产换文件 生命周期要调用方管
未知后端 静默降级或运行时报错 类型系统挡住 早失败 需要类型检查器配合

再往前一步

把 Storage 换成 Protocol（只要求方法签名）：第三方类不用继承你的基类也能被接受，适合「接口是别人定的」场景；代价是实例化时不再有检查。再进一步加 delete、keys()、__contains__，并把「整表序列化」换成「追加日志 + 定期压缩」，避免每次写都重写全文件。

单元验收

  • 契约：同一个接口分别用 ABC 与 Protocol 实现，说明差异
  • MRO：给出一个多继承类，正确预测属性查找顺序
  • super：写出三层协作式 __init__，字段不丢
  • 取舍：为一个真实场景写出「继承版」与「组合版」，并给出选择理由
